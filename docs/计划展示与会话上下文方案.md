# 计划展示与会话上下文 · 方案

> **后续状态（2026-08-20）：** 文中 Kimi 行调研的是现已废弃的 ACP 链路。
> 内置 Kimi 改走 `kimi web` 后，计划直接读取公开 `todo_list` display，实时流与历史回填
> 都归并成同一张 `PlanItem`；下文 ACP 载荷分析仅作历史证据。

> 本文合成自四份候选设计、三路对抗评审、五份 adapter 落点调研。
> 所有行数用「eslint 口径」（`skipBlankLines: true` + `skipComments: true`）实测，不是 `wc -l`——
> 这个仓库注释密度极高，`wc` 会把余量高估四成以上。
> 所有引擎断言只写有证据的；查不清的一律进「待验证」，并写明怎么验。

## 一句话结论

**主题一（计划 / 待办展示）：做翻译，做卡，做一条只在有计划时才存在的常驻进度条；不做假进度、不做可勾选的步骤、不做长输出折叠。**

`plan` 这个 item kind 早就在 protocol 里了，四态齐全（`packages/protocol/src/item.ts:100-108`）。缺的不是协议，是**产出端**——claude 的 TodoWrite/Task 族被画成一条点不开的死行，codex 的 `turn/plan/updated` 被 switch 的 default 静默丢弃。所以第一刀是补两路翻译 + 抑制随之而来的重复工具行 + 把正文里那段 `<pre>` 换成一张卡；第二刀才是贴输入框上方的常驻进度条，而且它**完全数据驱动**：没有 plan item 就不进 DOM。不加 `EngineCapabilities` 位——能力位在这件事上会撒谎（见 §5.2）。

**主题二（项目 / 本地 / 分支）：只显示，不切换。先修两处现在就在说假话的地方，再把已有的两颗 chip 变成可点的；不做分支切换、不做原地换项目、不画「本地」chip。**

omni 其实**已经有两颗 chip 了**（`apps/desktop/src/renderer/components/Chips.tsx:49 行有效代码`，文件夹 + 分支），只是它们是死的 `<span>`，而且底下的 git 调用在空仓库和游离 HEAD 两种真实情况下会给出错误答案。所以主题二八成的真实收益在「修对 + 让它自己刷新」，不在「加控件」。分支切换给死结论：**不做**，理由是三条硬的（§6.3）。「本地」那颗 chip 搬到真正会变的那个轴上——不是「引擎在哪儿跑」（omni 恒为本机），是「你从哪儿看」，所以它只出现在 `apps/web`。

**三条从表里直接读出的结论：**

1. **三态是行业已经收敛掉的形状**——五家的枚举都是 `pending / in_progress / completed`（codex 只是 camelCase），和 protocol 的前三态一一对应。不存在「有的只有 done/not-done」这种对不齐。
2. **第四态 `dropped` 在任何一家上都没有可靠的生产路径**。claude 的 `TaskUpdate.status="deleted"` 在它自己的 reducer 里是**从表里删掉**；grok 的 `_meta.cancelled` 在本轮实跑抓到的 entries 里**根本没有 `_meta` 键**；其余三家封闭三态。**界面不得依赖 `dropped` 有数据。**
3. **单条工具耗时只有 codex 一家给得出，输出截断标记只有 grok 一家给得出。**为一家能填的字段改 protocol，等于把「按引擎名分叉」藏进数据里——两样本轮都不接（codex 的 1 MiB 截断标记除外，因为那是**修一处正在说假话**，不是加字段，见 §7.2）。

## 主题一 · 计划与进度展示

### 5.1 抽象放在哪一层

| 层 | 改动 | 为什么在这里 |
|---|---|---|
| `packages/protocol` | **零** | `PlanItem` / `PlanStep` 一个字节都不改。现有形状（text + 四态）恰好是五家的交集，加任何字段都会变成「一家能填、四家为空」 |
| `packages/engine` | 五路各写各的翻译，共享一张状态映射表 | 驱动内部的事件翻译本来就是逐引擎的 |
| `packages/host` | **零** | 计划不参与会话编排 |
| `packages/store` | **加一个纯函数文件** `plan.ts`（layer 1） | 桌面与手机端在 `scripts/check-arch.mjs` 的 LAYER 表里**同为 4、同层不得互引**。「第 N / M 步」是一个四分支算法，放渲染层必然在 web 端手抄一遍，而抄错不报错 |
| `apps/desktop/renderer` | 三个新组件（浮层 / 步骤行 / 内联卡） | 措辞与截断留在这里（要用 `tool.ts` 的 `VERB`/`brief`，那些不能进 store） |
| `apps/web` | 一个窄版进度条 | 见 §8.5 |

**`packages/store/src/plan.ts` 的边界要说死：纯函数、不读时钟、不返回文案。**
它导出 `latestPlan(items)` / `openPlan(items)` / `stepProgressOf(steps)` / `visibleSteps(steps, max)`，返回的是 `{index, total, done}` 这样的结构，**不返回「第 2 / 5 步」这句话**——让 store 不必知道 `/bin/zsh -lc '…'` 外壳长什么样，也不必知道手机屏比桌面窄。这是 `packages/store/README.md` 那条「不拥有渲染」的直接延伸。

同理，**不在 store 里编码「先画哪一档」的优先级**：那是纯呈现决策，两端的呈现预算不同（手机只画 8 颗点、不做展开）。

### 5.2 能力位：不加，而且加了是错的

题目问要不要给 `EngineCapabilities` 加一位 `plan: boolean`。**不加**，三条理由，第二条是决定性的：

1. **没有入口可给。**进度条不接受任何操作，它是只读陈述。`capability.ts:1-16` 那条原则管的是「这颗按钮出不出现」；而这条带子的出现与否由「这条会话里有没有 plan item」决定——那是数据，不是能力。
2. **`plan: true` 会变成一句假话。**能力位是握手时报的、静态的；而「这一轮有没有计划」是动态的：codex 的 `[tools] update_plan.enabled` 可以关掉，claude 的 Task 族被两道远程 开关控制着（Anthropic 可以在不改任何本地文件的情况下让它消失），kimi 今天压根不发。**一个握手报了 true、下一分钟一条都发不出来的能力位，比没有能力位更糟**——界面会给一个空面板，而不是不给面板。
3. **数据驱动的显隐已经实现了同一件事。**没有 plan item → 浮层不进 DOM → 天然满足「不给入口，而不是给一个点了没反应的控件」。这既不嗅探引擎名，也不嗅探命令名，完全符合那条原则的精神。

**什么时候才该加位**：如果哪天要做「用户在浮层上勾掉一步」——那是入口。而届时它对**五家都会是 false**（codex 的 plan 只有通知没有请求方法，ACP 的 plan 是单向推送，claude 的 todo 是模型自己的工具）。这条现在就写进「不做什么」。

### 5.3 「按工具名翻译」违不违反能力原则

不违反，但这条辩护**必须写进代码注释**，否则后人会拿它当反例：

`capability.ts` 那条原则管的是**界面上给不给入口**（它举的反例是 `commands.some(c => c.name === "compact")` 这种用命令名反推能力）。而 `claude/translate.ts` 里的 `TOOL_KIND` 表早就在按名字把 `Read`/`Edit`/`Write` 映射成 `file_read`/`file_edit`——驱动内部的事件翻译本来就是逐引擎的，那正是驱动存在的理由。界面那一侧看到的仍然只有 `kind: "plan"`。

不过在 ACP 那一路，判据**不用名字用形状**：`rawInput.todos` 是数组且每项有非空字符串的 `title|content` 与三态之一的 `status`。原因不是原则，是可靠性——ACP 的 tool_call 首帧连 `kind` 都可能没有（grok 实跑确认），title 是英文文案会随版本变。这也正是 kimi 自己的 web 后端 kap-server 在用的判据。

### 5.4 UI 形态：三个面，分工说死

> **正文里的内联卡回答「计划是怎么变的」；贴输入框的浮层回答「现在到第几步」；底部状态行回答「它此刻在干什么」。**
> 三件事，三个面，任何一个面不许兼职另外两个。

**（a）正文内联卡 `PlanCard`** —— 默认折成一行 `▸ 计划 · 5 步（2 已完成）`，点开才是完整列表。

为什么不保留现在那段完整的 `<pre>`：浮层已经在显示当前计划，正文里再画一份完整的，同一份东西在一屏里出现两次。而折成一行**保住了浮层给不了的东西——时间**：一条多轮会话里会散落 N 条 plan item，每条钉在它第一次出现的位置，那正是「计划在哪一刻被改写了」的记录。

**（b）常驻浮层 `PlanPanel`** —— 挂 `Workspace` 的 `Between` 带子（Transcript 与 Composer 之间），不挂 `.composer__inner` 内的绝对定位层。

折叠态一行：

```
◐ 第 2 / 5 步 · 把 codex 的 plan 通知接进 wire        ⌄  ×
```

- 三态圆圈（`○` 未开始 / `◐` 进行中 / `●` 完成，`dropped` 画 `×`）；
- 药丸「第 X / N 步」；
- 当前步文本用 **CSS 单行省略，不在数据层截**——数据层截了，复制和读屏就只剩半句；
- chevron 展开；最右一颗 `×`（本会话收起）。

展开态：完整列表（与 `PlanCard` **共用同一个 `PlanSteps` 组件**，这是保证「当前步」标记两处逐字一致的唯一办法）。超过 8 条时不做无限滚动，抄 kimi TUI 的选择策略：先收全部 `in_progress`，再用最靠前的 `pending` 填满，**但两边都有候选时给「最后一条刚做完的」留一个槽**，底部一行「… 还有 N 条（3 已完成 · 2 未开始）」。直接截前 8 条不行——一份 12 步的计划走到第 10 步时，前 8 条全是打勾的，屏幕上等于什么都没说。

挂点的三选一：

| 方案 | 结果 | 判断 |
|---|---|---|
| `Between`（`Changed` / `Queued` 的邻居） | 占布局，把输入框往下推 | **选它。**这条带子的形制、CSS、展开方向（往上长，避免顶走输入框）都有现成先例 |
| `.composer__inner` 内绝对定位 | 盖住转录区底部 | 不选。① `z-index: 20` 已被 `.mentions` / `.slash` 占着，常驻元素挤进去必然要写「打开 `@` 时让位」；② **常驻的东西盖住内容是错的**——瞬态菜单可以盖，常驻的不能 |
| `Popover` | — | 不选。它设计成瞬态菜单，capture 阶段的 `pointerdown` 就关，常驻用它等于点一下别处就消失 |

`Between` 里三条的顺序：`Changed` → `PlanPanel` → `Queued` → 输入框。从上到下是「跑完的账 → 正在跑的进度 → 你还没发出去的话」。

**（c）底部状态行 `TurnStatus`** —— **一个字都不动。**

### 5.5 正面回应 TurnStatus 那段反对钉住状态行的注释

`TurnStatus.tsx:12-28` 是一条明确的既有决策：上一版把状态行挪到输入框上方，错在「把两件事绑在了一起」——「它在想什么」是**对话内容**，就该长在对话末尾；「停下来」才是逃生口。而且它给出的正确解法（「回到底部」按钮）在 `Transcript.tsx:220` 已经实现了。

**这段注释是对的，而且它没有否定本方案。**判据是「变不变」和「可不可校验」：

- 「它在想什么」是**连续量**：每秒都在变，是模型的意识流。钉在底部会变成一个和对话无关的跑马灯——那段注释是对的。
- 「走到第几步」是**离散量**：一轮里变三五次，每一次都是模型自己声明的一个可校验的事实。它更接近 `Changed` 的「N 个文件已更改」——一个稳定的、你随时想瞥一眼的事实。它在 transcript 里其实**没有正确的位置**，往哪儿插都是错的。

所以边界划死：**浮层里只放步骤和序号，绝不放「正在思考」「正在运行 pwd」，也不放秒表。**

这一条是本方案里被评审判过 fatal 的地方，必须写清楚为什么这么收窄：曾经有一版设计在浮层里加了「第 7 个动作 · 执行 pnpm test」当降级档。**那是 omni 自己发明的假进度**——没有任何引擎报这个数，它没有分母、也不代表任何进展（模型可以连读 20 个文件一事无成），但它长得像进度、和上面的「第 2 / 5 步」共用同一个视觉槽位和同一句话式。这正是 `scope.ts:139` / `workdiff.ts:165` / `worksite.ts:25` 三处独立写过的最高优先级判据——**看起来正常、内容是错的，比空白难发现得多**。同时它还会和 `TurnStatus` 说出两个版本的同一句话（`brief()` 砍到 48 字并剥 shell 壳，浮层里更长），读者会当成两件事。

**结论：没有计划时，浮层不存在，就这样。**

### 5.6 「第 X / N 步」怎么算

```
N   = 非 dropped 的步数
idx = steps.findIndex(s => s.status === "in_progress")

idx >= 0             → 第 (idx+1) / N 步
idx <  0 且 done==N  → N / N 已完成
idx <  0 且 done==0  → 共 N 步          （不说「第几步」）
idx <  0 且 其余     → 第 (done+1) / N 步
```

**「一个 in_progress 都没有」必须处理，这不是防御性编程。**codex 的工具描述是 *at most one*，claude 是 *at least one*——两家保证的方向相反。写死 `findIndex` 会在 codex 上稳定地显示「第 0 / 4 步」。

`dropped` 不计入分母：药丸是给人算进度的，把已经放弃的步骤算进去，进度条永远到不了头。

### 5.7 三条派生规则

**规则 A · 取「最后一条 plan item，且它还有未完成的步骤」，跨轮取。**

不是「当前轮次的 plan item」。三家作用域不一样：codex 是 **turn 级**且不落 rollout（resume 即丢），claude 是 **session 级**（作为 tool_use 落 transcript），ACP 协议原文说 plan 是**会话级的一份**。按 `item.turnId === turn.id` 取，会让「这一轮没碰计划但上一轮的计划仍然有效」的情形掉档，带子在第二轮莫名其妙消失。

而且这条取法不是新发明：`packages/handoff/src/build.ts` 的 `openOf` 已经在用（取最后一份 plan、过滤 done 和 dropped），注释里还写了为什么不取并集。两处同源是好事。

**规则 B · 空 `entries` 是信号，不是噪声。**

zcode 在 todos 被清空时会发一条 `entries: []`（`_lastPlanSig` 初值 `"__none__"`，所以会话一开始的空列表也会发）。适配器**如实上报**（一条 steps 为空的 plan item），浮层视为「计划被清了」→ 不显示。**绝不在浮层里画一个空框**——那是最典型的「看起来正常、内容是空的」。

**规则 C · 中断之后，omni 侧把残留的 `in_progress` 降回 `pending`。**

用户中断一轮之后，浮层会永远停在「第 2 / 5 步」，而那一步早就没在跑了。修在 `acp/update.ts` 的 `sweep()` 里——它已经在对在途的**工具调用**做同一件事（把 running 改成终态，实测 `update.ts:270-281`），计划只是漏了。

**但这里有一处必须写进已知限制的冲突**：grok 会在轮次收尾额外发一条清扫版 plan，把还挂着的 `in_progress` **改写成 `completed`**（它自己源码里标为 transient、不落盘）。而这条在 ACP 线上和真实更新一模一样——同一个 method、同一份形状、没有任何标记。本轮实跑里模型只调了一次 `todo_write`、一个文件都没读，收尾那条却报「第 1 步 completed」。

后果有两层：① 轮次结束后药丸会自己往前跳一格；② 更要紧的是 `handoff/build.ts` 的 `openOf` 按 done 过滤，会**把没干完的活当成干完了带进交接包**。

**omni 修不了这个**（它是 grok 说的谎，且 omni 分辨不出）。处理办法：sweep 的降级只作用于 omni 自己确知的事实（轮次结束了，没有步骤在跑）；grok 后到的那条会覆盖成 done。唯一观察到的区别是真实更新的 `params._meta` 带 `eventId/promptId/updateType:"Plan"`，收尾那条整个 `_meta` 缺席——**n=1，不足以当判据**，进待验证（§11-3）。

### 5.8 状态机

```
没有 openPlan(items)              →  整条不进 DOM（不是隐藏）
有 openPlan，轮次跑着              →  显示，默认折叠成一行
有 openPlan，轮次结束、仍有未完成    →  继续显示（这正是它最有价值的时刻：
                                       一轮跑完但活没干完，人要知道下一句说什么）
全部 done / dropped               →  openPlan 返回 undefined → 消失
用户点了 ×                        →  本会话收起
切换会话                          →  key={thread.id} 强制重挂，回到展开
```

**跳动次数**：因为只在有计划时进流、且跨轮沿用到做完，布局跳动是「**每份计划各一次**」而不是「每轮各两次」。这是拒绝「无计划时也常驻」那个设计的另一个具体收益。

**收起态的归宿**：`key={thread.id}` + 组件内 `useState`。不放 `useApp`（实测 160/200，余量要留给别的）；代价是切回来会展开——这个代价换掉了「收起态跟着跑到下一条会话」那类静默串台，值。

### 5.9 降级链条：omni 的兜底只做翻译和展示，不做生成

1. **不替引擎拆步骤。**一家引擎这一轮没发计划，就是没有计划。不做「omni 从模型正文里抠出 1. 2. 3. 自己拼一份」——那是替引擎做编排，越过 AGENTS.md 的线，而且失败模式是「看起来正常、内容是编的」。
2. **不做计划过期提醒。**kimi 引擎内部有一套（10 轮没写 todo 就往上下文注入当前列表），omni 不该复刻——那等于往模型的上下文里塞 omni 自己写的话。
3. **不做「用户在界面上勾掉一步」。**协议全是单向推送，做成可点的复选框 = 点了引擎不知道 = 界面和引擎的状态永久分叉。**勾选框长得像可点的，所以连样子都不要做成方框**——用圆圈。

## 主题二 · 会话上下文

### 6.1 定性

**只显示，不切换。**增量收敛到四件：

1. 修两处现在就在说假话的地方（空仓库 / 游离 HEAD）；
2. 把白送的「未提交 N 个文件」取出来（现在算了却扔掉）；
3. 让它自己刷新——窗口 focus + shell 类工具收工，由此产出「这一轮里分支从 X 变成了 Y」；
4. 把两颗死 `<span>` 换成 `<button>`，点开走**已有的** `EnvCard`。

### 6.2 项目：omni 已经有了，v1 零新增数据面

**「项目」从来就不是引擎的概念**（表二：0/5）。各家自己也都是从 cwd 反推的——kimi 的项目列表就是把 `session_index.jsonl` 里出现过的 workDir 去重，和 omni 的 `projectsOf` 是同一个算法。

而 omni 其实已经有一个成型的项目概念，只是没给它名字：

```
身份    cwd（绝对路径，主键）
清单    Settings.projects（打开过的，一个项目不必有会话）
        ∪ projectsOf(rows)（从 Thread.cwd 归堆，name 取 baseNameOf）
不在项目中工作   workspaceKind: "chat" + chatDir() 在 ~/Documents/omni/<日期>/ 建目录
图标/排序/置顶   projectIcons / projectOrder / pinned / threadOrder
```

**v1 只做一件：项目 chip 从 `<span>` 变成 `<button>`，点开走 EnvCard。**

**不造 `ProjectPicker`。**侧栏已经有完整的四件套：按项目分组、新建会话、新对话、打开一个文件夹，项目行悬停还有 `+`。再复制一份到输入框旁边只会多两处状态要同步——`renderer/omniCommands.ts:12-17` 对同一个问题已经表过态（「改模型 / 改信任档：输入区里已经有两个下拉，就在手边，再复制一份到命令面板只会有两处状态要同步」）。

**「更改此聊天的项目 ⌥⇧⌘O」做不到，三层堵死：**

1. **协议层**：`Command` 联合 18 种里没有 `thread.setCwd`；`host.ts` 的 `HANDLERS` 是由这个联合**映射**出来的表，漏接一条编译不过——所以「悄悄加一个 handler」这条路不存在。
2. **运行层**：cwd 在 `driver.start()` 那一刻被冻进驱动（各家此后一律读 `this.req.cwd`，没有 setter）；审批规则表是 launch 时读的**一次性快照**；ACP 更是明说 cwd 是会话身份的一部分（`load` 的 cwd 必须与会话原 cwd 一致）。
3. **语义层**：审批记忆按 cwd 分桶。一条会话在 A 目录点过的「一直允许」，挪到 B 目录之后要么跟着走（越权），要么不跟（用户以为自己授过权）。**两种都错，而且都是静默的。**

所以入口的语义写实：**「在别的项目里开一条新的」，不是「把这条挪过去」。**文案必须说实话——写成「更改」的话，点开发现开了一条新会话会被当成 bug，而它不是 bug。

**「带着这段对话换个地方跑」的正确形状**：给 `thread.fork` 加一个**可选的目标 cwd**（`branch.ts` 现在是对象展开、沿用源 cwd），**不是**给 `Thread` 加 setter。本版不做，方向写死，免得后来人走上 setCwd 那条路。

### 6.3 分支切换：**不做**（死结论）

先承认正方的四条，都成立：

- 数据已经在手上，chip 已经在屏幕上，切换只差一条命令；
- 「引擎会改到哪个分支」omni 自己已经认定必须常驻可见，让人原地改它是自然的下一步；
- **agent 现在就能自己切且不问人**：`packages/approval/src/redline.ts` 里跟 git 有关的只有 `git-push` 和 `git-destructive`（后者只认 `reset --hard` / `clean -f` / `checkout --force`），一条裸的 `git switch feature` 三条都不命中，落到档位默认，而 `exec` 在 auto-edit 档下是 `allow`；
- 不带 `-f` 的 `git switch` 实测**绝不丢数据**（要么拒绝、工作区原样不动，要么把改动带过去）。

**结论仍然是不做**，三条更硬的：

**（一）失败模式的性质不对——全是「看起来成功、内容是错的」。**

- **归属静默错乱**：脏文件在两个分支上内容**相同**时，`git switch` **成功**，只在 stdout 打一行 `M shared.txt`，改动被安静地带到新分支上。agent 在 feature 上做了一半的活，现在挂在 main 头上了。**二次确认挡不住这个**——它挡的是「我不是想点这个」，挡不住「我不知道我这一半的活会被带走」。
- **cwd 被从目录树上摘掉**：`Thread.cwd` 指向一个只存在于当前分支的子目录（monorepo 里极常见），切到没有它的分支会把这个目录整个删掉。三层后果一层比一层糟：① 从这条会话再起任何子进程 → `spawnSync git ENOENT`，报错里一个「分支」字都没有；② `worksiteInfo(cwd)` 失败 → **你刚用来切分支的那枚 chip 自己消失了**；③ 实测确认：已经在跑的进程，cwd 被 unlink 之后 `process.cwd()` **照旧返回老路径**（撒谎），读相对路径 ENOENT，而**写相对路径会成功**——写进一个已经从目录树上摘掉的 inode。**agent 报告「已写入」，磁盘上什么都没有。**

第三层是 omni **无法探测、无法提示、无法补救**的失败。

**（二）既有判例直接适用，而且违反的是它的两半。**`omniCommands.ts:12-17`：「不可撤销的事不放进一个『打两个字母就中』的入口。它在行内 `···` 里，还有二次确认，那是它该待的地方。」而**贴在输入框上方、一直可见、一点就开的 chip，就是 omni 目前最低摩擦的入口**。

**（三）AGENTS.md「omni 不重写任何一家的能力」的同构推论。**git 是一家外部工具。omni 对它的立场至今一致：**只问 git 要只读事实**。全仓库调 git 的两个文件里，子命令全集是 `rev-parse` / `status` / `diff` / `ls-files`——**没有一条会改变 git 状态**。切分支会是第一条，而且它绕开了整个审批体系（信任档/红线管的是引擎请求的事，主进程自己发起的 git 写不经过那套闸门）。

**连 `git switch -c`（创建并检出）也不做。**单看 git 语义它确实无条件安全（不动任何文件、脏改动原样跟过去）。但它仍然踩（二）：**它把「写 git」这件事放进那个最低摩擦的入口**。一旦那颗按钮存在，下一版加「切到已有分支」就只是一行 `if`，而那一行的评审语境已经变成「反正这里已经能写 git 了」。

**绝对不做 auto-stash。**`git switch` 本身是 git 里少数几个绝不丢数据的命令（要么拒绝要么带过去），auto-stash 恰好破坏这个性质。

**那用户想切分支时怎么办——完整答案（说明白「不做」也是一种交付，留白才是偷懒）：**

| 场景 | 出口 |
|---|---|
| 我自己去终端切 | omni 自动感知：**窗口 focus 时刷新**。你要去终端切分支，必然离开 omni 又回到 omni——这一条覆盖全部情况 |
| agent 自己切了 | **shell 类工具收工时刷新** + 一行「这一轮里分支从 X 变成了 Y」。这件事**今天完全沉默**，而 auto-edit 档下它就在发生 |
| 想并行开两条线 | 用 `git worktree add ../omni-fix` —— 而 worktree 是**一个新目录**，于是它回落到「选目录」这条既有语义，omni 不需要任何新概念 |
| 真的要在同一个工作区切 | **omni 不做**，说出来，并给一颗「在终端里打开」把人送到能做的地方 |
| 想让这段对话换个地方接着跑 | 是 fork 加目标 cwd（§6.2 末），不是 setCwd。本版不做 |

**不做 `fs.watch` / `.git/HEAD` 监听**：全仓库零 watcher 是有意的（`packages/worksite/README.md` 明写「不监听文件变化，靠 15 秒 TTL」）。为了覆盖上面两条已经覆盖的场景引入第一个 watcher，收益和代价不成比例。

**分支列表本版也不做**：既然不切换，一份只能看的列表价值很低，却要新增一个 main 文件 + 一份真跑 git 的测试。真要做时，`git for-each-ref --count=100 --sort=-committerdate refs/heads` 实测 500 分支 39ms，且**只在点开面板时取**（不跟轮次节奏）。

### 6.4 「本地」chip：搬到真正会变的那个轴上

照抄会得到一颗**恒为「本地」**的 chip：omni 的产品边界钉死了只跑本机原生进程，而表二显示五家的「远程」全都不经 omni 现有的驱动路径。一个恒真的 chip 携带零信息量，却占一个视觉槽位、并暗示它可以被点开更改——**这正是「点了没反应的控件」的一个变体**：不是点了没反应，是看了没意义。

omni 里真正会变的是**你从哪儿看**：

- 在手机上看时，「引擎跑在那台 Mac 上，你在远程看」解释了一大堆事——为什么没有「在访达中显示」、为什么信任档被钳到 `maxTrust`、为什么关掉手机它照样在跑；
- 在桌面上看时，这句话是废话。

**所以：桌面端不画；web 端在 `ConnBar` 上加一行「在 <机器名> 上跑」。**数据走 `os.hostname()` 经 `/api/me` 加一个可选字段（实测该路由现在只回 `{id, name, maxTrust}`，`server.ts:208`）。

**不新增 `ServerFrame`**：机器名是**连接级常量**，不是会话事件流里刚刚发生的一件事；塞进事件流，每次全量重建都要重发一遍，还要顾及 `scopeReplay` 的字节预算。老桌面没有这个字段时那行整体不显示。

### 6.5 分支 / 项目 / 本地都不走 EngineCapabilities

`capability.ts` 的原则问的是「**omni 能不能驱动它**」。而这三样的判据是：cwd 是不是 git 仓库、git 装没装、`Settings` 里有没有这个 cwd——**全部与 engine 无关**。

加一位 `git: boolean` 的后果具体而荒谬：**同一个仓库换个引擎，分支 chip 就没了。**

这条要写进代码注释，因为「界面上给不给入口只看能力」很容易被误读成「所有入口都要有能力位」。正确的读法是它的否定式：**不许看引擎名字、不许嗅探命令名。**而「有没有 git 数据」是数据驱动的显隐，同样满足这条原则——就像计划浮层「有 plan item 才显示」一样。

**同理：不从任何引擎的私有索引里读项目列表。**kimi 的 `~/.kimi-code/session_index.jsonl` 技术上可达（`acp/kimi.ts` 已经在读它做交接包），但那是按引擎名嗅探、只对一家有效。项目列表只从 omni 自己的 thread 存储 + `Settings` 长出来。

### 6.6 新建会话首屏

**做「换个地方开」，不做起手卡片。**

**为什么不做起手卡片**：codex 那四张点了只往输入框填一个带尾空格的词（`"Explore "` / `"Build "`），第二层才是完整 prompt，且第二层按已连接的插件过滤——那套 omni 没有。而 omni 的用户是同时在用五家 coding agent 的重度用户，他们不缺「该说什么」的提示词模板。kimi 的新建首屏也没有起手卡片（只有一句空状态 + 项目 chip），说明这不是行业共识，是 codex 面向新用户的一个产品选择。

**首屏真正该说的话是「你在哪儿」**：从 Dock 冷启动时默认工作区是 home，人在那儿开始打字就是在 home 里跑 agent。现在 `Blank` 已经显示完整 cwd，属于「看得见但不显眼」。

所以首屏加两样：把当前分支/未提交数也显示出来（和输入框上方同源的只读上下文），以及一颗「换个地方开 ▾」。

**这颗按钮是唯一做选择器的地方**，理由和 chip 那颗恰好相反：新建首屏那里侧栏可能还没被注意到，而且此时会话是 `provisional`——**换地点等于另开一条，语义天然成立**（`create()` 里的 `dropTemps` 本来就会把上一条临时会话收掉，provisional 的会话不进侧栏、不落盘）。

面板内容三段，每一段都落在**已有**的动作上：

| 面板里的项 | 落到 |
|---|---|
| 项目列表（当前带勾，右边灰色短路径） | `Settings.projects` ∪ `projectsOf(rows)` |
| 「+ 打开一个文件夹…」 | 已有的 `openPicker()` |
| 「× 不在项目中工作」 | 已有的 `openChat()` |

**发出第一句话之后按钮消失（不是禁用）**——`provisional` 被清掉之后地点就锁死了，而「不给点了没反应的控件」这条对宿主自己的按钮同样成立。

**路径归一只做增量**：`/tmp/x` 和 `/private/tmp/x` 在 macOS 上是同一个目录，但 `projectsOf` 会分成两个项目（`workdiff.ts` 的 `gitRoot` 已经用 realpath 归一并在注释里点名了这条软链）。做法：`openPicker()` 拿到路径时由主进程 realpath 一次；**不追溯老数据**——那要改已有会话的 `Thread.cwd`，正好踩 §6.2 那三层。这是一个明确的「只修一半」，写出来是为了下次有人看到两个 `/tmp` 项目时知道这不是漏了。

**评审判定的 fatal 及其解法**（必须写在代码注释里）：

`loop.ts` 实测第 88-89 行是 `const pending = ref.tools.get(result.toolUseId); if (pending === undefined) continue`。而被抑制的工具行**从来没进过 `ref.tools`**——所以「不产工具行」和「从 tool_result 文本抠 taskId」两条在现有代码里互斥：taskId 拿不到 → 累积表建不起来 → 一条 plan item 都产不出，而工具行又被抑制了，**界面上关于计划一个字都没有，比今天那条死行还差**。

三层解法：

1. `absorbResult` 提到 `ref.tools` 门**之前**无条件跑一遍；
2. **抑制是条件抑制**：`absorbable()` 是形状判据（`TaskCreate` 要 `subject` 是非空 string、`TodoWrite` 要 `todos` 是数组且每项 `{content:string, status:三态}`），吃得下才抑制，形状不对的照旧产出 `other` 工具行——**畸形调用因此是可见的而不是被静默吞掉**；
3. 正则不匹配时步骤**留在 pending 里**（因而仍出现在合并列表中），所以万一 claude 改了那句文案，退化是「计划照画但状态不再更新」，不是「计划整个空掉」。

**三处刻意偏离 claude 自己的 reducer**，都写注释：
（a）`TaskUpdate.status = "deleted"` 映射成 `dropped` 而**不是**从表里删——omni 的 transcript 是事后要读的记录，一条步骤凭空消失读的人会以为自己记错了；claude 删它是对的，因为那是实时面板。
（b）`TaskUpdate` 撞上未知 taskId 时，带 `subject` 才建条目——claude 的 reducer 会拿 taskId 当标题建幽灵条目，那是「看起来正常、内容是错的」。
（c）**不读 `tool_use_result`**：它确实在流上（发送点已核到 `tool_use_result: i.toolUseResult` 是无条件展开的），但一条 user 消息只有一个该字段而 `tool_result` 块可以有多个，配对有歧义；正则是逐块的，没有这个问题。

**不做**：不注入 `CLAUDE_CODE_ENABLE_TODO_TOOLS=1`（§13-2）。

**那条被证伪的注释**：`notify.ts:88-93` 现在写着 delta 拼起来「**恰好等于**」收工时那条 `aggregatedOutput`，并预判失效模式是「双份输出」。**真实方向相反、是输出丢失**：`aggregatedOutput` 硬上限 1 MiB（超限时按 stdout 取 max/3、stderr 取其余，各自只保留**开头**，不插标记），而 delta 上限是按**条数** 10000 × 8192B ≈ 80MB。所以 1 MiB～80MB 区间里 delta 是完整的而 aggregated 被截，收工时 `item.updated` 整条替换会把用户刚刚看着滚过去的**尾部（错误就在那儿）安静地换成开头**。`packages/store/src/reduce.ts` 的 `MAX_LIVE_OUTPUT` 注释也建立在同一个错误前提上。

**codex 这一路不需要任何工具行抑制**——这是它和另外三家的实质差别。`PlanHandler::handle_call` 只做 `session.send_event(EventMsg::PlanUpdate(args))`，不 emit 任何 TurnItem；`TurnItem` 枚举里也没有待办清单变体（里面那个 `Plan(PlanItem)` 是 plan mode 的 markdown 提案，源码在上方专门写了一行注释区分）。**评审曾对「抑制工具行」记过一个 major（零证据），核实结果是该项应当从清单里删掉。**

（b）终态那条 `tool_call_update {status:"completed"}` 不带 todos，形状判据不命中，会顺着 `prev === undefined` 回落到 `onToolCall` 并在计划的 id 上**复活一条工具行**——`hidden` 早退必须加在回落之前。

**`translate.ts` 的输出修复（收益最大的一条）**：现在 `execDetail` 只读 `rawOutput.formatted_output`——那是 codex-acp 一家的私有键，**grok 和 zcode 都不发**。所以这两家的 shell 命令在 omni 上现在是「有一行命令、零输出」。新顺序：① `content` 里 `type === "content"` 的块取 `content.text` → ② `rawOutput.formatted_output` → ③ `rawOutput.output_for_prompt`（grok 的模型面版本，带 `exit: 0\n` 前缀，只当兜底）。

**两条不能错**：
- **只在终态读 `content`**。ACP 的 `ToolCallUpdate.content` 是 REPLACE 语义，而 kimi 在流式期间把 content 设成**累积的入参 JSON**；不加 `status === completed|failed` 的门，界面上会把「入参」当成「输出」显示。
- **不要碰 `rawOutput.output`**：grok 那个是**字节数组**不是字符串。

**形状判据会连带作用于三家**：grok 若命中，它那条 `Updating plan` 工具行会被一并吸收（grok 自己的 TUI 正是把它放进 `suppressed_tools`，属加分）；不命中则行为完全不变。两种结局都安全。

**grok 的 `_x.ai/git_head_changed` 本轮不接。**理由不是它不好，是分支的**数据**必须来自 omni 自己跑的 git（五家一致），而这条通知只能当「该刷新了」的提示；把提示落到界面需要新开一个只有五分之一引擎产得出的协议事件，且 `acp/driver.ts` 只剩 2 行。同样的刷新时机用 focus + 轮次首尾 + shell 工具收工就能覆盖，对五家都成立。**证据留档在 §11-7**，等真嫌延迟高再接。

### 8.1 main 的 git 调用

`apps/desktop/src/main/worksite.ts`（实测 59/300，余量充足）：

1. `git rev-parse --abbrev-ref HEAD` → **`git branch --show-current`**；空串 = 游离，再跑一条 `git rev-parse --short HEAD` 填 `head`。
2. `git status --porcelain` → **`--porcelain -z -uall`**，复用同文件已有的 `codesOf()` 出 `changed: number`，删掉 `dirty` 布尔。
   - **`-uall` 必须加**：不加的话未跟踪的整个目录折成一条 `sub/`，数会严重偏小（`workdiff.ts` 已经为同一个理由踩过一次）。
   - 口径必须和 `workChanges` **完全同源**（同一条命令、同一个 `codesOf`）。仓库里已经有三道各不相同的输出截断闸，不能再让「未提交多少个文件」出现第二种算法。
3. **四条 `run()` 全部显式加 `maxBuffer`**（照 `workdiff.ts` 的 `BIG * 4`）。这是评审记的一个 **major**：`execFile` 默认 `maxBuffer` 是 1 MiB，而按调查自己的实测场景（30285 条未 gitignore 的路径）输出会超限 → `ENOBUFS` → 现有的 `.catch(() => undefined)` **把它吞成「不是 git 仓库」**。也就是说在这个数最该出现的仓库上，整枚 chip 反而消失，而「封顶显示 999+」那条分支根本走不到。这条同时修掉 `workChanges` 里已经存在的同一个隐患。
4. 「不缓存」那条决策继续保持（注释原文：「一个过期的分支名比不显示更危险」），**焦点刷新正是它当初想要而没做的那一半**。

`apps/desktop/src/main/terminal.ts`（新，~35 行）：`open -a <Settings.terminalApp || "Terminal"> <cwd>`，参数走 argv 数组不过 shell。它是「想切分支请到终端里做」这条出口的落点。

**动作的判据**：只读且**目标必然存在**的动作可以默认给（Terminal.app 是 macOS 自带）；**要猜环境**的动作必须配置驱动、缺配置时不给入口而不是给哑控件——所以**不做「在编辑器里打开」**（`code` 命令未必装，其它编辑器更没准）。

## 风险与已知限制

### 明确接受的限制

1. **grok 的收尾清扫会把没做完的步骤说成 done。**它在轮次收尾发一条 transient plan，把 `in_progress` 改写成 `completed`，而 ACP 线上这条和真实更新一模一样。后果：药丸在轮次结束时会自己往前跳一格；`handoff/build.ts` 的 `openOf` 可能把没干完的活当成干完带进交接包。**omni 分辨不出，接受**（唯一可能的判据 `params._meta` 缺席，n=1 不足以采信，见 §11-3）。

2. **claude 的计划可能随时静默消失。**Task 族被两道远程 开关控制着，Anthropic 可以在不改任何本地文件的情况下关掉它；SDK 升到 ≥0.3.233 之后它也不在新模型的默认工具面上了。**界面表现是「没有 plan item → 没有浮层」，这是正确表现不是 bug**，要写进更新日志。这也正是不加能力位的理由。

3. **kimi 今天一条 plan 都不发**（v2 的 `TodoListTool` 漏了 `display`，像是从 v1 移植时的遗漏）。本方案改从 `rawInput` 形状还原，所以不受影响；但如果 kimi 哪天修好，会**同时**发 tool_call 和 plan，届时靠「plan 在 tool_call 之后到」的顺序收敛（这正是 acp-server 现在的发射顺序）。顺序若反转会多出一张卡——**未覆盖**。

4. **zcode 的输出被静默截到 2000 字符，不留任何标记。**所以任何「展开看全文 / 还有 N 行」的文案在 zcode 上都会是假话。本方案不做长输出折叠，正是因为这个诚实性问题解不掉。

5. **接回老会话时 codex 的计划一定是空的**（turn 级、不落 rollout），claude 的也是（累积器是进程内的，SDK 重放的是消息历史）。zcode 会在 `session/load` 重放（本方案修好了接收端），kimi 未知。

6. **单条工具耗时做不出来。**`item.updated` 携带的是整条新 item 且各驱动重铸 `at`（`acp/update.ts:125` 用 `ctx.now()`），`patchItem` 整条替换，「这条工具什么时候开始的」在 ViewState 里被销毁了。解锁点见 §11-8。

7. **claude 那一路的实时输出永远是空的。**内部 `bash_progress` 带 output/totalLines，转成 SDK 的 `tool_progress` 帧时全被丢掉。`ToolRun` 的 `LIVE_LINES` 尾巴对 claude 恒空——由数据驱动天然不渲染，但**不要为它预留视觉位置**。

8. **`/tmp` 与 `/private/tmp` 仍会被算成两个项目**（realpath 归一只做增量、不追溯，§6.6 末）。

   怎么验：跑一轮让模型把三步**真正全做完**，看最后那条 plan 带不带 `params._meta`；再跑一轮中途 interrupt，看清扫那条的形状。若 `_meta` 缺席这个差别稳定，就能在 `grok.ts` 里加一个私有判据，把清扫那条只用于「收起转圈」而不写进 done。**在验掉之前，不要让任何界面元素依赖 grok 的 done 是真的。**

4. **kimi 起一次真实的 `kimi acp` 会话。**
   怎么验：`packages/engine/src/acp/plan.live.test.ts`，发一个逼它写 todo 的 prompt，把 stdout 的 `session/update` 全录下来。三件事：(a) `grep '"sessionUpdate":"plan"'` 命中数为 0（钉死本方案的前提）；(b) `rawInput.todos` 的确切键名与 status 取值；(c) 走 lazy-create（先无 rawInput、后补）还是一次到位——这决定测试夹具照哪种写，**不影响设计**（就地转换对两种时序都成立）。

5. **zcode 的 plan case 先写上并接受失败。**
   本轮三次 turn 都被账号侧打回（3007 captcha verify failed / model_request_failed），换 GLM-5.3 与 GLM-5-Turbo 都一样。它的计划链路是逐行核对已安装的 0.5.1 产物源码得出的，**没有一次实跑报文**。同时要确认：它的 todo 工具会不会**也**发一条 tool_call（grok 是会的；zcode 的 `TOOL_KIND_MAP` 里没有 TodoWrite，会落 `kind:"other"`）。

6. **zcode 用什么字面量表示「放弃一条待办」。**
   `normalisePlanStatus` 只认三值、其余回落 `pending`，所以一条被放弃的步骤在 omni 上会**复活成「未开始」**。dist 里 `cancelled` 的五处命中经核对全是轮次取消、与 todo 无关。怎么验：在 zcode 里让模型放弃一条待办，看 `entries` 里那一项的 status 是什么。

7. **grok 的 `_x.ai/git_head_changed` 值不值得接。**
   本轮已验到底（不 opt-in 零条；在 `clientCapabilities._meta` 里加 `{"x.ai/gitHeadChanged": true}` 之后，会话建立时一条、外部 `git switch -c` 后数秒内一条，载荷 `{sessionId, branch, isWorktree, mainRepo}`）。接之前先量一件事：focus + 轮次首尾 + shell 工具收工这三个时机下，分支 chip 的**实际过期窗口有多长**。若从没超过一两秒，这条通知就永远不值得接。

8. **要不要让 `patchItem` 保住第一次的 `at`。**
   这是「每条工具跑了多久」的唯一解锁点。改成 `{ ...event.item, at: prev.at }` 是一行，但它改变了 `at` 的语义（从「最后一次更新的时刻」变成「第一次出现的时刻」），而 `group.ts` 的 `spanOf`、`export.ts`、`handoff` 都在读它。**单独评估，不夹带在本方案里。**

9. **`packages/store/src/reduce.ts` 的 `MAX_LIVE_OUTPUT = 8000` 是留尾不留头且完全静默。**
   界面上没有任何痕迹说开头被扔了——这是 omni 自己这一侧一处「看起来正常、内容不全」。修它要在 `ToolDetail.shell` 上加一个 `truncated` 位（协议改动）。本方案不碰，但**它比「显示更多 ∨」更该先修**：那个是外观，这个是诚实性。

## 被否决的做法及原因

写下来是为了防止以后有人重新提。

| 做法 | 否决理由 |
|---|---|
| **浮层加一个「第 7 个动作」的降级档**（无计划时也常驻） | omni 自己发明的假进度：没有分母、不代表进展（模型可以连读 20 个文件一事无成），但它长得像进度并和「第 2 / 5 步」共用同一个视觉槽位。撞三处独立写过的「看起来正常、内容是错的」判据。而且它会和 `TurnStatus` 说出同一句话的两个版本 |
| **把「正在跑什么」和「正在思考」从 `TurnStatus` 搬进浮层** | `TurnStatus.tsx:12-28` 是明确的既有决策，且它给的正确解法（「回到底部」）已经在 `Transcript.tsx:220` 实现了。两处都留会**不一致**（截断规则不同、取样时机不同），读者当成两件事 |
| **给 `PlanStep` 加 `id`** | 只有 claude 有；另外四家得靠数组下标伪造。一个「有时候是真身份、有时候是伪造下标」的 id 比没有更危险——界面会不知不觉地依赖它做动效，而整份替换加中间插步会让动效**稳定播在错误的行上**。直接推论：**不做需要步骤身份的动效** |
| **给 `PlanStep` 加 `activeForm` / `priority` / `explanation` / `blocks` / `owner`** | 全是一家能填、四家为空。加一个只有一家能填的字段，等于把「按引擎名分叉」藏进数据里 |
| **加 `EngineCapabilities.plan` / `.branch` / `.git`** | §5.2 与 §6.5。`plan: true` 会撒谎；`branch` 会导致「同一个仓库换个引擎，分支 chip 就没了」 |
| **做长输出折叠「显示更多（还有 N 行）」** | zcode 静默截到 2000 字符且零标记，ACP 唯一的 `truncated` 在 omni 不认领的 terminal 那条路上——那句话在 zcode 上必然是假的。而现状那个 320px 滚动盒已经解决了同一个问题。**诚实性结论保留为将来的前置条件** |
| **接引擎报的 `duration_ms`** | claude 的是每轮还是累计未验；codex 的要额外存轮次完成记录（store 跑完就把 Turn 摘了）；而「2 分 11 秒」和「2 分 9 秒」对人不可感。继续用 omni 自己的时钟，五家一致 |
| **把 `CLOCK_AFTER_MS` 从 15s 调小 / 把秒表搬进浮层** | 那条注释的理由仍成立（三秒的事摆个秒表，读数还没看清就没了）；时间是「这一轮」的属性不是「计划」的属性，挂到浮层上会让没有计划的会话没有秒表，反而更不一致 |
| **注入 `CLAUDE_CODE_ENABLE_TODO_TOOLS=1`** | 它改变的是**模型的行为**（会不会主动列计划），不只是接收信号——那越过「不做编排」的线。用户想要，claude 自己的 settings/env 就能开（omni spawn 时继承 `process.env`） |
| **设 `KIMI_CODE_LEGACY_FLAG=1` 换回带 `display` 的 v1 路** | 同上判据：替用户决定引擎怎么跑 |
| **在 initialize 里声明 `clientCapabilities.plan = {}`** | kimi 的 bundle 里 `plan_update`/`plan_removed` 的命中全是内部 plan-mode 的重放事件，不是 ACP 的那两个 session update；grok 用 Rust crate 0.10.4 不发新式。声明了今天一条也不会多 |
| **分支切换（含 `git switch -c`）** | §6.3 三条硬理由 + 滑坡论证 |
| **auto-stash** | `git switch` 本身绝不丢数据，auto-stash 恰好破坏这个性质 |
| **`thread.setCwd` / 原地换项目** | 协议、运行、语义三层都堵死（§6.2）。正确形状是给 `thread.fork` 加可选 cwd |
| **在输入框 chip 上做 `ProjectPicker`** | 侧栏已有完整四件套，再复制一份只会多两处状态要同步（`omniCommands.ts:12-17` 对同一问题已表过态）。选择器只放在新建首屏那一处 |
| **四张起手卡片** | omni 的用户不缺提示词模板；kimi 的新建首屏也没有，说明不是行业共识。首屏那块地方留给「你在哪儿」 |
| **画「本地」chip** | 恒为一个取值的选择器是装饰，且它暗示可以点开更改 |
| **走引擎问 git / 从引擎私有索引读项目列表** | 前者四家空白加一家特殊；后者（kimi 的 `session_index.jsonl`）是按引擎名嗅探、只对一家有效 |
| **手机端新增 `/api/worksite` 显示分支** | 手机场景里分支不可操作也几乎不需要；新增远程面 + 鉴权 + 节流不成比例，而 `server.ts` 只剩 6 行余量 |
| **`fs.watch` / 监听 `.git/HEAD`** | 全仓库零 watcher 是有意的；focus + 轮次 + shell 收工三条已经覆盖同样的场景 |
| **超时后退回上一次的分支名并标「陈旧」** | 与 `worksite.ts:19-27` 那条既有决策直接冲突（「一个过期的分支名比不显示更危险」），也与全文的「缺席优于假信息」冲突。**超时即整段不显示** |
| **未提交数封顶计算（500+）** | `workdiff.ts` 的 `MAX_FILES` 截的是要传给界面的**文件列表**（几十 MB 的实际负担），而这里只是一个整数。**不封顶计算、只封顶显示（999+）**，准确数放浮层 |
| **在 store 里编码「先画哪一档」的优先级** | 那是纯呈现决策，两端预算不同，撞 `packages/store/README.md` 的「不拥有渲染」 |
| **给 codex 的 `update_plan` 抑制工具行** | 核实结论：`PlanHandler::handle_call` 只 `send_event`，不 emit TurnItem，`TurnItem` 枚举里也没有待办变体。**codex 这一路不需要抑制**，写了就是无依据的代码 |

## 需要用户拍板的问题

1. **常驻进度浮层（批次 2）第一版做不做？**
   三路评审里两路支持、一路主张先只做「翻译 + 抑制 + 卡片」，跑一周看真实痛点再说。
   *推荐*：**做**，但排在批次 3（修 git）之后。理由是它已经被两条约束驯服了——完全数据驱动、跨轮沿用到做完（布局跳动从「每轮两次」降到「每份计划两次」）。砍掉它只需删三个文件，不影响其余批次。

2. **claude 升级 SDK 后计划会静默消失，omni 要不要注入 `CLAUDE_CODE_ENABLE_TODO_TOOLS=1`？**
   *推荐*：**不注入**。它改变模型行为而不只是接收信号；用户想要，claude 自己的 settings/env 就能开。代价是升级后「claude 这一路没有计划」，要写进更新日志并列入升级检查单。

3. **grok 的收尾清扫把没做完的步骤说成 done，要不要为它加私有判据？**
   *推荐*：**先不加，等 §11-3 验掉**。加了如果判据不稳，就是在一个说谎的信号上再叠一层猜测。但要接受它会污染交接包（`openOf` 按 done 过滤），这一条现在就写进已知限制。

4. **项目改名（`Settings.projectNames`）做不做？**
   两个具体的拦路：入口无处可放（`SidebarGroup.tsx` 实测 196/200，加一项就要再抽一次），以及 `thread.title` 是建会话那一刻的**快照**、改名后不会跟着变，于是首屏和侧栏会显示两个名字。
   *推荐*：**本版不做**。同名项目先靠已有的 `projectIcons` 区分。真要做时形状照 `projectIcons` 抄（键是路径、限长 40 字素、空串丢键、缺省不落盘），并明写 `thread.title` 不跟随。

5. **新建会话首屏（批次 4）要不要做？**
   它解决的是一个真问题（Dock 冷启动默认工作区是 home），但也是四批里最偏「新功能」的一批。
   *推荐*：**做，但排最后**，且严格只做「显示上下文 + 换个地方开」——不做起手卡片、不做搜索框以外的任何项目管理。
