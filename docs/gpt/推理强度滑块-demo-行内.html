推理强度滑块 · GPT 三个理解

综合 Kimi 的跟手与性能、Claude 的定宽与动效、Grok 的刻度与落点：控件先可用，状态再表达，窄屏最后让布局让步。

身份：GPT-5 驱动的 Codex，omni 的界面协作者。本页不替 Grok、Claude 或 Kimi 代言，而是在三方已验证的基础上补三点输入框判断。
01 · 语义先于皮肤

用原生 range 承担档位交互

渐变、拇指和动画都可以换，但键盘、触摸和辅助技术不该跟着重写。这个版本让原生 range 做真正的控制面。

▱ omni⌘ main
交代任务…（@ 引用文件，/ 用命令）

当前档位：最高。按 Enter 或点击发送开始。

焦点、方向键、触摸和档位步进由浏览器原生控制；视觉只负责表达已选位置。

02 · 状态要可读

把消耗提示放进可访问的状态层

不要只靠输入框边框、扫光或鼠标悬停的 title 说“更快消耗额度”。同一句话要能被键盘聚焦、触摸和读屏用户得到。

▱ omni⌘ main
交代任务…（@ 引用文件，/ 用命令）

当前档位：超高。发送后将更快消耗使用额度。

状态文本始终跟随 range 更新；颜色只做第二层提示，不把“是否重要”交给颜色本身。

03 · 布局让步

窄屏时让条子换行，不牺牲点击精度

宽屏保留“模型 → 强度条 → 发送”的一行关系；容器变窄后，条子占下一行，发送按钮仍在控制行右侧。下面的卡片故意限制为窄容器。

▱ omni⌘ main
交代任务…（@ 引用文件，/ 用命令）

当前档位：高。条子折到下一行。

换行是布局状态，不是错误状态；不用把 180px 的精度压缩成一条难以触摸的细缝。
