# GPT · 推理强度滑块

> **2026-09-25 起输入区已没有这条滑块**：强度只在模型菜单的「推理强度」一节里改，模型按钮写「模型 · 档位」（见 `更新日志.md`）。本文留作设计记录。

## 身份

我是 GPT-5 驱动的 Codex，本次作为 omni 的界面协作者，负责从交互、可访问性和响应式布局三个角度审查输入框。

我不是 Grok、Claude 或 Kimi，也不替任何引擎补造能力；这份目录只记录我对现有输入框方案的理解和一个可独立试用的对比 demo。

## 三方底稿

- **Kimi**：先解决跟手和性能——拖动时去掉追赶目标的过渡，用 `translateX`、rAF 合帧、CSS keyframes 和 `ResizeObserver`，并补齐 reduced-motion、键盘菜单和颜色对比。
- **Claude**：再解决展开的几何手感——宽度一次量定，用 `clip-path` 保持胶囊切口，展开 300ms、收起 200ms；同时用材质高光、深空和“最后一档才上色”验证状态表达不必只靠颜色。
- **Grok**：最后把信息落到控件结构——右端刃口、与档位数对齐的刻度，以及把最贵档的强调放到发送键，而不是让整个输入框常驻发光。

GPT 版沿用这三方已经验证过的结论：动画尽量交给合成器、条子保持稳定宽度、普通档保持中性、离散档位要看得见、贵的语义靠近发送动作。我的三点新增判断放在更基础的一层：控件语义、可访问状态和窄屏布局。

## 三个理解

### 1. 强度控制应该先是语义控件，再是视觉效果

现有 demo 用 `div[role=slider]` 自己接管拖拽、键盘和档位映射，视觉上很灵活，但每一个平台细节都要自己维护。GPT 版改用原生 `input[type=range]`：浏览器和移动端自带键盘、触摸、焦点和辅助技术语义，CSS 只负责把它画成行内条。

视觉上的“滑块”可以继续有渐变和拇指，但行为不应该依赖渐变来成立。没有颜色、动画或鼠标时，用户仍然能读到当前档位并把它改掉。

### 2. “更贵”要靠明确状态传达，不靠持续制造噪声

普通档保持安静；到最高消耗档时，只在发送动作附近给出强调，并把完整说明放进可读的状态文本。这样既保留了现有“落点”思路，也不把整张输入框长期染成警告色。

提示不只放在 `title`：键盘聚焦、触摸和读屏用户也要能得到同一句“当前档位 / 发送后的影响”。状态文本用 `aria-live` 更新，颜色和动画只是辅助信号。

### 3. 行内展开要优先保护输入和发送两个锚点

宽屏时，条子在模型和发送按钮之间展开，发送按钮保持在最右侧；窄屏时不要把条子压到难以点击的 96px，而是把条子独占下一行，输入区高度只增加一行，焦点和发送按钮位置仍然稳定。

这比“所有东西永远挤在一行”更符合真实窗口：输入内容、模型名称和审批方式都可能变长，布局应当让出空间，而不是让控制精度退化。
