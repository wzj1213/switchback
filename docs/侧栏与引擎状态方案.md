## 0. 修订 · 2026-08-19：按「共建者不是上下级」总纲翻掉 B 在 codex 上的结论

本文成稿之后，`AGENTS.md` 的「产品边界」加了总纲：**omni 与引擎是共建者，不是上下级**，
裁决判据是「**这件事是引擎自己把它当功能暴露出来的，还是 omni 拿它的零件替它攒出来的**」。

按这条重读 §6.2，**codex 的 `sideQuestion` 必须从 `true` 改成 `false`**：

- codex 的 app-server **没有「侧问」这个功能**。§6.2 那套是 omni 拿 `thread/fork(ephemeral)` +
  `inject_items` + `turn/interrupt` 三个底层 RPC，把 codex **TUI 里**的功能重新实现一遍。
- 代价在 §5.6 的自查表里已经写明「⚠️ 不满足」：要由 omni 携带一段 `SIDE_BOUNDARY_PROMPT`
  塞进模型上下文。照抄 `side.rs` 原文也仍然是 omni 在往模型上下文里塞话——总纲第①条直接禁掉。
- §4.1a 查实 codex 的侧问**不禁工具**，于是 §6.2 的补法是「omni 侧把这一轮按 `read-only` 判」，
  原文写着「**这是 omni 强制的，不是求来的**」——总纲第②条直接禁掉：审批层判每一轮，是因为
  用户在 omni 里选了那个档；单方面为某条 lane 改掉用户选的档，是 omni 在替他做决定。
- **而且本文自己已经有判例**：§6.3 否掉 kimi 的 `/btw` 用的理由是「它没从 ACP 那扇门出来，
  不是 kimi 弱，是这条路不通」。codex 的侧问同样没从 app-server 那扇门出来，
  只是它的底层原语恰好够得着。**够得着不是判据**，否则两家用的是两套标准。

**翻掉之后 B 的形态**：`sideQuestion` 只在 **claude** 上为 `true` —— 那是它 SDK 自己暴露的
`askSideQuestion` 原生 API（`skipTranscript` / `maxTurns:1` / `canUseTool` 一律 deny，
语义天生对得上，omni 只是调它，不携带任何提示词、不钳任何档）。codex / kimi / grok / zcode 全报 false，
界面按 §6.6 不给入口。**一家支持的能力还值不值得做，是产品问题**，见文末待办。

同时作废的还有：§5.6 表格 (b) 行的「明确接受」、§6.5 里 `codex/side.ts` 的落位硬约束、
§10 关于 `SIDE_BOUNDARY_PROMPT` 过期的风险项、§11 里那条「每次升级 codex 依赖时 diff 这两段常量」
—— 它们全都是为那个被翻掉的做法服务的。

A（状态回读）与 C（侧栏 / 进度树）**不受影响**：A 是纯读回引擎自报的值、永不覆盖 `Thread.trust`，
C 是把引擎已经推出来的东西换个地方画。两者都在总纲的正确一侧。

## 1. 一句话结论

| | 定性 | 怎么做 |
| --- | --- | --- |
| **A 引擎侧状态看不出来** | **做，而且第一个做。** 这不是缺功能，是**界面在撒谎**：档位下拉写着一个值，引擎实际在另一个值上，而 omni 已经收到了信号、在 `reduce.ts:165` 把它丢了 | 新增 `Thread.engineState`（只读镜像，**永不覆盖 `Thread.trust`**）+ 能力位 `modeReadback`；驱动经 `StartRequest.onEngineState` 回写，形状照抄唯一的既有先例 `onHandle` |
| **B 侧问混在主线里** | **做，但砍到单轮。** 第一版只支持「问一句、拿一段答案」，不支持在旧侧问上追问 | 能力位 `sideQuestion` + 命令 `thread.sideQuestion` + `EngineSession.askAside?`；claude / codex 报 true，kimi / zcode / grok 第一版报 false |
| **C 侧栏 + workflow** | **做侧栏，做进度树，但树排在最后一批。** claude 的 workflow **能**用同一个侧栏解决（§8） | `Lane` + `Item.lane` 一根正交轴；侧问和编排进度共用它。进度树是一条 lane 内部的扁平节点表，不是每个 agent 一条 lane |

三件事共用一条原则，而这条原则代码库里已经有先例（`mode.ts:140` 的 `warnNativeFixed`、`codex/driver.ts` 的沙箱 degraded）：

> **拿不准就说出来，不假装。** 引擎那边改不了就明说；引擎自己改了 omni 不假装是自己改的；这家读不回来就说「这里显示的是 omni 让它去的那一档」。

## 2. 现状与病灶

### 2.1 A：信号到了 `reduce()` 就断，或者驱动压根没往回走

1. **`engine.status` 只有三档会变成界面上的东西。** `reduce.ts:156` `const LOUD = new Set(["crashed","timeout","degraded"])`，`:165` `if (!LOUD.has(event.status)) return state`。而 `acp/update.ts:238` 的 `onModeChanged`（「引擎把档位切到了 X」）发的是 `status:"ready"` —— 正好落在被丢掉的那一档。
2. **同一条静默还吞掉了两句用户说明**，它们一次都没到过界面：`acp/mode.ts:120`（「没有报告可选档位，omni 的信任档只在本机判定层生效」）与 `:126`（「omni 的『X』档在 <引擎> 的档位里找不到对应项」）。这两句代码写着，但走 `ctx.status("ready", …)`。
3. **`engine.status` 这条路本身是死的**：`journal/src/codec.ts:19` 的 `SKIP` 跳过它（不落盘），`host/src/ctx.ts:132` 的 `LIVE_STATE` 也不收它（全量重建不补发）。走这条路的档位信号是「刷新即还原」的假状态。
4. **驱动碰不到 `Thread`。** `Thread.trust` 只有三个写入点，全在 `host/src/session.ts`：`newThread`、`adopt`（硬编码 `auto-edit`，注释写着「不猜它当初在引擎里是什么档」）、`setTrust`。驱动手上只有 `req.emit(Event)`，发不出 `thread.updated`。
5. **同一个 bug 已经存在于模型上**：ACP 的 `config_option_update` → `onConfigOptions`（`acp/update.ts:258`）→ `ctx.onCatalog`，驱动 adopt 到自己的 state 之后只 emit `models.updated`，**没有任何地方改 `Thread.model`**。于是 agent 自己换模型后 ModelPicker 画的还是旧值。
6. **还有一个真短路 bug**：`acp/mode.ts:129` `if (target === ctx.state.mode) return`。引擎自己切到 X 之后驱动的 `state.mode` 还记着旧值（`UpdateContext` 里根本没有 `state`，见 `acp/update.ts:28-50`），omni 再调 `setTrust` 想切到 X 时会误判「已经是这一档了」而**不发 `session/set_mode`**。

### 2.2 A 的真实场景不是用户举的那个 —— 必须先纠正

用户举的例子是「kimi 的 `/yolo` 打开全自动批准」。**这个场景在 omni 的架构下触发不到**，方案必须先说清楚，否则验收时会被当成没修好：

- omni 每条会话起一个私有 `kimi acp` 进程（`apps/desktop/src/main/registry.ts:52`）。用户在 omni 的输入框里打 `/yolo`，走的是 `thread.prompt` 的纯文本，而 kimi 的 ACP `available_commands` 只有 compact/status/usage/mcp/tasks/help + 动态技能，`/yolo` 会被判成 `Unknown ACP command`（**活体实测**，见 §4）。**用户在 omni 里没有任何途径打开 yolo。**
- 另一个 kimi TUI 是另一个进程、另一条 stdio，它改的档传不到 omni 这条连接上。

**A 真正会发生的漂移只有两类**，方案按这两类设计：

- **模型自己进/退计划模式**：grok 的模型调 EnterPlanMode 类工具时引擎会主动推 `current_mode_update`；zcode 每轮收尾会重读权威 mode 对账（都有源码证据，见 §4）。
- **omni 自己设档之后的回声不一致**：codex 的 TUI 就是照回声刷显示的，omni 现在做的是本地乐观更新。

### 2.3 B：斜杠命令没有路由层，`/btw` 必然是普通文本

`renderer/slash.ts:29` 只认行首 `/`，`useSlash.ts` 选中之后替换输入框文本，`Workspace.tsx:274-283` 最终 `send({type:"thread.prompt", text})`。`SlashCommand.source` 只影响面板分节。链路上没有任何一处能拦。而按 `capability.ts:1-15` 的原则，也不许靠命令名嗅探来拦。

### 2.4 C：分组轴只有 `turnId`，三个 `meta` 扩展位全代码库无人写无人读

`item.ts:17-18` 的 `meta?: Record<string, unknown>`（注释：「厂商特有字段的出口，借 ACP `_meta` 约定」）、`Turn.meta`、`Thread.meta` —— 全库没有一处赋值、没有一处读取。`engine/README.md` 说「其余 SDKMessage 落 meta 或丢弃」，实际全是丢弃。

`Turn` 也不能当载体：`store/src/state.ts` 的 `turns` 是 `Record<ThreadId, Turn>`（一个会话一条），`turn.completed` 一到就整条摘掉。

### 2.5 两个「今天就在错」的驱动层缺口

- **ACP 驱动从不读 `params.sessionId`**：`acp/driver.ts:221` 的 `onNotification` 只判 `method !== "session/update"`，是就转走，否则直接 `handleUpdate`。而 `wire.ts` 的 `AcpNotification` 明明声明了 `sessionId`。
- **codex 的 `notify.ts` 每个 handler 都用 `ctx.threadId`**（`:111`、`:256` 等），从不读 `params.threadId`。侧问 fork、detached review、子 agent 都在**同一条 stdio** 上推带不同 threadId 的通知。

## 3. 为什么必须是第三栏（先把更省的做法否掉）

评审提过一个正当的质疑：B 的隔离性本来就由引擎保证（claude 的 `skipTranscript`、codex 的 `ephemeral`），omni 剩下的活只是「画得看得出不同」；C 的进度树完全可以当成一条就地更新的 item 画在主线里（`PlanItem` 就是这个形状）。那为什么还要加一栏？

**结论：数据轴（`Lane`）先做，第三栏后做，而且第三栏要有它自己的理由。**

- **内联能拿到 80%**：侧问以缩进+异色块呈现，隔离是真的（来自引擎）；workflow 当一条自替换的 item，比现状（一行 `other` 工具 + 截断到 4000 字的结果，`claude/translate.ts` 的 `TOOL_KIND` 表里没有 `Task`）好一个数量级。
- **第三栏多买到的那 20% 是「并排」**：侧问要在主线**跑着**的时候读；workflow 树要在主线滚动时钉住不动。这两条是内联做不到的，也正是用户诉求 C 的原话（「专门承载旁路内容」）。
- **所以顺序是**：批 2 落 `Lane` 数据轴（此时侧问已经能用内联形态发布），批 3 才建第三栏。任何一批出问题，前一批都是可用的。

第三栏的连带成本一并列出（都在 §9 的文件清单里算过账）：`--aside-w` 进 `tokens.css`（`check:tokens` 强制）、`check:css` 的同端样式表校验、renderer 组件 200 行闸门、Compare 下的互斥、web 的换屏、以及 §10 记着的滚动竞争未验证。

### 4.1 三条必须写进正文的纠偏

**(a) codex 的侧问不禁工具。** 两份候选方案都把「原生侧问都硬禁了工具」当作准入判据，这在 codex 上是**假的**：`codex-rs/tui/src/app/side.rs:36` 与 `:50` 原文 —— *"External tools may be available according to this thread's current permissions"*，`:40`/`:56` *"Do not modify files… unless the user explicitly asks"*。全是**提示词层面的请求**，没有任何 veto/deny 机制。对照真禁的三家：claude 的 `canUseTool` 一律 deny、kimi `btwService` 的 `event.veto()`、grok 丢弃全部客户端工具调用。

→ 判据改成事实成立的那一条：**codex 与 kimi 的差别是 `ephemeral:true`（不落进引擎自己的会话列表），不是工具**。而「侧问不动手」这件事由 **omni 自己保证**：侧问 lane 的这一轮，omni 的审批层按 `read-only` 判（`@omni/approval` 的 `decide()` 在 omni 手上，见 `acp/permission.ts:113` `trust: ctx.trust()`）。这是 omni 强制的，不是求来的。

**(b) claude 的 `dontAsk` 是「预先拒绝」，不是最宽松档。** `claude/driver.ts:20` 注释原文写明 `acceptEdits`/`bypassPermissions` 预先放行，`dontAsk`/`auto` 预先拒绝（`auto` 用模型分类器判，omni 完全看不到）。→ **本方案不做任何 mode→Trust 的反向映射**（见 §5.1）。

**(c) claude 上 `adopt` 拿不到「当初是哪一档」。** `claude/driver.ts:75` 每次 `query()` 都显式传 `permissionMode: PERMISSION_MODE`（`:28` 常量 `"default"`），resume 路径只额外加 `resume` 字段、没有去掉 `permissionMode`。所以接管老会话时 `system/init.permissionMode` 报回来的必然是 omni 刚设的 `default`。→ **`session.ts` 那句「不猜它当初在引擎里是什么档」的注释继续成立，本方案不声称修好了它。**

## 5. 抽象设计

### 5.1 A 的载体：`Thread.engineState` —— 一组具名轴，不是一个 mode id

**上一版为什么不行**：两份候选都把「引擎自己的档」建模成单个 mode id。装不下：

- **codex 的档不是单值**。omni 的 Trust 在 codex 上同时落到两个独立旋钮：`codex/driver.ts:90` `sandbox: SANDBOX[req.trust]` 与 `:196` `approvalPolicy: POLICY[this.req.trust]`。而实测的 `thread/settings/updated` 快照里是 `approvalPolicy` + `sandboxPolicy` + `activePermissionProfile` + `collaborationMode` 四个并列字段，**没有任何一个叫 mode 的 id**。
- **grok 是两条正交轴**：mode 轴（Plan/Ask/Default，走 `current_mode_update`）与审批轴（走单向的 `_x.ai/yolo_mode_changed`，没有入站信号）。压成一维就得现编一个合成 id，然后对齐判定跟着变成猜。

```ts
// packages/protocol/src/thread.ts

/**
 * 引擎自己那边的状态。**只读的镜像，不参与任何判定。**
 *
 * 与 `Thread.trust` / `Thread.model` 的关系：那两个是**omni 设的**，这一份是**引擎报的**。
 * 两者可以不一致，而不一致本身正是要显示给用户看的东西。
 *
 * ## 为什么绝不能写进 `Thread.trust`
 *
 * `trust` 有双重身份：它既是「omni 想让引擎处于哪一档」，也是
 * **omni 本机审批判定器的输入**（`acp/permission.ts:113` 的 `decide()` 吃的就是 `ctx.trust()`）。
 * 引擎报 yolo 就把它写成 `full`，等于**顺手把 omni 自己那层审批也关掉**——
 * 那是用户从没点过的一次放权，而且没有任何地方会报错。
 * 任何把引擎自报状态直接写进 `Trust` 的方案都是一个静默提权口，一律排除。
 */
export interface EngineState {
  /**
   * 引擎自报的**每一维**当前值。一维一条，缺席 = 这一维读不回来。
   *
   * 为什么是数组不是一个字段：codex 的档同时落在 approvalPolicy 与 sandboxPolicy
   * 两个旋钮上，grok 的 mode 轴与审批轴互相独立且后者没有入站信号。
   * 压成一个值就得由驱动现编一个合成 id——那正是「界面显示一个引擎从没说过的东西」。
   */
  axes: readonly EngineAxis[]
  /** 引擎当前实际在用的模型 id。和 `Thread.model`（omni 设的）分开存。 */
  modelId?: string
  /** 这份镜像什么时候报的。**陈旧的镜像比没有更糟**，界面据此判断还显不显示。 */
  at: number
}

export interface EngineAxis {
  /**
   * 这是哪一维。ACP 家填 `"mode"`；codex 填 `"approval"` 与 `"sandbox"` 两条；
   * grok 填 `"mode"` 一条并**明确缺席** `"approval"`。
   * omni 不解释这个字符串，只用它做去重和排序。
   */
  axis: string
  /** 引擎侧原样的值（`"yolo"` / `"bypassPermissions"` / `"dangerFullAccess"`）。**omni 不翻译它。** */
  id: string
  /** 引擎给的人话名。没有就显示 `id`。**界面永远不自己编一个中文名。** */
  label?: string
  /**
   * omni 设的档和这一维**对不对得上** —— 由**驱动**判定，界面不反推。
   *
   * 反推做不到：`pickMode` 是 Trust→modeId 的打分匹配（`acp/mode.ts:76` THRESHOLD=4），
   * 有损、多对一，反过来是一对多。而驱动知道它自己发过什么、引擎回了什么，它答得起。
   * 上一版设计过一个 `trustHint`（驱动反向猜出 omni 的哪一档），已否决：见 §12。
   */
  match: "aligned" | "diverged"
}
```

**只留两档 `match`（观测）**，`unmapped` / `fixed` 移到它们该在的地方 —— 那两个描述的不是「引擎现在是什么档」，而是 **omni 最后一次设档的结果**：

```ts
/**
 * omni 最后一次把 `trust` 落到引擎上的结果。
 * 和 `engineState` 分开：那是观测，这是历史。混在一个字段里，消费方分不清哪些是现在。
 *
 * 这三档正好一一对上 `acp/mode.ts` 里**已经写着、但被 `reduce.ts:165` 的 LOUD 吞掉**的分支：
 * `unmapped` ← `mode.ts:120` 与 `:126` 的两句 `ctx.status("ready", …)`；
 * `fixed`    ← `mode.ts:140` 的 `warnNativeFixed`。
 * 补这一位和救活既有代码是同一件事。
 */
export interface TrustApply {
  result: "applied" | "unmapped" | "fixed"
  /** `result !== "applied"` 时给人看的一句话，由驱动给，**必须说得出下一步**。 */
  detail?: string
  at: number
}

export interface Thread {
  // …
  trust: Trust
  /** 引擎自报的状态。**只有驱动写得动，不参与任何判定。** */
  engineState?: EngineState
  /** omni 最后一次设档的结果。 */
  trustApply?: TrustApply
}
```

**为什么进 `Thread` 而不是像 `models` / `commands` / `usage` 那样另开一张 ViewState 表** —— 两条先例都摆着，选 `Thread` 的三个理由：

1. **落盘、resume 读得回、⌘R 不丢。** 走 `engine.status` 那条路的东西 `codec.ts:19` 不落盘、`ctx.ts:132` 不补发，是「刷新即还原」的假状态。
2. **手机端白捡。** `apps/web/src/screens/Thread.tsx` 的 `hintOf` 那行 `${thread.engine} · ${thread.trust}` 会自动跟着变。
3. **远程钳制看得见**（`remote/policy.ts:79` 的 `maxTrust` 判据读的是 Thread）。

### 5.2 A 的回写通道：照抄 `onHandle`，不新开事件

驱动手上没有 `Thread`，发不出 `thread.updated`。全代码库唯一一条「驱动发现了什么 → 写进 Thread → 落盘 → 上界面」的先例是 `contract.ts:95` 的 `StartRequest.onHandle` → `session.ts:44` 的 `rememberHandle`（注释：「走 `thread.updated` 而不是私存一份：那样它才会跟着事件流落盘」）。照抄。

```ts
// packages/engine/src/contract.ts —— StartRequest
/**
 * 驱动发现引擎自己的当前状态时回调。传部分字段，宿主做合并——
 * 引擎往往一次只报一样（claude 的 `system/status` 只带 permissionMode，
 * ACP 的 `config_option_update` 只带模型）。
 *
 * 为什么档位和模型合成一个回调：它们是**同一个 bug 的两个实例**
 *（见 §2.1 第 5 条）。分成两个，迟早有一条路上的人忘了 emit。
 */
onEngineState?: (patch: { axes?: readonly EngineAxis[]; modelId?: string }) => void
/** omni 设档的结果。`applyTrust` 现在那两句被吞掉的 `ctx.status("ready", …)` 改走这里。 */
onTrustApply?: (result: TrustApply) => void
```

宿主侧 `rememberEngineState` / `rememberTrustApply`，形状与 `rememberHandle` 一模一样，且**只接受它认得的字段，绝不碰 `trust`**。

### 5.3 A 的能力位：`modeReadback`

```ts
/**
 * 引擎会不会**主动告诉 omni 它自己改了档**。
 *
 * ## 为什么这一位不能省
 * `engineState` 缺席有两种截然不同的含义：「这家从不报，omni 不知道」，
 * 和「这家会报，现在恰好是对齐的」。不区分的话界面上长得一模一样。
 *
 * ## 这一位和别的能力位不是同一类，别混
 * `compact` / `steer` / `fork` / `sideQuestion` 管的是**给不给入口**——报 false 就不画按钮。
 * `modeReadback` 管的是**这条信息可信到什么程度**：报 false 时档位下拉照给
 *（omni 设得动，只是读不回来），但下面多一行灰字。
 * 把它当成「不给入口」那一类处理，等于因为读不回来就不让人改档——那是另一个 bug。
 */
modeReadback: boolean
```

### 5.4 B/C 共用的轴：`Item.lane` + `Lane`

```ts
// packages/protocol/src/item.ts
/**
 * 这条 item **不属于主线**，属于哪条旁路。**缺席 = 主线。**
 *
 * ## 为什么是 `ItemBase` 上的一等字段
 * (1) 不是新的 `ItemKind`：`protocol/README.md` 的「已知限制」写着新增一种就要动两端
 *     所有渲染分支，那是**有意的摩擦**。而旁路里的内容和主线里的内容本来就是同一种东西
 *     ——侧问的回答就是 `agent_message`，子 agent 的调用就是 `tool_call`。
 *     为侧栏发明第二套 item 类型等于把整套渲染写两遍。
 * (2) 也不该进 `meta`：`item.ts:17` 的契约是「厂商特有字段的出口，读之前自己判类型」，
 *     而 lane 归属是 omni 自己的一等概念、是渲染层每一帧的主分流轴。
 *     把主干逻辑放进一个自称要现场判类型的抽屉里，就是每个消费点各写一次 type guard。
 *     `meta` 仍然留给真正的厂商私货（zcode 的 `_meta.subagent` 那份 token 统计）。
 * (3) 可选字段：老日志回放时缺席，全部落主线，不需要迁移；
 *     `apps/web` 不认识它也不会崩（`pnpm typecheck` 跑 `apps/web/tsconfig.json`，
 *     加一种 ItemKind 会当场红，加字段不会）。
 */
export interface LaneRef {
  id: string
  /**
   * 挂在哪个工具调用下。主 transcript 靠它在那一行工具上画「在侧栏查看」——
   * 旁路内容被抽走之后，主线上会剩一条**看不出发生过什么**的 `other` 工具行，
   * 那比不抽更让人迷惑。**侧问不留锚点**：它本来就不该在主线上留痕迹。
   */
  originItemId?: ItemId
}
```

```ts
// packages/protocol/src/lane.ts（新文件，L0，零依赖纯类型）
/**
 * 一条**旁路**：属于这条会话、但引擎明说了它不属于主线 transcript 的东西。
 *
 * ## 为什么侧问和编排进度是同一个概念
 * 不是我觉得像，是各家自己的实现摆在那儿：
 * - claude 用同一个 `skip_transcript` 标了侧问 / 后台任务 / workflow 三类
 *   （sdk.d.ts:4710-4713 注释原文：「Consumers should hide this from the inline
 *   transcript; it may still appear in a tasks panel」——**引擎自己就假定宿主有一个独立面板**）
 * - codex 把三类全表达成「另一条 thread」（ephemeral fork / parent_thread_id / reviewThreadId）
 * - grok 三类走同一条私有通知 `_x.ai/session_notification`
 * - kimi 的 Web UI 已经用同一个侧面板渲染（`'compaction' | 'agent' | 'btw' | diff` 判别式）
 * omni 是目前唯一一个把它们平铺进一条 transcript 的客户端。
 */
export interface Lane {
  id: string
  threadId: ThreadId
  /**
   * **两档，不是五档。**
   * 界面上唯一真正的分歧是「这儿有没有输入框」：`aside` 能问，`activity` 只能看。
   * 再细分（workflow / subagent / 后台任务 / detached review）是**引擎自己的分类学**，
   * 界面不需要它——需要说明白的时候让 `title` 说。
   * 多分一档，就多一处接第五家时要改的地方（同 `EngineCapabilities` 的理由）。
   */
  kind: "aside" | "activity"
  title: string
  status: "running" | "done" | "failed"
  at: number
  /** 一句话结论（子 agent 的最终报告、侧问的答案摘要）。远程全量重建时它优先于 items。 */
  summary?: string
  /**
   * 进度树。**这条 lane 内部的扁平节点表**，不是每个节点一条 Lane。
   * 报不上来就缺席——缺席时画转圈，不画一条永远 0% 的进度条。
   */
  progress?: LaneProgress
  /**
   * 引擎侧的句柄：codex 是子 thread id，grok 是 child_session_id，claude 是 task_id。
   * **omni 只原样存取，不解释它**——和 `Thread.engineHandle` 同一条规矩。
   */
  handle?: string
}

/**
 * **全量快照，REPLACE 语义。**
 * 和 `item.updated` 携带整条 item 是同一个取舍：节点表很小，全量替换换来
 * 「渲染层永远不需要做补丁合并」。而且三家给的本来就是快照
 *（claude 的 `workflow_progress` 全量、grok 的 `WorkflowUpdated` 带单调 `revision`、
 * codex 的 `turn/plan/updated` 全量）。做增量补丁是在发明一个没人需要的合并逻辑。
 */
export interface LaneProgress {
  nodes: readonly LaneNode[]
  budget?: { used: number; total?: number }
}

export interface LaneNode {
  /** 支线内唯一即可。 */
  id: string
  label: string
  /**
   * 缺席 = 挂在根上。**树形只靠这一条**，不要再发明第二种表达。
   * 三家上游本来就是扁平的：claude 的 `workflow_phase{index}` + `workflow_agent{phaseIndex}`、
   * grok 的 `agents[]` 每个带 `phase`、codex 的 `agent_path` 是 `/root/worker` 路径串。
   * 硬拗成嵌套等于替三家做一次它们都没做的转换。
   */
  parent?: string
  state: "pending" | "running" | "done" | "failed" | "skipped"
  /** 最近一步在干什么，一行。引擎给不出就缺席。 */
  detail?: string
}
```

**为什么不是「每个 phase / 每个 agent 一条 Lane」**（候选方案 2 的做法，已否决）：一个 30 agent 的 workflow 每个 tick 会产生 30 条 `lane.updated`，而 `codec.ts:19` 的 `SKIP` 是**黑名单**（新事件默认全量落盘）；ViewState 里那个数组每条都要整表重建，任何 memo 直接失效；还得多一个「本身没有内容」的 `group` kind，而那正是它声称要消灭的 default 分支换了个地方。

事件只加一条：

```ts
/**
 * 一条旁路的当前样子。**upsert，全量替换**，同 id 覆盖。
 *
 * 不分 started / updated 两条：各家「起」和「改」的边界不一样
 *（claude 的 `task_started` 与 `workflow_progress` 是两条消息，
 * grok 的 `WorkflowUpdated` 第一条就是全量快照），分成两条就要让每个驱动
 * 自己记「我是不是第一次报这条」——那正是驱动最不该操心的事。
 * item 那边分三条是因为有流式文本要追加；Lane 没有流式内容
 *（它的内容以带 `lane` 的 item 形式走 item 那条路）。
 */
| { type: "lane.updated"; at: number; threadId: ThreadId; lane: Lane }
```

- **落盘**：落（它是内容，不是进程状态）。
- **`LIVE_STATE`**：不进（落盘了，重放能回来，补发反而重复）。
- **ViewState**：`lanes: Readonly<Record<ThreadId, readonly Lane[]>>`，`thread.removed` 时一起 `omit`（漏了就是内存泄漏）。
- item **仍然全部进 `items[threadId]`**，分流放在选择器里。理由：`owner` 表的语义要跟着变（`item.delta` / `item.updated` 只带 itemId，拆表后还得记「它在哪张表里」），而回放老记录时那批 item 没有 `lane`。选择器分流是纯函数、可表驱动测、老记录天然全落主线。

### 5.5 一条硬规则：审批与错误**永远不进 lane**

`ApprovalItem` / `ErrorItem` 都继承 `ItemBase`（`item.ts:12-19`），拿到 `lane` 就会随分流走进侧栏。侧栏关着、或选中的是另一条 lane 时，用户看不到一张**正在等他点**的审批卡。而 omni 刚发过一版专治「点了没反应、转圈没尽头」（`b719253`），这是在同一个坑上新挖入口。

→ **`kind: "approval"` 与 `kind: "error"` 的 item 一律不打 `lane`**，留在主线。这条写进 `protocol/README.md` 的「不拥有什么」。验收项：侧栏关着时在侧问里触发一次审批，主界面必须当场看得见。

### 5.6 B 的能力位、命令与驱动方法

### 5.7 驱动层地基：按 wire 的会话 id 分流

这不是给谁写 if，是承认一个被忽略的事实：**线上的会话 id 不等于 omni 的会话 id**（证据见 §2.5）。

- ACP 驱动与 codex 驱动各加一张 **wire 会话 id → laneId** 的登记表；登记过的走 lane，没登记的走主线。
- `AcpUpdate` / `AcpToolCall` 补 `_meta?: Record<string, unknown>` 并在 `toToolCall` 里透传到 `Item.meta`（zcode 的 `_meta.subagent` 现在整个丢掉了）。
- `handleUpdate` 的 switch 现在是 10 个 case + default（`acp/update.ts:287-310`），圈复杂度 ≈ 11，上限 12（`eslint.config.js` complexity 12）。加 `session_info_update` 就顶格。→ **同一批把它换成表**，照 `store/src/reduce.ts` 的 `Handlers` 映射类型写法，复杂度回到 2。

## 6. 各引擎落点与降级

### 6.1 claude

- **`modeReadback: true`。** 信号已经在 omni 当前订阅的那条 `for await (const msg of handle)` 流里，**不需要新通道**：`claude/loop.ts:145-151` 的 `case "system"` 只认 `subtype === "init"`，其余 `default: return`。放行 `subtype === "status"`（判据 `status === null && permissionMode !== undefined`），初值取 `system/init` 的 `permissionMode`（必填字段，现在只取了 `session_id`）。
  - **轴**：`axis: "permission"`，`id` 原样填 permissionMode。`match` 由驱动判：omni 把 SDK 的 permissionMode 钉死在 `"default"`（`claude/driver.ts:28,75`），所以引擎报的不是 `default` 就是 `diverged`。
  - **现实覆盖面要如实写**：omni 起自己的子进程（`driver.ts:81` `spawnClaudeCodeProcess`），没有第二个客户端能敲 `/permissions`。能触发的现实来源只有**模型自己进/退 plan 模式**。界面文案照 plan 写，别拿 `bypassPermissions` 当范例。
- **`sideQuestion`：运行时能力探测** `typeof q.askSideQuestion === "function"`，**不做版本嗅探**。探测通过但首次调用失败 → 出 Notice + 把能力降为 false（规则见 §6.6）。语义天生对得上：`skipTranscript:true`、`maxTurns:1`、`canUseTool` 一律 deny，所以这条 lane 里不会出现 tool_call。**历史由 omni 保管**（CLI 走 SDK 路径时 `threadHistory:false`）——第一版单轮，这块暂时不用。
- **workflow**：见 §8。

### 6.2 codex

- **`modeReadback: true`，代价是 `initialize` 要开 `capabilities:{experimentalApi:true}`**（今天发的是 `codex/driver.ts:239` 的 `capabilities: null`）。

- **workflow**：`CollabAgentToolCall` / `SubAgentActivity` 是稳定 item 类型，`agent_path`（`/root/worker`）按 `/` 切一刀就是 `LaneNode.parent`；`turn/plan/updated` 白捡。

### 6.3 kimi —— 三位全 false，而且这是故意的

- **`modeReadback: false`**，两条理由，第二条更硬：(1) acp-server 源码自己的注释「Engine-side mode changes are not observable」；(2) `currentModeId` 是纯内存镜像，`session/load` 后一律重置成 `default`，哪怕引擎实际还在 yolo（活体实测）。**报 true 等于让界面显示一个已知会撒谎的值。**
  - 规则写死：**kimi 驱动在 resume / adopt 路径上一律不报 `engineState`**，宁可空着。这和 `session.ts` 的 `adopt` 硬编码 + 注释「不猜它当初在引擎里是什么档」是同一条原则。

- **`sideQuestion: false`**：三重封死，证据见 §4。kimi 的 `/btw` 实现得很完整（fork 子 agent + `event.veto()` 硬禁工具 + 边界提示 + 独立面板），它只是**没有从 ACP 那扇门出来**。不是 kimi 弱，是这条路不通。
- **workflow：没有数据**，`lanes` 永远是空数组，侧栏开关不出现。
- **白捡一条**：kimi 会推 `session_info_update`（会话标题），是 omni 唯一漏接的一种 sessionUpdate，而 `event.ts:88` 的 `thread.renamed` 正好对得上。

### 6.4 grok / zcode

- **`modeReadback: true`，但只覆盖 mode 轴。** 引擎自己会切（模型调 EnterPlanMode 时 `enqueue_current_mode_update`），这条通知**已经到 omni 手上**，只是被翻成一行被吞掉的文字。审批档**没有入站信号**（`_x.ai/yolo_mode_changed` 单向）→ `axes` 里**缺席** `approval` 这一维，而不是编一个值。

**zcode**：

### 6.5 降级策略：omni 要不要自己兜底侧问

**分三档，档档不同，不做统一兜底。**

**档 1：引擎有原生侧问 RPC**（claude 的 `askSideQuestion`、grok 未来的 `_x.ai/btw`）。驱动直接调，omni 什么都没编排。

**档 2：引擎没有原生 RPC，但它自己的官方前端就是用 fork 拼的**（只有 codex）。**允许拼**，但必须过下面四条**可检验**的准入 —— 这四条取代候选方案里那句无边界的「照抄官方用法就不算编排」（按那句话可以顺势豁免 `/agents` 面板、CollabAgent 派生、detached review 编排）：

| # | 准入条件 | codex 现状 |
| --- | --- | --- |
| a | 全程只用该家的**稳定** RPC | ✅ fork / inject_items / turn/start / interrupt / unsubscribe 全稳定 |
| b | omni **不注入由 omni 维护的提示词文本** | ⚠️ **不满足** —— `SIDE_BOUNDARY_PROMPT` 要由 omni 携带 |
| c | 旁路会话**不落进引擎自己的历史** | ✅ `ephemeral: true` |
| d | 同一时刻**至多一条**旁路会话，且结束即回收 | ✅ 第一版单轮，跑完立刻 interrupt + unsubscribe |

**(b) 明确接受，并写进已知限制**：那段词**原样照抄 codex 的 `side.rs:28-56`，一个字不改写**，并在源码里留注释指向该文件。理由：不注入的话 fork 方案是坏的（模型会把继承历史当活指令）。它与 `item.ts` 那条「omni 不再替用户往对话里塞任何东西」的注释**不冲突但擦边**，两条线守住：① 那段话**不进 transcript**，omni 不为它铸 item，用户在侧栏看到的第一条永远是自己问的那句；② 它不是替用户表达意图，是协议层的边界声明。**接受的风险是它会过期**（codex 改了自己那份 omni 不会跟）——所以 §11 里有一条「每次升级 codex 依赖时 diff 这两段常量」。

**落位是硬约束**：这套拼装必须写在 `packages/engine/src/codex/side.ts`，**不许提到 `acp/` 或 `host/` 去当通用兜底**。一旦提上去，它就从「codex 的驱动实现」变成「omni 的编排逻辑」，而 host 里会长出一段「起一条子会话、注入提示词、等它答完、把结果收回来」的代码 —— 那句话就是 `AGENTS.md` 点名的坑。

**档 3：只有会话级 fork，没有侧问语义**（kimi）。**不兜底，报 false。**
- kimi 的 `session/fork` 报了能力也实测可用，但它是**会话级**的：新 sessionId、落进引擎自己的历史列表（用户点一次侧问，kimi 的会话列表里多一条他没建过的「Fork: xxx」）。这是把 omni 的实现细节泄漏到别人家的数据里。**codex 的 `ephemeral:true` 明确不落盘 —— 差别就在这儿，那不是一个可以忽略的参数。**
- 还要付上下文双份的 token，换来一个仿制品。这正是 `capability.ts` `NO_CAPABILITIES` 的原意：**默认不给入口，而不是默认给**。

**绝对不做的兜底**：把侧问退化成「普通 prompt + 一句『这是个侧问，别当成任务』的前缀」。那句话会真的进主线历史、真的占上下文、真的影响后续轮次，而界面把它画在侧栏里 —— **看起来隔离了，其实没有**，这是最坏的一种撒谎。

### 6.6 能力位可以晚到，也可以从 true 降到 false —— 但探测不许由用户点击触发

- `capabilities` 挂在 `Thread` 上、走 `thread.updated`，本来就可变，不需要新机制。
- **探测要在 `openSession` 握手阶段用一次无副作用的调用完成**，用户看到的按钮从出现的第一刻起就是可用的。候选方案里「用户第一次点侧问 → 拿 -32601 → 出 Notice 并收掉按钮」的做法**已否决**：那是把探测成本转嫁给用户，正是 `reduce.ts:180` 注释里「点了没反应」的招牌病。
- 握手阶段探不出来的（claude 的 `askSideQuestion` 只能探到「方法存在」），首次真实调用失败时**必须同时**：出一条 Notice 说清楚发生了什么，并把能力降为 false。「刚才有的按钮不见了」比「一直没有」更让人困惑，那条 Notice 是必需的不是可选的。
- **绝不做版本嗅探**（`if (version >= "1.0.6")`）。grok 1.0.5 的二进制里 `x.ai/btw` 0 命中而同期仓库 HEAD 里有 —— 这是版本嗅探会翻车的现成例子。

## 7. UI 设计

### 7.1 桌面端：第三栏

```css
/* app.css:104 —— 现状：grid-template-columns: var(--sidebar-w) 1fr */
.shell        { display: grid; grid-template-columns: var(--sidebar-w) 1fr; height: 100% }
.shell--aside { grid-template-columns: var(--sidebar-w) 1fr var(--aside-w) }
```

- `--aside-w` 进 `tokens.css`（现有 `--sidebar-w: 258px` 在 `:119`）。取 340px：比会话列表宽（里面要放 transcript），比 1fr 窄。
- **关闭时整列不渲染，不是宽度 0。** 宽度 0 的列里 `Transcript` 仍然挂着、仍然跑贴底逻辑、仍然在流式输出时触发 memo 比较 —— 那是一份看不见的性能账，而且是「只在长会话上表现为卡顿」的那种账。
- 状态挂进 `useShell`：`asideLane: string | undefined`（**不是布尔**）。`useShell.ts:25-30` 已经有 `comparing` / `settingsOpen` / `reviewOpen` 三个同类值。存 laneId 而不是布尔的理由：关掉再开应该回到刚才那条；存布尔就得再存一个「上次是哪条」，而两个值什么时候同步、谁负责清，在两个组件之间说不清楚。

### 7.2 与既有三个副面板共存

| | 形态 | 侧栏怎么办 |
| --- | --- | --- |
| **Settings / Review** | 覆盖层（scrim + `z-index:70` + `useModalKeys`） | 盖住就盖住，互不影响 |
| **Compare** | 换屏（`Compare.tsx` 自己渲染 `<main>`，内部 `grid 1fr 1fr`） | **Compare 分支不渲染侧栏**，`asideLane` 保持不变，退出自动回来 |
| **SidebarPane**（会话列表） | 布局第一列 | 不动 |

Compare 下不并排是算术问题：258 + 1fr + 1fr + 340 在 13 寸上每份 transcript 不到 300px，而 Compare 存在的理由就是并排读两份。更要紧的是「这条侧问属于左边那条会话还是右边那条」**没有不含糊的答案**，含糊的答案比没有更糟。

**Esc 的归属写死一条链**：有覆盖层 → 覆盖层；否则有查找框 → 查找框；否则不响应。**侧栏不进这条链**（它不是「打断你正在做的事」那一类），关它走顶栏按钮 + ⌘J。抢过来会让「关设置」变成「关侧栏」。

### 7.3 侧栏内部：复用现成件

```
┌─ 旁路 ─────────────────────  × ┐
│ ▾ 阶段一 · 探索             ✓  │  ← LaneTree：node.parent 缩进
│    ├ explore-a   ✓  12.4k     │
│    └ explore-b   ●  跑着…     │
│ ▾ 阶段二 · 实现             ●  │
│    └ impl        ●  Edit(3)   │
│ ────────────────────────────  │
│ ○ 侧问 · 这个 flag 谁在读      │  ← kind:"aside"
├───────────────────────────────┤
│ (选中那条 lane 的 transcript) │  ← 复用 Transcript
├───────────────────────────────┤
│ [ 问一句不打断主线的话… ] ↵    │  ← 仅 capabilities.sideQuestion
└───────────────────────────────┘
```

1. **多条 lane 时顶部用现成的 `Select`**（和模型 / 档位选择器同一个控件）。只有一条时不显示选择器 —— 一个只有一个选项的下拉框是纯噪音。
2. **内容区直接复用 `Transcript`**。`Compare.tsx` 已经证明它能并排两份，且 `onReuse` 可缺席（`Transcript.tsx:174` 注释：「对比视图里没有输入框，所以可以缺席」）。
3. **底部是精简输入框，不是 `ComposerBar`**：没有模型选择器、没有档位、没有附件。那些属于主线，摆在侧问下面只会让人以为改的是这条支线。
4. **`LaneTree` 不复用 `PlanItem` 的渲染**：那是个 `<pre>` 拼字符串前缀（✓/→/·/×），本来就不是树，只是当初凑合。
5. **无内容的节点不可选中。** `LaneNode` 是纯展示数据，本来就不可点 —— 这也是选「一条 lane 内嵌节点表」而不是「每个 agent 一条 Lane」的收益之一：一棵 20 节点的树里绝大多数点开都是空的，比不给点更糟。

### 7.4 分流的最小改动点与 memo 陷阱

在 `items` 进 `groupRows` **之前**按 `item.lane?.id` 分两份，两边各跑一次 `groupRows`（那是个有测试的纯函数，不用改）。

**稳定化必须放在 `useApp.ts`（实测 160/200，有余量）或新建的 `renderer/lanes.ts` 里，对外暴露稳定引用 `app.mainItems` / `app.laneItems`；任何组件内不得出现现场 `.filter()`。** 这个坑代码库踩过并留了注释 —— `App.tsx:150-152`：「**`app.items` 不是 `app.itemsOf(thread.id)`**：后者在空会话时每次渲染都造一个新数组，而 `Transcript` 的 memo 认引用」。现场 filter 的表现是「侧栏一开，主区打字就变卡」，而且没有任何地方报错。

### 7.5 档位的显示：显示 omni 的档，对不上时两个都显示

**默认只显示 omni 的档。** 它是唯一一个「用户点了就一定生效」的东西 —— 就算引擎那边接不上，它至少驱动着 omni 本机的审批判定层。引擎的档是个**观测值**：可能过时、可能读不回来（kimi）、可能只覆盖一半（grok）。

**有一维 `match === "diverged"` 时两个都显示，形态不同**：

```
档位  [ 自动编辑 ▾ ]
      ⚠ Claude 那边现在是 Plan（不是 omni 切的）。
        omni 的审批层仍按「自动编辑」在拦。            [ 切回来 ]
```

- omni 的档是**可操作的 Select**；引擎的档是**不可点的一行事实**，后面跟一个「切回来」（重发一次 `setTrust`）。
- **必须把后半句说出来**。只说前半句，用户会以为自己的档位被改了。
- `trustApply.result !== "applied"` 时另有一行：`unmapped` → 「这一档只在 omni 本机判定层生效」（不给动作，因为没有动作可做）；`fixed` → 「换档要重开一条会话」（给「新开一条」）。
- `modeReadback: false` 时是一行灰字：`${engineLabel} 不会把它自己改的档位告诉 omni；这里显示的是 omni 让它去的那一档。`（引擎名插值，不是字面量）。

**不给引擎档做下拉。** 两个理由：(1) 得维护「这家有哪几档」的清单 —— ACP 报 `availableModes`、claude 只报当前值不报可选清单、codex 是固定枚举，三种形状一个控件画不出来；(2) 更要命的是选完之后 omni 的 `Trust` 不知道该跟到哪一档（`pickMode` 多对一，反过来一对多），**等于把不一致从展示搬进了操作**。

### 7.6 窄屏与 apps/web

- **web 单栏全屏，不做并排。** `thread__head` 上加一枚计数徽标「旁路 3」，点开把 `body` 换成 lane 列表 → lane 详情 → 返回。这是**换屏**，和 Compare 在桌面端的做法同构。**不做抽屉** —— 抽屉在只有一只手的时候关不掉。
- **web 第一版只读**：`sideQuestion` 在 web 上一律不给入口。理由不是技术做不到，是**别在最薄的那一端加最新的功能**；而且 `thread.sideQuestion` 进了 `RUNS_IN_THREAD`，得先把「超过 `maxTrust` 整条拒掉时界面怎么说」想清楚。
- **A 在 web 上是纯白捡**：`engineState` 进了 `Thread`，`hintOf` 那行后面接一句即可。
- **桌面窄屏**（`@media (max-width: 1100px)`）：侧栏从第三列变成从右侧滑入的覆盖层，**改 CSS 不改组件结构** —— 换屏要改 JS，那意味着窄屏和宽屏两套渲染路径，两套都得测。
- ⚠️ `scripts/check-css.mjs` 对 web 的 styles 目录是 `apps/web/src` 且 **非递归 `readdirSync`** —— web 的 lane 样式必须放在 `apps/web/src` 根下的 `.css` 里，放进子目录当场红。

## 8. claude 的 workflow：侧栏能不能解决

**能。而且不需要新通道 —— 信号全在 omni 已经订阅的那条 `for await (const msg of handle)` 流里，`claude/loop.ts:151` 的 `default: return` 把它们全丢了。** 但可信度分两档，必须分开写。

### 8.1 拿得到什么（按证据强度分档）

| 消息 | 证据强度 | 映到哪 |
| --- | --- | --- |

`skip_transcript` 的文档注释是 SDK 官方给宿主的建议（*"…it may still appear in a tasks panel"*）—— **侧栏不是 omni 自己发明的分类，是照着引擎给宿主的建议做的**。这条对抽象的正当性很重要。

### 8.2 三档阶梯，降级自动发生

```
有 workflow_progress           → 完整树：阶段 + 每个 agent 的状态/模型/token/最近一步 + 预算
只有 task_started/updated/notification → 一条 lane 一个节点：描述、状态、跑了多久、用了多少 token
两者都没有（老 SDK）           → capabilities 不报 workflow，侧栏图标对这家不出现
```

**降级不需要用户知道，也不需要驱动做版本判断** —— `workflow_progress` 字段在就画树，不在就画单节点。这是**结构性探测**，不是版本嗅探。

### 8.3 上限（三条，都要如实说）

1. **`workflow_progress` 是 bundle-only、无兼容承诺。** → §9 把「跑一次真实 workflow 抓帧」写成**批 4 的准入条件**（一条 `*.live.test.ts`，omni 已有这个约定）。抓不到帧就把 claude 降级成「单节点 lane」发布，**别把树画进第一版**。
2. **子 agent 的正文对话默认拿不到。** 要整条嵌套对话得开 `Options.forwardSubagentText`，而 `Options` 只能在 `query()` 时给、运行期改不了（和 `effort` 同一个毛病），且打开后主消息流的量显著变大 —— `engine/README.md` 已写明「事件流不做背压」。
   → **默认不开**，设置里给一个「下次开会话生效」的偏好（和现有 `effort` 的处理一致）。没开时点进子 agent 显示一行「这条会话开场时没有打开子 agent 正文转发，看不到逐句对话」。**不假装能看。**
3. **`parent_tool_use_id` 在入站方向没有实测证实**（`loop.ts` 的 `RawMessage` 窄声明里没有它，但 `claude/driver.ts:145` 出站构造时显式写了 `parent_tool_use_id: null`，说明字段存在）。→ **第一版不靠它分流**，靠 `task_id`（public type）。

### 8.4 跨引擎对照（这是抽象不是硬凑的最后一条证据）

grok 的 `WorkflowUpdated` 同构（phases + agents + budget + revision），codex 的 `agent_path` 是真树路径，zcode 半张，kimi 没有。**三家三套私有结构落到同一个 `LaneNode{id,parent,label,state,detail}` 上，而界面一行 if 都不写引擎名。** 如果这套抽象是为 claude 量身定的，grok 和 codex 的数据不会这么顺地填进去。

## 10. 风险与已知限制

按包 README 的口径写。这些不是「以后会修」，是「知道它有，且知道为什么先不修」。

**关于 A**

1. **`Trust` 和引擎档位是两套语义，omni 永远不会把引擎报的档写进 `Trust`。** 后果可见：引擎在 yolo 而 omni 在 `read-only` 时 omni 这层仍然会拦 —— 用户会觉得「我明明开了全自动怎么还在问我」。界面必须把「两层」说清楚，否则这个**正确**的行为会被当成 bug 报上来。
2. **用户举的 kimi `/yolo` 场景，本方案不解决，因为它在 omni 里发生不了**（§2.2）。A 覆盖的是「模型自己进/退计划模式」和「omni 设档后的回声不一致」两类。
3. **claude 的 `adopt` 仍然猜不到「当初是哪一档」**（§4.1c）。`session.ts` 那句注释继续成立。
4. **kimi 的 `modeReadback` 永远是 false**，不是「还没做」。代价：接回老会话时 kimi 的引擎档一片空白。收益：不报一个确定是错的值。
5. **grok 的档位只覆盖一半**：审批档没有任何入站信号，`axes` 里缺席 `approval` 这一维，而界面上不会有东西提示「另一半没覆盖到」。**这是本方案已知的一个诚实性缺口**，接受理由是：编一个值比缺席更糟。
6. **`match` 只有两档且只覆盖驱动答得起的问题。** `unmapped` 之后引擎再改档，omni 只能说「它现在在 X 档」，**说不出「X 相当于 omni 的哪一档」** —— 那时界面显示引擎给的原文，不翻译。这是打分匹配不可逆的直接后果，不是实现懒。

**关于 B**

7. **codex 的侧问可以动手**（§4.1a）。omni 用自己的审批层按 `read-only` 钳住这一轮，但那是 omni 的一层，不是 codex 的。侧问入口上要写明「这条侧问在 <cwd> 里可以读，写会被 omni 拦下」。
8. **codex 侧问的边界提示词由 omni 携带**（准入条件 b 不满足，明确接受）。原样照抄、留注释指向 `side.rs`，并在 §11 加一条升级时 diff 的检查。**它会过期**，而它是「模型别把继承历史当活指令」的唯一屏障 —— 一个过期的屏障配上界面还在说「不打断主线」，比没有屏障更糟。
9. **侧问的 token 是双份**（fork 继承全部历史，`ephemeral:true` 只是不落盘，**不省 token**）。这个成本没有量化过。
10. **claude 的 `askSideQuestion` 是未公开 API**（运行时有、公开 `Query` 类型没有、CHANGELOG 没提过）—— 无兼容承诺。运行时探测，失败降级不崩。
11. **侧问的上下文在引擎那边不留**（claude 的 `skipTranscript`、codex 的 `ephemeral`）。omni 自己落盘所以看得见，但**接回会话之后引擎那边已经没有那段上下文了**。第一版单轮正好回避这个问题；日后加追问时，resume 之后的旧侧问 lane 必须标只读。
12. **kimi / zcode / grok(1.0.5) 上没有侧问，且 omni 不兜底**（三条代价见 §6.5 档 3）。

**关于 C**

13. **`workflow_progress` 是 bundle-only**，omni 自己声明最小结构性类型。SDK 补上或改名时 omni **静默降级**到单节点 lane —— 不会崩，但树会消失。
14. **claude 的 subagent 正文第一版不转发**：侧栏里有进度树，没有嵌套对话。
15. **zcode 的后台子 agent 正文无法分流**（backend 自动起 `inputVisibility:"model-only"` 的新轮次，桥原样转发成 `agent_message_chunk`）。**omni 单方面解不了**，只能等 zcode 桥升级。所以 zcode 的侧栏是半张。
16. **kimi 的侧栏永远是空的**，开关不出现。
17. **grok 的 workflow 能力是 gated 的**，omni 这条连接上能不能触发未确认（§11）。若不能，grok 的侧栏只剩 `Subagent*` 三条，抽象通用性的论证改用 claude + codex 撑。

**关于工程**

18. **`LaneProgress` 的落盘体积。** 它和 `item.updated` 同等待遇（落盘、全量替换），**节流的责任在驱动，不是优化项**：claude 自己就按毫秒窗口节流纯 `progress` 批次、状态跃迁才立即发；grok 带单调 `revision` 可去重。驱动不节流，一条跑十分钟的 workflow 能把 journal 撑成主要体积。
19. **远程全量重建的字节预算。** `scope.ts` 开头记着一次真事故：判据用条数不用字节，5.2MB 切成 271 片，手机收不完 → 没游标 → 重连从头 → 死循环，真机复现「连上 5 次、一条会话都没显示」。预算是 `REMOTE_REPLAY_CHARS = 192K` / 单会话 `REMOTE_THREAD_CHARS = 64K`。→ **远程全量里 lane 的 item 按 lane 截断（每条只带最后 N 条），`Lane.summary` 优先于 items。这一条必须在批 3 就做，不能等出事再补。**
20. **codex 开 `experimentalApi` 是一次协议版本升级，不是一个开关** —— 它是总开关，开了之后所有实验方法/字段/通知一次性全开。缓解是 `notify.ts` 现有的形状（认不出就忽略），但那只挡崩溃、挡不住语义漂移。嫌吵时可用 `opt_out_notification_methods` 按方法名做减法（76 种通知的黑名单维护）。
21. **侧栏与主区同时流式输出时的滚动竞争没有验证。** `Transcript` 的贴底逻辑按单个滚动容器写，Compare 并排用过两份**但那两份都不流式**。
22. **`LaneId` 是裸 `string`，不是品牌类型。** `ids.ts:3-5` 现在全是 `export type ThreadId = string` 之类的裸别名，零类型隔离。本方案的 `Lane.id` 沿用同款，**不提供误传保护**。要改成品牌类型是波及全库构造点的单独一批，不混进 lane。
23. **七道闸门里最容易在最后一刻红的两道**：`check:css`（组件里每个静态 className 必须在**同一端**样式表里出现过，模板字符串拼出来的那半不算；web 的 styles 目录非递归）和 `check:tokens`（`var(--aside-w)` 必须有定义，两端各算各的集合）。
24. **`AGENTS.md` 的依赖图已经过时**（图里没有 store 和 wire）。真正强制的是 `check-arch.mjs` 的 LAYER 表。对本方案的约束：**「怎么识别侧问 / 怎么认出子 agent」只能在 `engine`(L2) 里做，`store`(L1) 只能吃已经打好标记的 `Item` 和 `Lane`；`lane.ts` 放 `protocol`(L0)，零依赖纯类型。**

## 12. 被否决的做法及原因

写下来是为了防止以后有人重新提。

1. **把引擎自报的档写进 `Thread.trust`。** `Trust` 同时是 `@omni/approval` `decide()` 的输入（`acp/permission.ts:113`）。引擎报 yolo → 写成 `full` → **omni 自己那层审批也关了**，而那是用户从没点过的一次放权，且没有任何地方报错。**这是一个静默提权口。**
2. **驱动把引擎 mode 反向猜成 omni 的 `Trust`（`trustHint`）。** (a) 有损：`pickMode` 是多对一打分（`mode.ts:76` THRESHOLD=4），反过来一对多；(b) 一个需要靠注释拦着「只准生成提示、不准参与判定」的字段，是为抽象而抽象；(c) 上一版真的猜错了方向 —— 把 claude 的 `dontAsk`（预先**拒绝**）映射成了 `full`（最松），会把最严的一档在界面上说成最松的一档。**改用「驱动比对自己发过什么」得到 `match`，不需要猜。**
3. **把引擎的档位做成一个可选的下拉。** 三家三种形状（ACP 报 `availableModes`、claude 只报当前值不报清单、codex 是固定枚举），一个控件画不出来；更要命的是选完之后 omni 的 `Trust` 不知道该跟到哪一档 —— **等于把不一致从展示搬进了操作**。
4. **把引擎的档建模成单个 mode id。** 装不下 codex（approval + sandbox 两个旋钮）也装不下 grok（mode 轴 + 没有入站信号的审批轴）。压成一维就得由驱动现编一个合成 id —— 界面会显示一个引擎从没说过的东西。
5. **每个 workflow phase / agent 各是一条 `Lane`。** 一个 30 agent 的 workflow 每 tick 产生 30 条落盘事件；ViewState 数组每条都要整表重建，memo 直接失效；还得多一个「本身没有内容」的 `group` kind —— 那正是它声称要消灭的 default 分支换了个地方。**改成一条 lane 内嵌扁平节点表。**
6. **给侧栏发明第二套 `ItemKind`。** `protocol/README.md` 写着新增一种要动两端所有渲染分支，是有意的摩擦；而旁路里的内容和主线里的本来就是同一种东西（侧问的回答就是 `agent_message`）。加可选字段 web 不崩，加 ItemKind 当场 typecheck 红。
7. **把 lane 归属塞进 `Item.meta`。** `meta` 的契约是「读之前自己判类型」，而 lane 是渲染层每一帧的主分流轴。把主干逻辑放进一个自称要现场判类型的抽屉里，就是每个消费点各写一次 type guard 且零编译期保护。
8. **用 `Turn.meta` 标记侧问轮次。** `state.turns` 一个会话只留一条，`turn.completed` 一到就整条摘掉 —— 跑完之后界面上查不到。
9. **在 `reduce` 里就把 items 拆成主线/旁路两张表。** `owner` 表的语义要跟着变（`item.delta` / `item.updated` 只带 itemId），而回放老记录时那批 item 没有 `lane`。选择器分流是纯函数、可测、老记录天然落主线。
10. **用 `session/fork` 给 kimi 仿一个侧问。** 会话级分叉：新 sessionId、**落进引擎自己的会话列表**（用户点一次侧问，kimi 的列表里多一条他没建过的会话）、工具不禁用、双份 token。`NO_CAPABILITIES` 的原意就是「默认不给入口，而不是默认给」。
11. **把侧问退化成「普通 prompt + 一句『这是个侧问』的前缀」。** 那句话真的进主线历史、真的占上下文、真的影响后续轮次，而界面把它画在侧栏里 —— **看起来隔离了，其实没有**。
12. **靠命令名嗅探判断能不能侧问**（`commands.some(c => c.name === "btw")`）。四家里三家是假阴性：grok 的在 TUI 自己的表里，kimi 走 ACP 直接判 Unknown，claude 的是 `local-jsx` 会被非交互过滤器滤掉。
13. **靠 `detail.kind === "other" && detail.name === "Task"` 读 claude 的编排数据。** 数据确实原封不动躺在那儿，但那是 `capability.ts:7-10` 骂过的坑，而且更脆 —— claude 改个工具名，侧栏默默变空。
14. **用户点一次按钮来做能力探测**（拿 `-32601` 再收掉按钮）。把探测成本转嫁给用户，正是 `reduce.ts:180` 注释里「点了没反应」那个招牌病。**探测放在握手阶段。**
15. **版本嗅探**（`if (version >= "1.0.6")`）。grok 1.0.5 的二进制里 `x.ai/btw` 0 命中而同期仓库 HEAD 里有 —— 现成的翻车例子。
16. **把 codex 的 fork 侧问提到 `acp/` 或 `host/` 当通用兜底。** 提上去它就从「codex 的驱动实现」变成「omni 的编排逻辑」，host 里会长出一段起子会话/注提示词/等结果的代码 —— `AGENTS.md` 点名的那个坑。
17. **第一版就支持在旧侧问上追问。** 那需要 fork 常驻 + `laneId → 子 threadId` 账本 + 后台清理（codex 自己为这块修过两次 bug）+ omni 保管问答链。这三块正是让「侧问」看起来像编排的那部分,而用户诉求只是「不打断主线问一句」—— 单轮就满足。
18. **`Esc` 关侧栏。** Esc 归覆盖层（Settings / Review）；抢过来会让「关设置」变成「关侧栏」。
19. **Compare 视图里并排显示侧栏。** 258 + 1fr + 1fr + 340 在 13 寸上每份不到 300px；而且「这条侧问属于左边还是右边」没有不含糊的答案。
20. **窄屏用换屏而不是改 CSS。** 换屏意味着窄屏和宽屏两套渲染路径，两套都得测。
21. **先救活 `engine.status` 的 `LOUD` 过滤再删。** `mode.ts` 那两句 `ctx.status("ready",…)` 直接改走 `onTrustApply`；救活一条本来就不落盘、不补发的路，只会多一次「刷新就没了」的投诉。
