# 引擎能力适配层 · 方案

> **后续状态（2026-08-20）：** 本文关于 `kimi acp` 的探测仍是当时那扇协议门的历史证据，
> 不再代表内置 Kimi。内置链路现已改为 Kimi 公开的 `kimi web` REST + WebSocket；
> steer、侧问、运行期档位读回与压缩都从这扇原生门接入。ACP 结论只适用于废弃兼容链路。
>
> **后续状态（2026-08-25）：** 本文把分支型历史回退列为“不做 boolean”的结论已被实现证据

## 一句话结论

把 `EngineCapabilities` 的每一位从「有 / 无」升成「有 / 五种不同的没有」，配一张统一的界面判定表把那句话讲到用户眼前——机制不换（新增一位时编译器仍然逼五家驱动逐位表态），换的是**一个 `false` 现在必须说出自己是哪一种 `false`**。位从四个加到七个，其余二十来项调研出来的能力明确不做并写下理由。

## 1. 病灶：四种事实共用一个像素

用户的原话是「在 omni 里用 kimi 时能选模型，但选不了思考强度……这个对于用户来说是黑盒，其他家的估计也有这个问题」。

顺着这句话查下去，病灶是 `apps/desktop/src/renderer/components/ModelPicker.tsx:37` 那一行：

```ts
const efforts = current.efforts ?? []
if (efforts.length === 0) return [modelSection]   // 「推理强度」那一节静默不出现
```

`efforts` 为空有四种成因，用户的下一步动作各不相同：

| | 事实 | 用户该做什么 |
| --- | --- | --- |
| (a) | 这家引擎确实没有推理强度这个概念 | 换引擎，或接受 |
| (b) | 引擎有，omni 没读那个字段 | **来报一句 bug** |
| (c) | 有，但当前这个模型不支持 | 换个模型 |
| (d) | 有、omni 也接了，但这条会话此刻拿不到 | 重开会话，或先换一次模型 |

四种事实，**同一片空白**。这就是「黑盒」的确切定义：不是没有信息，是四种信息被渲染成了同一个东西，于是用户既做不了正确的下一步，也不会来报 bug——他看到的和「本来就没有」不可区分。

### 1.1 「消失」是 omni 现在的默认降级方式

八域普查把同一个病灶数出了一整排，全部在同一次改动里可以核对：

| 位置 | 缺席时发生什么 |
| --- | --- |
| `ModelPicker.tsx:153` `if (current === undefined) return null` | **整颗模型下拉从输入区消失** |
| `ModelPicker.tsx:37` | 「推理强度」那一节静默不出现 |
| `ModelPicker.tsx:68` `return undefined` | 「恢复默认设置」整行不出现 |
| `ContextMeter.tsx:13` `return null` | 上下文比例条整个不出现 |
| `Composer.tsx:180` + `useAttachments.ts:38/54` | 粘贴 / 拖放 / 附件条**三处一起哑掉**，拖一张图进去连一个字都没有 |
| `apps/desktop/src/renderer/usage.ts:51` | 「引擎未提供窗口大小」这句解释**只写进 `title`**——悬停才看得见等于没有 |

模型下拉那一格尤其说明问题：**五家引擎全部原生支持切模型**，所以 `models` 为空**永远不可能是 (a)**，只可能是 (b)(d)。而它渲染出的东西和「这家不支持切模型」一模一样——**omni 把自己的欠账渲染成了引擎的固有属性**。用户看不出该向谁报 bug，于是他不报，于是我们收不到反馈。

### 1.2 一半的 `false` 其实是 omni 的欠账，而它们伪装成引擎的属性

`packages/engine/src/acp/setup.ts:285-289` 对**所有** ACP 引擎一刀切：

```ts
compact: false,   // 理由是「实测 kimi：session/compact → Method not found」
steer:   false,   // 理由是「ACP 没有往正在跑的那一轮里插一句的入口」
```

两条结论对 kimi 成立，被推广到了整个协议。而本轮实测：grok 有 `_x.ai/compact_conversation`（回 `{}` 并随后推 `auto_compact_completed`）与 `_x.ai/interject`（回 `-32602 missing field 'text'`，即方法存在）；zcode 有 `session/compact`（成功）。同一个 `false`，一半是事实一半是欠账，而界面分不出来。

同类的过时断言，本轮抓到四条，全部是「写成 `false` 之后就再没人质疑过」：

| 位置 | 断言 | 实测 |
| --- | --- | --- |
| `claude/driver.ts:150-155` | 「SDK 的 effort 是 Options 字段，运行期没有 setter」 | `applyFlagSettings({effortLevel})` 运行期真生效（`applied.effort` 走 xhigh→low→max） |
| `claude/driver.ts:235` | 「SDK 没有复制会话的入口」 | `Options.forkSession:true` + `resume` 实测分出新会话，历史全带 |
| `claude/loop.ts:31-33` | 「窗口大小 SDK 不给」 | 每条 result 的 `modelUsage[model].contextWindow` 就给（opus[1m] = 1000000） |
| `codex/driver.ts:419-433` | 「OS 沙箱在 thread/start 时定死，要新开会话」 | `turn/start.sandboxPolicy` 在生成的官方 TS 里非实验，中途可改 |

**一个 boolean 不会过期，它只会一直错着。** 这是本方案要求「非 true 必须说出理由」的直接动机——写理由的那一刻，过时的断言会当场暴露。

### 1.3 已经写好的正确的话，走了一条被过滤掉的通道

驱动里其实早就写好了大量精确、可行动的「为什么这家没有」：

```
acp/grok.ts:72-76    「Grok 在这一档下自动放行一切工具调用……要真正限制它请用只读档」
acp/mode.ts:120      「kimi 没有报告可选档位，omni 的信任档只在本机判定层生效」
acp/setup.ts:216-222  sayWhy()：「这家适配器没实现这件事。要改就去它自己的界面或配置里改」
```

它们全部走 `ctx.status("ready", note)`，而 `packages/store/src/reduce.ts:156` 的 `LOUD` 集合只收 crashed/timeout/degraded 三档，`apps/desktop/src/main/host.ts:113` 的日志也只记 `status !== "ready"`——**两处同向过滤，这些话在界面和日志里同时蒸发**。

即便是过得去的那三档（degraded），承载方式也是错的：`Notices.tsx` 只画最新一条；横幅是**时刻**不是**状态**，历史全量也会在宿主侧过滤瞬时事件。而「这家不支持 X」描述的是一个**一直成立的事实**——用一次性横幅承载它是类型错配。

### 1.4 还有一处已经在撒谎的硬编码

`apps/desktop/src/renderer/components/Transcript.tsx:41-46` 的空态里写着：

> 「（Claude 的历史能搬，codex 目前不行——它还没开放读取历史内容的接口。）」

三重问题：它违反 `capability.ts` 开篇那条硬规则（界面不能看引擎叫什么名字）、五家里只提两家、**而且对 codex 已经过期**——`thread/resume` 的响应里 `thread.turns[].items` 就是历史正文。

## 2. kimi 思考强度：确切诊断与修法

### 2.0 更正 · 2026-08-19：**kimi 的标准是官方维护的那个，本节此前的诊断作废**

「kimi」在 2026 年有两套实现，但**只有一套是标准**：官方仓库 `MoonshotAI/kimi-code`
（TypeScript / MIT，当天仍在推提交），npm 包 `@moonshot-ai/kimi-code`。
另一套 `MoonshotAI/kimi-cli`（Python）已由官方公告
**「evolving into Kimi Code CLI … will be gradually wound down」**，**按非标处理**。

用户此前看到的「能选模型、选不了思考强度」来自那套非标实现（host-b 上装的是它）。
**该现象不进能力表**——把一个已停止维护的实现的形状写进 protocol，就是替厂商维护它的过去。
host-b 已于 2026-08-19 换成标准实现（`@moonshot-ai/kimi-code` 0.37.2）。

**标准实现上，omni 的形状本来就是对的**，逐条对得上（源码 `MoonshotAI/kimi-code` @ `2ea2ef62`）：

| 能力 | kimi 怎么报 | omni 怎么接 |
| --- | --- | --- |
| 思考强度 | `configOptions[id='thinking', category='thought_level']`，`session/new` 与 `session/load` 都报 | `setup.ts:256` 的 `effortsOf` 认的正是这两个判据 |
| 档位 | 四档，在 `configOptions[id='mode']`（`modes` 字段已移除） | `modesOf`（`setup.ts:169-176`）本来就有这条回落分支 |
| 续跑 | `session/load` **回目录**（model + thinking + mode） | **`76962de` 接住这个回包**——不接就丢整份目录 |
| 附件 / 分叉 | `promptCapabilities.image=true`；`sessionCapabilities` 含 `fork`/`close`/`delete` | 通用推导直接产出 `true` |

最后一行值得单独说：`76962de` 不是给非标实现打的补丁，**它是标准实现的必需件**。

**留一条观察，不加位**：强度在 codex 上也折进 modelId（`gpt-5.6-sol[low]`），
「把一个维度折进另一个维度」是这批引擎里反复出现的形状。曾考虑为它加第六种 why `folded`，
**本轮不加**——codex 另有 `turn/start.effort` 那条真轴、报 `true`，而非标实现不进表，
于是这一档**没有任何现存使用者**，按 §6.1 的收位判据不该收。哪天真出现一家只折不给轴的，再回来看这条。

### 2.1 先排除三个假设（**以下为标准实现 `@moonshot-ai/kimi-code` 的实测**）

**假设 (c)「kimi 把思考编进模型名」证伪。** 用户截图里的 `k3-256k (thinking)` 是 kimi 自家 TUI 按模型 capabilities 加的**能力徽章**，不是档位。实测本机 kimi 0.36.1 的模型清单是干净的 `kimi-code/k3` / `kimi-code/k3-256k`，无任何后缀。

但要记一笔：`/opt/homebrew/lib/node_modules/@moonshot-ai/kimi-code/dist/main.mjs` 里 `buildModelOption` 的注释白纸黑字写着——Phase 15 **之前**它确实把档编进 modelId（`k2,thinking` 双行），Python 参考实现至今还这么干，`setModel` 还在兼容拆这个后缀。**同一家引擎在版本之间换过形状**，这就是能力表必须带版本戳的理由。

**假设 (a)「kimi 真没有」证伪。** 实测 `session/new` 回包里有：

```json
{ "id": "thinking", "category": "thought_level", "type": "select",
  "currentValue": "high",
  "options": [{"value":"low"},{"value":"high"},{"value":"max"}] }
```

**假设 (b)「omni 的匹配条件对不上」证伪。** `packages/engine/src/acp/setup.ts:256-268` 的 `effortsOf` 认 `category === "thought_level"`，正好命中。把真回包喂给编译产物 `packages/engine/dist/acp/setup.js` 跑了一遍，输出是 `effortConfig="thinking"`、`efforts=[low,high,max]`、`effort="high"`，一字不差。

顺带排掉一个竞争假设：本机 `kimi-for-coding` / `-highspeed` 两个模型在 config 里确实没有 `support_efforts`，但按 kimi 的 `buildThinkingOption`，那时 `configOptions` 里仍会出现一个 1~2 项的 thinking 选择器（退化成 `off`/`on`），**不会整项消失**。这条路解释不了「选不了」。

### 2.2 已确证的机制：(d)，续跑那条路把回包丢了

`packages/engine/src/acp/open.ts` 续跑分支（约 :160-170）：

```ts
await ctx.rpc.call("session/load", { sessionId: ctx.req.resume, ...shared })   // 返回值扔掉
ctx.state.acpSession = ctx.req.resume
```

而同一个文件里，新建（:171）和分叉（:188）两条路都调了 `adopt()`。实测 kimi 的 `session/load` 回包**和 `session/new` 一模一样**：`configOptions` 三项（model / thinking / mode，都带 `currentValue`）加 `modes`。kimi 自己仓库的 `test/session-load.test.ts:299` 也断言了 `thought_level` 在 load 回包里。

后果链条完整可追：

```
回包丢掉
  → state.effortConfig = undefined、modelConfig = undefined、modes = []、windowOf = {}
  → model.ts:68-80 的 applyEffort 撞上 configId === undefined 直接 return
     ——不发 RPC、不报错、不发 degraded
  → 而 modelConfig 也丢了，换模型退回发规范的 session/set_model
     ——kimi 恰好实现了这条
  → 「能选模型、选不了强度」
```

**界面之所以看起来还正常，是因为 store 回放了 journal 里旧的 `models.updated`（那是落盘的）——界面靠磁盘上的旧快照撑着，而驱动手里什么都没有。**

同根坏掉的还有两处：续跑会话的信任档映射（`modes = []` 使 `pickMode` 返回 undefined）、续跑会话的上下文分母（`windowOf = {}`）。一个根。

grok 与 zcode 也全中：实测 grok 的 `session/load` 与 `session/resume` 都回 `{models, _meta}`（模型目录、每模型 `reasoningEfforts`、`totalContextTokens` 全在）；zcode 的 `session/load` 回 `{modes, configOptions, replayMeta}`、`session/resume` 回 `{modes, configOptions}`。

### 2.3 但因果没有实物证据——如实说

**机制三段全部坐实，「它是用户那句话的成因」这一步没有验证。** 具体缺口：

- 没有在 GUI 里复现用户那一次点击。
- 查了真机 journal（`~/Library/Application Support/omni/threads`），唯一那条 kimi 会话的 `models.updated` **带着 `efforts:[low,high,max]`**（说明当时强度选择器是在的），且它是切引擎新开的、`engineHandle` 一次成型，**没有走过 resume**。

所以本节的结论应当被读成「已确证的机制 + 待验证的因果」，而不是「病根」。验证方式见 §13 第 1 条——一分钟的事。

### 2.4 修法：一行，排在能力层之前

```ts
const loaded = (await ctx.rpc.call("session/load", { sessionId: ctx.req.resume, ...shared })) as AcpNewSession
// load 的回包不带 sessionId——句柄仍用请求里那个
adopt(ctx, { ...loaded, sessionId: ctx.req.resume })
```

`adopt()` 已经把 `catalogOf` / `modesOf` / `currentModeOf` / `contextWindows` 一次算齐（`open.ts:206-218`），不需要另写一份——`adoptCatalog` 上面那段注释「写两遍的下场是其中一遍漏掉一样」正是为这类事写的。

**这一步必须排在能力层之前。** 不修它，续跑会话里驱动手上根本没有能力信息，画出来的三态五态全是编的：驱动会诚实地报 `unknown`，而用户在那条会话上看到的是一片「不知道」。

### 2.5 修完之后，能力位补上第二道保险

加上 `effort` 位之后，「界面上能点、点了驱动内部悄悄 return」这个状态在**类型上不再可表达**：要么位是 `true`（那驱动就有义务发得出 RPC，发不出要发 degraded），要么位是 `Absent`（那界面上只有一句话，没有可点的东西）。中间地带被消灭了。

**顺带纠正一句要点名的话：能力层对用户报的那个具体现象一个像素都没改善。** 它解决的是 (b) 那一类——grok 的强度（在 `models[]._meta` 里，`effortsOf` 不去那儿找）、claude 的强度（`applyFlagSettings` 没接）、以及 ACP 三家被一刀切的 compact/steer。把功劳记对，落地顺序才排得对。

## 3. 八域能力矩阵

取值只有四种：`原生`（引擎有明确接口 / 字段）、`可推导`（omni 能从别处算出来，代价是一家一份）、`无`（查过了确实没有）、`未知`（问不出来 / 没验）。**每格带证据；无证据只能填「未知」。**

证据缩写：`sdk.d.ts:N` = @anthropic-ai/claude-agent-sdk 0.3.231；`v2/*.rs` = codex 仓库 app-server-protocol；`scratchpad/*.json` = 本轮真机探针回包原文；「实测」= 本轮真的发过那条 RPC 并看到了回包。

### 4.1 形状：`Support = true | Absent`

```ts
/** 能力键的唯一真源。加一位就改这里，别处全部跟着编译报错。 */
export const CAP_KEYS = [
  "compact", "attachments", "steer", "fork",   // 既有四位，语义一字不改
  "effort", "trust", "transcript",             // 本次新增
] as const
export type CapKey = (typeof CAP_KEYS)[number]

/** 一位能力的取值：支持就是 `true`；不支持必须说明为什么。 */
export type Support = true | Absent

export type AbsentKind =
  | "engine"     // 查过了，这家确实没有
  | "unwired"    // 引擎有，omni 还没接
  | "by-design"  // 引擎有，omni 有意不给这个入口
  | "model"      // 有，但当前模型 / 这条会话上没有
  | "unknown"    // 问不出来

export type Absent =
  | { why: Exclude<AbsentKind, "engine">; note?: string }
  /** engine 是最强的一句话——说出去要负责，所以必须交证据。 */
  | { why: "engine"; note?: string; checked: string }

export type CapabilitySet = { readonly [K in CapKey]: Support }
```

**为什么删掉 `false`。** `false` 是一个不携带任何信息的值，而它现在正是四种事实的公共出口。类型上把它删掉，驱动作者就没有「随手填个 false」这条路可走了。

**为什么是 `true | Absent` 而不是 `{ ok: boolean; why?: string }`。** 现有三个消费点今天已经全部写成 `=== true` / `!== true`：`host/prompt.ts:43`、`host/branch.ts:147`、`Workspace.tsx:121`。换成 `true | Absent` 之后这三处**一个字符都不用改**，语义还正好收紧（对象不是 `true`）。换成 `{ok, why}` 则三处全要改，而改的过程中很容易把 `?.ok !== true` 写成 `?.ok === false`——那两者在能力集整个缺席时行为相反。

反过来，那些**只判真值、不看原因**的地方会红（`Workspace.tsx:234-235`、`useOmniActions.ts:39`）。**这个红是设计的一部分**：它把「这里只判了有没有，没管为什么」逐个揪出来。一次类型变更 = 一次编译期的全仓普查。

### 4.2 怎么保住「新增一位时编译器逼所有驱动表态」

这是本方案的生死线，也是 `capability.ts` 现有设计唯一真正值钱的性质。**答案是 `CapabilitySet` 必须是封闭键集上的映射类型，绝不能是数组、Partial 或 `Record<string, _>`。**

用仓库自带 tsc（`--strict --module nodenext`）实跑过六个反例，全部按预期报错：

| 错法 | 编译器 |
| --- | --- |
| 少写一位（漏 `transcript`） | `TS2741 Property 'transcript' is missing` |
| 写 `false` | `TS2322` |
| 写**派生 boolean**（`attachments: promptCaps?.image === true`） | `TS2322` |
| `{why:"engine"}` 缺 `checked` | `TS2322` |
| 多写一位（`plan`） | `TS2353 Object literal may only specify known properties` |
| 合法的五态字面量 | 零报错 |

三种会悄悄丢掉穷举性的写法，必须作为反面注释写在类型定义旁边——它们都能通过直觉 review（「不就是一份能力清单吗」），但丢了穷举性之后这个方案就只剩一堆容易过期的字符串：

```ts
type CapabilitySet = readonly { key: CapKey; cap: Capability }[]  // 错
type CapabilitySet = Partial<Record<CapKey, Support>>              // 错
type CapabilitySet = Record<string, Support>                        // 错
```

**比今天更严的两处**：(1) 派生 boolean 编译不过——ACP 那条 `attachments: agent?.promptCapabilities?.image === true` 的一刀切写法被类型堵死，作者必须写三元并为 false 分支指明是哪一种「没有」；(2) `engine` 档的 `checked` 是类型级必填。

`contract.ts:233` 的「`capabilities()` 是必选返回值、不做成可选方法」这条设计原样保留——那个「烦」是特性。

### 4.3 通道：新事件，能力不再挂在 `Thread` 上

```ts
| { type: "capabilities.updated"; at: number; threadId: ThreadId
    engine: EngineId; capabilities: CapabilitySet }
```

进 `packages/host/src/ctx.ts:132-149` 的 `LIVE_STATE` + `liveKey("caps:<threadId>")`（不落盘、按键留最后一条、全量重建时补发）。`ownerOf` 的默认分支落到 `directOwner`，而它是三项白名单（usage / engine.status / models），新事件**天然不进 journal**。

**为什么不继续挂在 `Thread` 上。** `host/session.ts:185` 的注释说「能力握手时问一次就够——它不随轮次变」，而这个前提已经被两处证伪：`acp/update.ts:248-260` 的 `config_option_update` 会改变强度词表；codex 的 `attachments` 随当前模型变（spark 的 `inputModalities` 是 `["text"]`）。既然会变，它就和 `models.updated` 是同一类东西。

更硬的一层：**`Thread` 是落盘的会话记录，而能力是活进程的事实**。挂上去意味着旧 journal 会重放一句带引证、带版本戳的断言（`checked: "kimi 0.36.1 …"`），而用户可能早升到 0.40。一个过期的布尔无害；一个过期的、带引证的、看起来很确定的句子，正是本文反复警告的「过期的说明比没有说明更危险」。

**为什么不走 `engine.status`。** 那条通道有三条性质，对「持续状态」全是错的：不落盘、也不进 `LIVE_STATE`、只在 LOUD 三档下成为一次性横幅。

**`engine` 字段不冗余**，理由与 `models.updated` 一字不差：一条会话中途会换引擎，切过去之后新那家的能力集是异步才到的；不带这一条的话，那段时间界面照着**上一家的能力**画控件。

### 4.4 向后兼容：不做 `sealCaps`，删字段本身就是兼容机制

候选方案里有一个 `sealCaps()`（驱动形状 → 线上 boolean 形状），动机是防止老客户端把 `Absent` 对象读成真值。**本方案不做它**，理由：

- 线上出现的是一个**全新事件名**，没有任何既有消费方读它；`packages/store/src/reduce.ts:269-274` 对分发表里没有的事件原样返回旧状态。
- 同时 `Thread.capabilities` 字段消失，老消费方读到 `undefined` → 退回今天的行为。
- 实测 `grep -rn "capabilities" apps/web/src` **零命中**——手机端根本不读能力位，那个「老手机长出点了没反应的按钮」的场景今天不存在。

也就是说：`sealCaps` 解决的是「保留字段」制造出来的对象真值陷阱；把字段删掉换成新事件，那个问题从源头消失，而不是被一个必须长期同步的转换函数缝住。

**但真值陷阱在仓库内部仍然存在**（`if (caps.effort)` 恒为真，实测编译零报错）。对策见 §4.5，并写进 `packages/protocol/README.md` 的已知限制。

### 4.5 渲染层的唯一问法：极性反过来

渲染层**不读** `caps.effort` 的真值，只调：

```ts
vocabOf(cap: Support | undefined, opts): Vocab | undefined
// 支持 → undefined（没话可说，正常渲染）
// 不支持 → 一个 Vocab（有话要说）
```

host 侧要布尔的两处用 `can(set, key)`。极性反过来之后，真值读法**自然是对的**——不可能再出现「不支持却渲染成支持」，因为渲染层拿到的是「要不要说话」，不是一个可能被误读的成员。

`vocabOf` 的签名只收 `subject: string`（引擎的显示名，来自 `EngineInfo.label`）、**拿不到 `EngineId`**——`capability.ts` 开篇那条硬规则（「不能看引擎叫什么名字」）禁的是 `if (engine === "kimi")` 这种分支，不是禁止把名字印进句子；把它在类型上守住，比写在注释里可靠。

### 4.6 per-engine 的真相住在哪里：注入，不是 if

三路评审共同点名的 fatal：**ACP 是一个驱动接三家以上引擎**，而 `capabilitiesOf(info: AcpInitialize)` 的唯一输入是握手结果，它推不出「这家真没有」还是「有但 omni 没接」。两个现成反例：

- grok 自报 `promptCapabilities.image === false`，实测它照收照读图片；
- grok 的 `sessionCapabilities` 无 `fork` 键，而 `_x.ai/session/fork` 存在。

照「由握手推导出 false 就写成 absent」的落法，这两格都会变成 `{why:"engine"}`——把 (b) 说成 (a)，只是换了一个更自信的壳。旧版的 `false` 至少是沉默的，新版会把它变成一句带理由的断言。

**硬纪律（写进类型注释，并由测试断言）：**

> 通用 ACP 推导只允许产出 `true` 或 `{why:"unknown"}`。
> `engine` / `unwired` / `by-design` 三档**只能由 per-engine 补充写死**。

per-engine 补充走已有的注入面（`AcpDriverConfig` 现在已有 `logPath` / `contextUsed` / `nativeApproval` 三个同形状的钩子，`registry.ts:52-63` 逐家注入）：

```ts
export interface AcpSupplement {
  caps?: (base: CapabilitySet, info: AcpInitialize) => CapabilitySet
  foreign?: (method: string, params: unknown) => ForeignSignal | undefined
  ext?: { fork?: (sid) => Call; compact?: (sid) => Call; interject?: (sid, text) => Call }
}
```

`ext` 的值是**构造器**而不是裸方法名——`_x.ai/session/fork` 要的是 `sourceSessionId`，光有名字不够。驱动只调 `config.ext?.fork?.(sid)`，仍然一个引擎名都不认识。

**同时必须补齐第三方引擎的注入面**：`apps/desktop/src/main/engines.ts:122-133` 的 `registerAcpEngines` 现在只传 `{id, command, args, env}`，从 `engines.json` 进来的引擎（zcode 就是）拿不到任何 per-engine 适配。不补这一步，写在能力表里的 `unwired` 对它们就是一张**永远兑不了的支票**——而那正是这一档会退化成新谎的路径。

### 4.7 位与值分工：能力表不复制值

- **`effort` 位**回答「这条会话**能不能在运行期改强度**」——引擎有没有这个接口是静态的。
- **`ModelOption.efforts`** 回答「当前模型有哪几档」——随模型变，跟着 `models.updated` 走，已有通道。

配一条渲染规则收口：**位是 `true` 但 `efforts` 为空时，那一节仍然留位**，措辞走 `model` 模板（「当前模型上没有推理强度，换个模型可用」）。这样 claude 的 haiku、grok-4.5 少一档 xhigh 这类情况也有话说，**而不需要任何新位**。

不把值搬进能力表的理由，仓库里有活样本：`setup.ts:38` 把 `currentValue` 当 `isDefault` 用，代价是 kimi/zcode 上「恢复默认设置」那一行**永远不显示**。同一件事有两处真源的下场已经吃过一次。

一条补充纪律：**位是 `true` 但 `efforts` 为空、且 route 是会话级**，是一个矛盾状态——按 `unknown` 渲染（用户看到诚实的「问不出来」），同时在诊断页把这一格标成「驱动契约违反」。不走 `console`：`eslint.config.js` 里 `no-console` 是 warn 级，`pnpm check` 未必会红，一个不会红的告警等于没有。

## 5. 五个 why 各是什么、为什么是五个不是三个

| why | 含义 | 谁能填 | 用户的下一步 |
| --- | --- | --- | --- |
| `engine` | 查过了，这家确实没有 | per-engine 补充，**必须交 `checked` 证据** | 换引擎；或去引擎自己的界面 |
| `unwired` | 引擎有，omni 还没接 | per-engine 补充 | **来报一句**（这正是现在收不到的反馈） |
| `by-design` | 引擎有，omni 有意不给这个入口 | 驱动 | 去用引擎自己那个入口 |
| `model` | 有，但当前模型 / 这条会话上没有 | 驱动（动态算） | 换模型 |
| `unknown` | 问不出来 | 通用推导的唯一 false 出口 | 试一下（**入口仍然可点**） |

**`unwired` 为什么必须独立成档。** 它是唯一能让 omni 的欠账被用户看见、进而收到反馈的机制。现在收不到关于强度的反馈，恰恰因为用户看到的空白和「本来就没有」不可区分——他不会为一个「引擎本来就没有」的东西来提意见。

**`by-design` 为什么必须存在。** claude 有两格是它：`compact`（自己的 `/compact` 已在斜杠命令列表里，omni 再给就是同一件事出现两次）、`trust`（`permissionMode` 有意钉死 default，因为只有走到 `ask` 的决定才经 `canUseTool`，换档等于绕过 omni 的判定器）。另外三档没一种说得对：`engine` 把用户导向「换引擎」（谎），`unwired` 把用户导向「报 bug」并往 CI 欠账清单里塞一条**永远不会修**的条目。

**`unknown` 为什么必须存在，且规则和另外四档不同（仍然可点）。** 仓库里已有现成先例——`EngineInfo.state`（`event.ts:49-56`）：

> unknown / 缺席 → 什么都不做。**猜不出来就别猜。**
> 灰掉一个其实能用的引擎，比不检查更糟：用户会相信自己没装，去装第二遍。

如果只有三态，`unknown` 只能被迫填成 false，也就是被迫拦住一个可能能用的入口——那正是 `EngineInfo.state` 当初论证过、并且明确否掉的做法。

## 6. 加哪几位：七位，不是二十位

### 6.1 收位判据（一位必须同时满足四条）

1. 它决定**一个界面入口给不给**（不是一个值、不是一段文案）
2. **五家里有分歧**（全有或全无的不需要位）
3. omni **已经有或即将有**这个入口
4. 它是引擎的**静态属性或按模型可算的属性**，不需要为它另开一条事件通道

### 6.2 既有四位：保留，不吸收，不改名

`compact` / `attachments` / `steer` / `fork` 的**语义一个字不改**，只有类型从 `boolean` 变成 `Support`。`capability.ts` 里那四段论证注释原样保留——塞进泛型表之后注释无处安放，六个月后没人记得 `compact` 问的到底是哪个问题。

迁移代价逐条：

| 改动点 | 代价 |
| --- | --- |
| `host/prompt.ts:43`、`host/branch.ts:147`、`Workspace.tsx:121` | **零**（已经写成 `=== true` / `!== true`） |
| `codex/driver.ts` 的 `{compact:true, attachments:true, steer:true, fork:true}` | **零字符**（`true` 是合法值），只需补新位 |
| `claude/driver.ts:230-236` | 三个 `false` 各要填一个 why——**而填的过程就是一次修正**（fork 那句注释当场暴露为过期） |
| `setup.ts:capabilitiesOf` | 四位扩到七位，约 +30 行 |
| `NO_CAPABILITIES` | 从全 `false` 改成全 `{why:"unknown"}`。**为什么是 unknown 不是 engine**：它是「驱动没表态」的兜底，omni 并不知道引擎有没有，填 engine 是撒谎 |

### 6.3 新增三位

**`effort`** —— 本次触发点。回答「这条会话能不能在运行期改推理强度」。五家取值：

| | 值 | 依据 |
| --- | --- | --- |
| kimi | `true` | 实测 `configOptions[id=thinking, category=thought_level]` |
| zcode | `true` | 实测 `configOptions[id=thought]`，且**本轮真的发过** `set_config_option{thought:"low"}` 并成功 |
| codex | `true`（+ note「下一轮生效」） | 实测 `turn/start.effort`；官方生成 TS 里非实验 |
| grok | `{why:"unwired", note:"Grok 把强度放在模型清单的扩展字段里（models[]._meta.reasoningEfforts），omni 还没读那儿"}` | 实测它根本没有 `configOptions` |
| claude | `{why:"unwired", note:"SDK 0.3.231 的 applyFlagSettings({effortLevel}) 能在运行期改，omni 还没接"}` | 实测 `applied.effort` 走 xhigh→low→max |

五家取值里恰好有三种不同的 why，是这套形状最好的验证样本。

**`trust`** —— 回答「omni 的三档信任落不落得到引擎上」。它示范了「同一套形状能覆盖不同形态」：**不让控件消失**（omni 自己的判定器照常工作），只改副标文案。

**`transcript`** —— 回答「接管来的会话能不能把引擎那边的正文搬进来」。加它的直接收益是**删掉 `Transcript.tsx:41-46` 那段硬编码引擎名的、且对 codex 已经过期的字面量**。这不是加功能，是修一处现存违规。

> 这一位与收位判据一（「不是一段文案」）有张力，本方案接受这个例外并写明理由：它删的是现存的硬规则违规，且 `unwired`（去报 bug）与 `engine`（去引擎自己的界面看）对用户是两个不同的下一步。若不接受这个例外，替代方案是把那段文案删成一句不点名的通用话，代价是失去 (a)/(b) 区分。

### 6.4 两条渲染规则，而不是两位能力

**模型清单为空。** 候选方案里有人提议加一位 `model`，本方案**否掉**：五家全部原生支持切模型，这一位恒为 `true`、不携带信息（违反判据二）。而一条渲染规则比恒 true 的位**更强**——它说得出「这里永远不是 (a)，只可能是引擎没报或 omni 没接」，一个恒 true 的布尔说不出这句话。

规则：`models` 为空且非 detached/starting 时，触发器**留在原位、禁用、label 就是那句短话**（「模型 · 引擎没报清单」）。删掉 `ModelPicker.tsx:153` 的 `return null`。label 不依赖当前值，所以清单为空时也有东西可写。

**续跑。** 有人提议加一位 `resume`，同样否掉：实测三家 ACP 的 initialize 都同时报 `loadSession:true` 且 `sessionCapabilities` 含 resume，claude 与 codex 也都支持，**五家里一个分歧实例都没有**。`open.ts:161` 那句「只认 loadSession，只报 resume 的引擎被判成不支持」是一处**驱动判据 bug**，改判据即可（`loadSession || sessionCapabilities.resume`），不需要一位能力。

## 7. 能力缺席时的界面语汇（本方案核心产出）

**形态由控件性质决定，措辞由 why 决定——两个正交维度。**

### 7.0 两条前置规则（压过一切）

1. **会话 `detached` 时，一切入口按「这是历史会话」处理，不显示任何能力归因。** 那时点不动的原因是没有活着的进程，不是引擎不支持；混在一起说会让用户以为换个引擎就好了。`ComposerBar.tsx:61/73` 三处控件的 `disabled` 今天已经只认 detached，规则与现状一致。
2. **能力集缺席（`capsOf` 返回 undefined）或 `thread.status === "starting"`** → 控件留位、禁用、一句「引擎还在起，还不知道它能做什么」。**绝不退回「都不支持」。**

### 7.1 形态：三条判据，顺序执行

| 判据 | 问题 | 走向 |
| --- | --- | --- |
| 一 | 缺的是**一个入口**，还是**入口里的一个选项**？ | 一个选项 → **静默少一条**，不解释 |
| 二 | 这个入口**当前有没有值可显示**？ | 有值 → **只读展示当前值 + 换标签文案** |
| 三 | 缺席时用户**会不会产生疑问**？ | 会 → **留位 + 禁用 + 一句可见的话**；不会 → **整格不存在**，只在诊断页记一行 |

**判据一**：轴还在，用户看得见轴本身。例：思考档里少一个 `off`（kimi 的 always_thinking 模型不给这一档）、斜杠命令少一枚来源角标。一个写着「来源未知」的灰角标会让每一行都长出一块噪声，而它换不来任何行动。**消失的如果是「一个选项」可以静默；消失的如果是「一个能力入口」绝不能静默。**

**判据二**：引擎报得出当前状态但 omni 改不了时，显示比不显示强得多。例：codex 的沙箱档、可写根目录。知道「它现在跑在 read-only 沙箱里」已经解决了九成困惑，哪怕那颗控件点不动。

**判据三**：这条判据比「这个能力重不重要」好用，因为它直接对应用户那句抱怨——**黑盒的定义就是「我有疑问而界面不回答」**。
- 会产生疑问：他在引擎自己的 TUI 里见过这个功能；或者他**刚做了一个动作**（拖一张图进来）而什么都没发生。
- 不会产生疑问：这个概念在这家根本不成立。例：codex 的 `shell_environment_policy` 在另外四家不是「不支持」，是**这一层压根不存在**——给它留位等于让用户去找一个不存在的功能。

### 7.2 措辞：五个模板（`{}` 是参数，不是分支）

| why | 句式 | 入口点不点得动 | 下一步 |
| --- | --- | --- | --- |
| `engine` | 「{引擎}不支持{这件事}」+ note + 依据（`checked`） | 禁用 | 换引擎；或去它自己的界面 |
| `unwired` | 「{引擎}支持{这件事}，omni 还没接上」 | 禁用 | 来报一句 |
| `by-design` | 「用 {引擎} 自己的{那个入口}就行，omni 不重复给一个」 | 禁用 | 用引擎自己的入口 |
| `model` | 「当前模型上没有{这件事}，换个模型可用」 | 禁用 | 换模型 |
| `unknown` | 「问不出 {引擎} 支不支持{这件事}」 | **仍然可点** | 试一下 |

### 7.3 那句话必须可见

短句渲染在**同一视觉块内、一行可见**；`note` 与 `checked` 收进可点开的详情或 title。

**绝不把那句话的唯一载体放进 tooltip。** 反面教材就在仓库里：`renderer/usage.ts:51` 把「引擎未提供窗口大小」只写进 `title`——悬停才看得见的解释等于没有解释，而 `apps/web` 连 hover 都没有。整份方案的产出就是让那句话到达用户；放进 tooltip 等于没到达。

### 7.4 逐格落地

| 位置 | 形态 | 具体表现 |
| --- | --- | --- |
| 强度那一节（`ModelPicker`） | disabled | **永远存在**。右边不是档位就是一句话：可选档位 / 「Kimi 支持，omni 还没接上」/「当前模型 Haiku 上没有，换个模型可用」/「问不出 ZCode 支不支持」 |

| 附件（`Composer`） | disabled + **动作要有回音** | 回形针留位灰掉 + 一行短句；`onDragOver` **照常 preventDefault**（让拖拽有落点），`onDrop`/`paste` 时不入列而是**就地弹一行同样的句子**，下次输入清掉 |

### 7.5 语气规则：读不回来就不许断言

这条治的是**比「控件不见了」更坏的一类**：界面对「我知道」和「我以为」用同一种排版，于是用户会确信一件错事（引擎降级路由之后 chip 纹丝不动）。

规则：**语气由运行期出处决定，不由静态位决定。**

- 值来自引擎回报（`thread/start` 响应、`config_option_update`、`model_changed`）→ chip 可以断言：「Grok 4.6 · 高」
- 值来自 omni 自己记的 → chip 说「Grok 4.6 · 高（你上次设的）」，详情里补「这家不报告引擎侧的变更」

**为什么不做成一个静态的 `notifies` 能力字段**（候选方案里有）：它填不出来。claude 的 0.3.231 里根本没有模型变更推送；codex 的 `thread/settings/updated` 带 `#[experimental]` 而 omni 传 `capabilities: null`——**这一位不是引擎的属性，是「omni 握手时报了什么」的函数**，用静态字段装它，第一天就会填错。

#### 8.4.1 一条 why 表的边界（由这一格逼出来，但对所有引擎成立）

kimi 的 `effort` 位是 **`true`**，而在 `76962de` 之前，续跑的会话上强度**确实设不出来**。
两者不矛盾——**它们回答的不是同一个问题**：

> 能力位回答的是「**这家引擎有没有这个能力**」，
> 不是「**omni 今天这条代码路径通不通**」。

那次设不出来的根因在 `acp/open.ts`：续跑那条路把 `session/load` 的回包整个丢掉、不调
`adopt()`，于是 `effortConfig` 停在 `undefined`。**那是 omni 的 bug，不是引擎的缺席。**

所以五档 `why` 里**故意没有**一档叫「omni 接了但在某条路径上失效」，也不许有：
那类东西必须修，用一句归因文案把它讲出来等于把 bug 制度化。判据写死：

- 引擎**从来就没有** → `engine`（交 `checked` 证据）
- 引擎有、omni **一行都没接** → `unwired`
- 引擎有、omni **接了但某条路走不到** → **既不是能力问题，也不填任何 why —— 开 bug 修它**

修好之前那一位照样报 `true`。**报 `unwired` 会是双重错误**——既撒谎（接线是存在的），
又把用户导向「来报一句」，而这件事根本不需要他报，我们已经知道了。

#### 8.4.2 对 §2 修法的一处纠正：不是一行

§2 写的「修法一行」（在 `open.ts:176` 后补一句 `adopt(ctx, loaded)`）**不能照做**：

`adopt()` 的第一句是 `if (id === undefined) throw new Error("没有返回 sessionId，无法继续")`
（`open.ts:219-221`）。而 ACP 的 `session/load` **不保证返回 session 对象**——它的常规形态是
回空、随后靠通知重放。对那样的 agent 补一句 `adopt()`，会把今天这个**静默降级**
变成**续跑当场抛错**，那是更坏的失败。

正确形状是只认领「目录」那一半，不碰 sessionId：续跑路径上 `acpSession` 已经由
`ctx.req.resume` 给定（`:177`），本来就不需要从回包里取。

顺带一处清理：`:180` 的 `void (ctx.state.trust, [])` 是逗号运算符的死代码，一并删掉。

**这条修复的收益不止强度。** 回包丢掉的是一整份目录，续跑的 ACP 会话上同时坏掉四样：

| 丢掉的字段 | 后果 |
| --- | --- |
| `effortConfig` | `applyEffort` 静默 return——不发 RPC、不报错、不发 degraded（本次触发点） |
| `modes` | `applyTrust` 走 `modes.length === 0` 分支直接返回——**续跑会话上切信任档也是空操作**，与 `mode.ts` 刚修掉的那个短路是同一族病 |
| `windowOf` / `contextWindow` | 上下文比例条不画（分母未知） |
| `models` / `modelConfig` | 清单空、换模型退回发 `session/set_model`。kimi 恰好实现了后者，所以「模型能换」——**它是撞对的，不是设计对的** |

最后一行正是这个 bug 难被发现的原因：**它坏掉的四样里，最显眼的那样恰好被巧合救了。**

   登录后重跑 `initialize` → `session/new` → `session/load`，一次可结掉三件：
   `configOptions` 里 thinking 的实际档位词表、`configOptions[id='mode']` 的四档 id

## 10. 明确不做的能力及理由

把「查过了、决定不做」记下来，和做出来一样重要——否则下一个人会重新调研一遍、重新论证一遍、再重新放弃。

| 不做 | 理由 |
| --- | --- |
| **MCP 清单 / 启停 / 登录** | 它不是「给不给入口」的问题：清单是数据、启停是写、登录是流程。一位布尔回答不了任何一样。需要的是一条新的数据通道，位解决不了。（顺带把 `open.ts:34` 的 `mcpServers: never[]` 类型放宽成 `readonly McpServerConfig[]` 并继续传空数组——代价零，收益是「以后接」不再是一次类型重构） |
| **hooks** | omni 已经做对了（`SettingsEnv.tsx` 那一页是全仓「不支持时怎么办」做得最彻底的一处：四家都列、没配的折成一行、三种「空」各说各的话、页尾明写「这三样我没查」），而它走的是读配置文件，不是会话能力 |
| **子 agent / workflow 进度** | 是**事件流**不是能力开关。详见方案甲 |
| **速度档 / service tier** | 两家有独立轴（codex/claude）、**两家把它编进模型名**（kimi 的 `-highspeed`、zcode 的 `-Turbo`）、一家没有。加位会在编进模型名的那两家上画一个诱导性的空控件——用户会以为能在 K3 上开 highspeed。（顺带纠正立项时的假设：被编进模型名的是**速度**，不是强度） |
| **rewind / 就地截断** | **一个 boolean 会造出一个会撒谎的按钮**：同一个「从这里重来」，codex/claude 是分支型（原会话留着），grok/zcode/codex-revert 是就地型（后面几轮真的没了）。它需要的不是一位，是把按钮上的动词换成后果。在文案规则定死之前给这一位是危险的 |
| **删除 / 归档** | 同上，破坏半径差一个数量级：codex archive 可逆、claude `deleteSession` 连 subagents 一起删、**kimi 的 logout 会重写 config.toml**（本轮调研中真实发生过一次事故，把本机登录态与模型配置抹了）。能力表如果只记「支持 / 不支持」，会把这些记成同一格 |
| **音频附件 / 预热 / 结构化输出 / 模型退役提示 / 远程执行环境 / per-MCP 权限覆盖 / 轮次预算** | 一家独有，或说不出 omni 的用户场景。做成通用位的代价是每次新增引擎都要为它表态一次，而五次表态里四次是「不适用」——四个不携带信息的「不适用」 |
| **输出样式 / 人格 / 语言** | claude 的 outputStyle 是一份用户可写的 markdown 文件，codex 的 personality 是一个三档枚举**且按模型而定**，另三家没有。硬凑出的下拉在每一家含义都不同——**这正是「求同」造出来的假抽象**。用户的真实诉求（「别写那么长」）用一句项目说明（AGENTS.md，五家都读）就能解决，成本低一个量级 |
| **轮次耗时 / @ 补全 / 排队 / 导出** | **omni 代偿**：五家一视同仁、根本不问引擎。给它们一个槽位等于诱导下一个人去接五份互不相同、语义还更窄的引擎数据 |
| **额度 / 账号 / 引擎版本 / 可执行文件路径 / 家目录** | 是**值**不是入口（违反判据一）。它们该走一张只读的引擎事实表（诊断页），不该套能力位的壳 |
| **`notifies` 静态字段** | 见 §7.5：它不是引擎的属性，是「omni 握手时报了什么」的函数，用静态字段装它第一天就会填错。语气由运行期出处决定 |
| **`model` / `resume` 两位** | 五家里无分歧（违反判据二）。改成两条渲染规则 / 一处驱动判据修正，见 §6.4 |

## 12. 风险与已知限制

### 12.1 最大的两个风险

**风险一：`engine` 这一档会因为引擎升级而悄悄变成谎，而没有人会去质疑一句「这家不支持」。** 本轮已经抓到四条现存的过期断言（§1.2），以及一次形状变更（kimi 在 Phase 15 之前确实把思考编进 modelId）。缓解有三层：`engine` 档必须交 `checked` 证据串（类型级必填）；诊断页把 `checked` 与 probe 探到的当前引擎版本并排显示，对不上就标「依据来自 X 版，当前是 Y 版」；`unwired` 有 CI 快照。**但没有任何机械手段能阻止一句写对了的话在半年后变错**——这是接受的残余风险。

**风险二：per-engine 注入落不到第三方引擎上，`unwired` 变成兑不了的支票。** `registerAcpEngines` 现在只传四个字段，`engines.json` 进来的引擎拿不到任何适配。本方案在批 3 补齐注入面（§4.6），但仍有两个残余：注入表按**键名**匹配（用户把 `zcode` 改成 `zcode2` 补充就悄悄丢了，退化成全 unknown——不崩，但会静默变哑）；以及 zcode 的**后端版本读不到**，所有「这条方法在这个后端上有没有」的格子只能永远挂 unknown。

### 12.2 已知限制（明确接受）

| 限制 | 为什么接受 |
| --- | --- |
| `Support = true \| Absent` 的对象恒为真，`if (caps.effort)` 类型抓不住（实测编译零报错） | 极性反转（`vocabOf` 返回 undefined 表示「没话可说」）+ host 侧只用 `can()`，覆盖了全部现有读点。不加 eslint 规则：选择器要么误伤诊断页的合法遍历、要么绕得过去 |
| ACP 上 (a) 与 (c) 在线上字节层同构 | kimi 源码原话：「ACP has no 'disabled entry' concept，省略就是线上版的灰掉」。这是协议的硬约束，omni 无法从线上区分。缓解是硬纪律：通用推导只产 `true`/`unknown`，`engine` 只能由 per-engine 写死 |
| `sayWhy()` 的产物不能进 `engine` 档 | `-32601` 同样可能是「omni 发错了方法」——`setup.ts:52-59` 记的那次 ZCode 事故正是这样（一律发规范的 `session/set_model`，而它只实现 `set_config_option`）。所以它只能进 `unknown`，且只在一次真实失败之后成立 |
| **codex 的非审批请求混进审批通道**（`approve.ts:123` 的 `endsWith("requestApproval")` 会命中 `item/permissions/requestApproval`，应答形状不匹配会挂住轮次；认不出一律 `respond({})` 而 elicitation 要必填 `action`） | 本方案不修（不属于能力层），但记账：这是一个**真的会挂住轮次**的 bug，应当单独立项。修法方向是「认不出的服务端请求回 JSON-RPC 错误，不许回空对象」——ACP 驱动已经这么做了（`driver.ts:302-306`），codex 侧照抄即可 |
| **kimi 的 ACP `logout` 是不可逆的破坏性动作** | 本轮调研中一位 agent 为确认方法存在调了它，清掉 OAuth token 并把 `~/.kimi-code/config.toml` 从 1861 字节抹到 277 字节。**omni 永远不该把它做成一颗界面按钮**；这也是「能力表不能只回答『能不能』、还必须能回答『该不该』」的最强论据 |
| claude 的强度回读走未声明 API（`getSettings()`） | 降级本身安全（少显示一个值，不撒谎），但没人会知道它降级了。见 §13 |

## 14. 需要用户拍板的问题

**1. `by-design` 这第五种 why 收不收？**
推荐：**收**。claude 有两格是它（compact / trust），而这两格恰恰是现在编码成 `false`、在界面上与「引擎不支持」不可区分的那两位。退路是 `engine` + 强制 note + 从 `unwired` 快照里排除，但那会稀释 `engine`（查过了确实没有）的定义，下一个人会照着这个先例继续误用。

**2. `compact` 这一位到底问什么？**
推荐：**本次维持现有语义（omni 要不要补入口），但把 grok/zcode 从一刀切的 `false` 改成 `unknown` 并把两条依据写进诊断页；下一轮把它重新定义成「入口从哪来」的三态枚举（omni 补 / 引擎自己的命令 / 没有）。**理由：两家都能压缩、且两家的 `/compact` 都已经在 omni 的命令面板里，`true` 会造出重复入口、`engine` 是谎、而 `unknown` 按「仍然可点」的规则又会给出一个可能 404 的按钮——一位布尔答不了这个问题。

**3. 要不要在 codex 的 initialize 里声明 `experimentalApi`？**
推荐：**先不声明**，把「引擎自发变更收不到」如实记成 `unknown` 而不是 `engine`。收益已实测（`thread/settings/updated` 在 plain 下 0 条、声明后有），但代价是把 omni 绑在 codex 的实验面上。配套必须有：一份「omni 认领了什么」的常量表 + CI 双向断言（已消费的必须认领、认领了的必须消费），否则这类「被 omni 自己的握手挡住」的格子会一直伪装成引擎的属性。

**4. `transcript` 这一位破了收位判据一（「不是一段文案」），破不破例？**
推荐：**破例并写明理由**。它删的是现存的硬规则违规且已过期的字面量，且 `unwired`（去报 bug）与 `engine`（去引擎自己的界面看）对用户是两个不同的下一步。若不破例，替代方案是把那段文案删成一句不点名的通用话，代价是失去 (a)/(b) 区分。

**5. `unknown` 的「仍然可点」要不要无差别套用？**
推荐：**拆成两句**——unknown 对**读**的槽位是「不断言、照常显示」，对**写 / 提供入口**的槽位是「不提供入口 + 诊断页留账」。原规则搬自 `EngineInfo.state` 的 `missing`，那里的语境是引擎选择（灰掉一个其实能用的引擎更糟）；但对 omni 自己提供入口的那类（compact 是典型），照常给按钮就等于把「点了没反应」换个地方复发。

## 15. 与另两份方案的接口

**方案甲（引擎状态可见性 / 侧问 / 侧边栏 / workflow 进度树）**要往这张表里插的行：

- C 域「引擎自报忙闲」——**不做能力位**（它是事件流），但要用本方案的 §7.2 措辞模板：kimi 的「看不到子 agent 活动」正好是 `{why:"engine"}`（源码原话：ACP 会话只订阅 main agent 的事件流）。
- B 域「引擎当前档位回读」——`update.ts:238-247` 收到 `current_mode_update` 只发一条被过滤掉的文字、不写 `state.mode`，这是方案甲的地基修复，本方案不动。
- C 域「侧问 / steer」——`steer` 位由本方案定义与落值（claude=engine、kimi=engine、grok/zcode=unwired），方案甲负责驱动侧实现；接上之后把 `unwired` 改成 `true`。
- 方案甲需要的**持续状态通道**（`engine.status` 不落盘、不进 `LIVE_STATE`、且只在 LOUD 三档下成为一次性横幅，三条性质对「能力受限」全是错的）不在本方案范围，但本方案给出了同一条路的先例：走 `LIVE_STATE` + `liveKey`。

**方案乙（计划/待办展示 / 会话上下文选择器）**：

- G 域「计划 / 待办」——**不做能力位**（就地展示，有计划才画，没有就没有，不构成疑问）。若要接 ACP 的增量计划（`plan_update` / `plan_removed`），需先在握手里认领 `clientCapabilities.plan`——那属于「omni 认领了什么」那张常量表（拍板题 3）。
- H 域「cwd 运行期可改」「额外工作目录」——按本方案的形状加位即可，本次不加。ACP 三家的「开会话时定死」正好是 `{why:"engine"}`；**kimi 那种「传了也静默忽略、只 log warn」尤其需要一句话**，否则它是第三种「点了没反应」。
- D 域「历史往回翻」——zcode 有 `session/load_earlier`、codex 有 cursor，但五家形状四种（数字 offset / 不透明 cursor / 按边界条目 / 分块序号），**不能自己拼页码**。

两份方案往这张表里插行时只需遵守三条：位要过 §6.1 那四条判据；措辞走 §7.2 五个模板；形态走 §7.1 三条判据。**其余都是它们自己的设计。**
