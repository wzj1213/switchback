## 0. 一句话

**omni 的 `renderer ↔ main` 通道本来就是一套远程协议**，只是现在跑在 IPC 上。
手机端的工作不是设计协议，是①换一根管子②补上 IPC 不需要但网络需要的三件事
（按客户端寻址、确认与重发、分片）③写一套手机形状的 UI。

codex 走的是同一条路：远程那层的载荷就是它本地 stdio 上那个 `JSONRPCMessage`，
一个字段都没变。

## 1. 现状盘点

### 1.1 已经有的（不用重写）

| 东西 | 在哪 | 远程能不能直接用 |
| --- | --- | --- |
| `Command` 上行 / `Event` 下行 | `packages/protocol/src/command.ts`、`event.ts` | ✅ 纯 JSON 联合，可直接上网 |
| 序号 + 补发环 | `apps/desktop/src/main/sequence.ts` | ⚠️ 见 §3，环要换成按确认保留 |
| 游标与补洞（纯函数，脱离 React 可测） | `apps/desktop/src/renderer/stream.ts` | ✅ 一行不改地复用 |
| 全量重建 + `resumeAt` 防重防漏 | `main/host.ts:355-407` | ⚠️ 体积见 §5.1 |
| 事件流 → 视图状态的纯归约器 | `@omni/store`（依赖只有 protocol） | ✅ 浏览器里直接跑 |
| 合帧（16ms / 500 条封顶） | `main/batch.ts:4,12` | ✅ 远程还要再粗一档 |
| 出声的三件事（等你批 / 跑完了 / 跑挂了） | `main/attention.ts`，出口收在 `tell()`（`:75`） | ✅ 推送就接在这一个函数上 |

### 1.2 渲染层只从一个洞碰主进程

全仓 `window.omni` 只出现在 12 个文件里，类型是 preload 的真实导出
（`apps/desktop/src/renderer/env.d.ts`，那份手抄的声明已经删过一次）。

**推论**：写一个 WS 版的 `OmniBridge` 垫片，**现有桌面 UI 一行不改就能在手机浏览器里跑**。
挤、丑、按钮小，但功能是全的。这是第 0 步的全部内容，也是 `apps/mobile` 做废时的退路。

### 1.3 为什么不把 host 搬上云服务器

产品前提写在 `README.md:5-7`、`AGENTS.md:54`：**引擎跑自己的原生进程、用自己的鉴权**，
工作区是**这台机器上的仓库**。搬上云意味着在 Linux 上把五家引擎重装重登一遍、
再把代码同步过去——那是「云开发机」，是另一个产品。

codex 的选择一模一样：`codex remote-control start` 起的守护进程跑在**你的机器上**，
手机连的是中继，不是另一台跑着 agent 的机器。

## 2. codex remote-control 是怎么做的（实读源码）

### 2.1 拓扑：本机外拨，中继在云上

```
手机 ChatGPT ──▶ chatgpt.com 后端（中继）◀── wss 外拨 ── 本机 app-server 守护进程
                                                            │
                                                  引擎进程 + 你的仓库
```

本机**不开任何入站端口**。`normalize_remote_control_url`（`protocol.rs:212`）把一个 base URL
展开成五个地址：一个 wss + 四个 https 端点。

### 2.2 注册与配对：四个 HTTP 端点（`protocol.rs:19-88`、`enroll.rs`）

| 端点 | 请求 | 响应 |
| --- | --- | --- |
| `…/server/enroll` | `{name(主机名), os, arch, app_server_version, installation_id}` | `{server_id, environment_id, remote_control_token, expires_at}` |
| `…/server/refresh` | `{server_id, installation_id}` | 续期 |
| `…/server/pair` | `{manual_code: bool}` | `{pairing_code, manual_pairing_code, expires_at}` |
| `…/server/pair/status` | `{pairing_code}` 或 `{manual_pairing_code}`（二选一） | `{claimed: bool}` |

三条细节值得抄：

- **鉴权只认 ChatGPT 登录态，明确拒绝 API key**（`auth.rs:43-48`）。账号是把「这台机器」
  和「那部手机」绑起来的东西。
- **令牌提前 30 秒续期**（`REMOTE_CONTROL_SERVER_TOKEN_REFRESH_SKEW_SECS`，`enroll.rs:29`）。
- **错误预览里要抹掉令牌**——它有一条专门的测试
  （`preview_remote_control_response_body_redacts_server_token`，`enroll.rs:602`），
  响应体预览还截到 4096 字节。日志里漏一次令牌就等于把机器给出去了。

### 2.3 信封协议（`protocol.rs:104-191`）——最值得抄的一段

```
ClientEnvelope { event, client_id, stream_id?, seq_id?, cursor? }
ServerEnvelope { event, client_id, stream_id, seq_id }

ClientEvent = client_message{message: JSONRPCMessage}
            | client_message_chunk{segment_id, segment_count, message_size_bytes, message_chunk_base64}
            | ack{segment_id?}          // 累积确认：seq_id 及以前的全收到了
            | ping
            | client_closed
ServerEvent = server_message | server_message_chunk | ack | pong{status}
```

四个要点：

1. **载荷就是本地那套 `JSONRPCMessage`**。远程不发明新协议，只是换根管子。
2. **`client_id` + `stream_id` 寻址**。多部设备同时连一台机器，各自一条流。
3. **`seq_id` + 客户端累积 `ack`**：发送端只保留**未被确认**的信封，重连后续发。
   重连时还带一个 `x-codex-subscribe-cursor` 请求头从游标续订（`websocket.rs:67,1176`）。
4. **分片带 `segment_id`，`ack` 也带 `segment_id`**，所以重连只重发没确认的那几片。

### 2.4 分片（`segment.rs:17-21`）

| 常量 | 值 |
| --- | --- |
| 目标片大小 | 100 KB |
| 单片上限 | 150 KB |
| 最多片数 | 1024 |
| 重组上限 | 100 MB |
| 同时在装配的消息数 | 128 |

### 2.5 连接维护（`websocket.rs:65-80`、`client_tracker.rs:27-28`）

协议版本 `"3"`；ping 10s；pong 超时 60s；重连退避上限 30s（**到顶后把计数清零重来**，
`next_reconnect_delay`，`websocket.rs:1186`）；连接超时 30s；关闭超时 5s；
客户端空闲 10 分钟回收，每 30s 扫一次。

### 2.6 设备管理面（`app-server/README.md:210-217`）

`remoteControl/enable` `disable` `status/read` `status/changed`
（四态：`disabled` / `connecting` / `connected` / `errored`）、
`pairing/start` `pairing/status`、`client/list` `client/revoke`。

两条设计选择：

- **`serverId` 有意不暴露给客户端**，只给 `environmentId`。
- **`client/list` 和 `client/revoke` 在本地中继关掉、甚至没注册时也能用**——
  那是账号级操作。「手机丢了，而那台 Mac 现在关着」正是最需要吊销的时刻。

### 2.7 URL 白名单（`protocol.rs:193-201, 260-290`）

只认 `https://chatgpt.com`、`*.chatgpt.com`、staging 域，或 localhost 的 http/https。
测试里专门挡掉 `chatgpt.com.evil.com` 和 `evilchatgpt.com`（`protocol.rs:378-400`）。

omni 已经有同一条纪律（`main/update.ts` 的更新源只认 https），但**没有后缀匹配这一坑**。

## 3. 逐条映射：抄什么、不抄什么

| codex | omni 的对应物 | 结论 |
| --- | --- | --- |
| `JSONRPCMessage` 载荷 | `Command` / `Event` | 现成 |
| `seq_id` | `Sealed.seq`（`sequence.ts`） | 现成 |
| 重连游标 | `resync(after)` / `replay.resumeAt` | 现成，语义等价 |
| 客户端 `ack` + 未确认保留 | **固定 5000 条环**（`sequence.ts:46`） | **要改** |
| `client_id` 寻址 | `emit` 广播给所有窗口（`host.ts:68-70`） | **要加 Sink 抽象** |
| 分片 100 KB | 无 | **要加** |
| enroll / pair / refresh | 无 | 要写，但可以简化（见下） |
| `client/list` + `revoke` | 无 | 要写，设置面板一页 |
| URL 白名单 | `update.ts` 只认 https | 扩展一下，补后缀匹配 |
| ping/pong/退避常量 | 无 | 抄数字即可 |
| 独立守护进程 | host 住在 Electron 主进程里 | **结构差异，见 §5.3** |

**一处不抄**：codex 的配对靠 ChatGPT 账号体系，中继替两边做握手。omni 的中继是**你自己的
服务器**，没有现成账号层——所以不抄那一层，直接发设备令牌：配对码在中继上换令牌，
令牌就是身份。少一层，安全性靠「令牌可吊销 + 只有你自己有这台服务器」兜。

## 4. 落地方案

### 第 0 步 · 桥垫片：今天就能在手机上打开（半天）

- **现状**：渲染层只认 `window.omni` 一个全局，类型是 `OmniBridge`（preload 的真实导出）。
- **改成**：写 `apps/desktop/src/renderer/bridge-remote.ts`——同一个接口，底下是 WS。
  页面 URL 带 `?remote=1` 时用它，否则用 preload 注入的那个。
  配 `ssh -R 7788:127.0.0.1:7788 你的服务器` + caddy 反代，手机浏览器直接开。
- **为什么**：在写 `apps/mobile` 之前先回答「远程这件事到底有没有用」。
  而且这是 `apps/mobile` 做废时的退路——它不会白写。
- **动哪儿**：新增 `renderer/bridge-remote.ts`；`main/index.ts` 的 `loadFile` 分支旁边加一条
  开发用的 `loadURL`。
- **风险**：桌面 UI 在手机上要靠捏合缩放；`pickFolder` / `reveal` / `find` 这几条在远程模式下
  必须**显式失败**而不是静默 no-op——`useOmni` 已经有 `bridgeMissing` 这个先例
  （`useOmni.ts:24-28` 的注释写了为什么不能静默）。

### 第 1 步 · Sink 抽象：让「窗口」和「手机」成为同一类东西（半天）

- **现状**：`createOutlet(windows: () => readonly BrowserWindow[], …)`（`host.ts:54`）内部直接
  `win.webContents.send("omni:events", sealed)`（`:68-70`）；`rebuild(attached, target: WebContents)`
  （`:379`）直接 `target.send("omni:replay", …)`（`:404`）。
- **改成**：

  ```ts
  interface Sink {
    id: string                                  // codex 的 client_id
    send: (channel: "omni:events" | "omni:replay", payload: unknown) => void
    alive: () => boolean
  }
  ```

  窗口包一层 `windowSink(win)`，远程连接包一层 `remoteSink(socket)`。
  `createOutlet(sinks: () => readonly Sink[])`，`rebuild(attached, target: Sink)`。
- **为什么**：这一步做完，桌面窗口和手机就是**对等的两个客户端**，而不是「主界面 + 一个
  远程视图」。codex 手机端能看见你在本机 TUI 里跑的那条会话，靠的正是这个——
  两边连的是同一个常驻 app-server。omni 的等价物是主进程里那个 host。
- **动哪儿**：`main/host.ts`（`createOutlet` / `rebuild` / `installBridgeChannels` 里的 resync）、
  `main/index.ts`（`omni:hello` 那段把 `event.sender` 包成 sink）。
- **风险**：**`rebuild` 只发给一个 target 这条规矩必须原样保留**——`host.ts:355-377` 那段注释
  解释了广播出去会让其他早已同步的窗口把整段历史再应用一遍，item 直接翻倍。
  加了 sink 之后这个诱惑更大（「顺手广播给所有客户端多省事」），所以那段注释要跟着搬。

### 第 2 步 · 新包 `@omni/wire`：传输层的规矩（1 天）

- **现状**：序号在 `main/sequence.ts`，补洞在 `renderer/stream.ts`，两边各一份形状声明，
  靠同名对齐。手机端要用同一套，再抄第三份就是三份。
- **改成**：新包 `@omni/wire`，L1（只依赖 protocol），`check-arch.mjs` 的 `LAYER` 表加
  `"@omni/wire": 1`。

  ```
  ## 拥有什么
  - Sealed / Replay / Envelope 的形状
  - 发送端：编号、按 ack 保留未确认、分片
  - 接收端：游标、补洞、重组（stream.ts 那套纯函数搬过来）
  ## 不拥有什么
  - 不拥有传输本身（不建连接、不发 HTTP、不认识 WebSocket）
  - 不拥有鉴权与配对
  - 不拥有事件语义（只搬运，不解释 Event 里有什么）
  ## 已知限制
  - 不做压缩；不做乱序容忍（假设单条连接内有序）
  ```
- **为什么不塞进 `@omni/store`**：store 的 README 明写「不拥有命令」「不拥有持久化格式」；
  而 protocol 的 README 更直接——「本包不做序号与重放，**序号是传输层的事**」。
  缺的正是这个包。
- **风险**：`stream.ts` 现在被 `useOmni.ts` 引用，搬走要跟着改 import。它自己的测试一并搬。

### 第 3 步 · `main/remote.ts`：主进程开一条远程口（1 天）

- **改成**：`http.createServer` + WS 升级，**只 listen `127.0.0.1`**。
  - 连上来先鉴权（配对令牌），再按 sink 注册，先发 `replay`，之后推增量。
  - 收 `{type:"command"}` → `host.dispatch`；收 `{type:"ack", seq}` → 释放保留缓冲；
    收 `ping` → `pong`。
  - 常量照抄 §2.5：ping 10s、pong 超时 60s、空闲 10 分钟回收。
  - 远程 sink 的合帧窗口比窗口那条粗一档（16ms → 100~250ms），`batch.ts` 的
    `MAX_BATCH` 保持。
- **为什么先做 listen 而不是外拨**：配 `ssh -R` 当天就能用，把中继那一步整个推后。
  只 listen 回环意味着**咖啡馆的 wifi 上什么都扫不到**，唯一入口是你自己开的隧道。
- **动哪儿**：新增 `main/remote.ts`；`main/index.ts` 的 `bootstrap` 里按设置起停。
- **风险**：Electron 主进程里起 HTTP 服务，`electron-vite` 的 external 表不用动（`node:http`
  已在 builtinModules 里）。WS 如果用 `ws` 包，要记住 `apps/desktop/README.md` 那条
  ——engine 的运行时依赖必须出现在 app 根目录。`ws` 是纯 JS，能被打进产物，但**要验一次**。

### 第 4 步 · `apps/mobile`：真正的手机界面（2~3 天）

- **改成**：Vite + React，依赖只有 `@omni/protocol` + `@omni/store` + `@omni/wire`（L4，
  **不依赖 host**——它是纯客户端）。**不移植桌面 UI**，只做三屏：
  1. **会话列表**：状态灯（running / waiting_approval / idle / detached）+ 等审批的置顶。
  2. **会话正文**：消息、思考默认折叠、工具行一行一条、diff 折叠。
  3. **审批卡**：命令原文（等宽、可横滚）+ 允许 / 拒绝 + 记忆范围三选一。
     `ApprovalItem` 已经带齐了要显示的东西（`protocol/src/item.ts:114-124`：
     `summary` / `reason` / `rememberHint`）。
- **为什么这三屏**：审批是 agent **唯一**会停下来等人的地方（`attention.ts` 顶上那段注释），
  而人在等的时候多半不在电脑前。这三屏是 60% 的价值、15% 的代码。
- **风险**：`@omni/store` 的 `ViewState` 全量常驻内存且没有淘汰（它自己的 README 写了）。
  手机上更紧，配合 §5.1 的分级 replay 一起解决。

### 第 5 步 · 云上中继 + 配对（1 天）

- **改成**：约 150 行 Node，四个东西：
  - `POST /pair` —— Mac 要一个短期配对码（照 codex：一个扫码用的 + 一个手输的）
  - `POST /claim` —— 手机拿码换长期 client token，绑设备信息
  - `WS /agent`、`WS /client` —— 两条 WS，中继只按 `client_id` 转发帧，不解析载荷
  - caddy：TLS + 托管 PWA 静态文件
  - Mac 侧从「listen」切成「外拨」，带 §2.5 那套退避与心跳。
- **风险**：**中继看得见明文**。服务器是你自己的，v1 接受这一点，但要在设置面板里明说。
  真要端到端，用配对密钥派生一个 AES-GCM 帧密钥，中继只转发密文——那是后话。

### 第 6 步 · 推送：三件事都要推，不只是审批（半天，但价值最高）

- **现状**：`main/attention.ts` 已经把出声这件事做完了——审批挂起、跑完了（15 秒以内的
  不出声）、跑挂了（自己按停的不出声），而且**三条路都汇进同一个 `tell()`**（`:75-78`），
  会话标题也在那儿了（`titles`，`:54`）。出口写死成 `new Notification()`。
- **改成**：`tell()` 里再接一条 Web Push（VAPID）。iOS 16.4+ 的 PWA 加到主屏后能收。
- **为什么三件事都要推**：`attention.ts:11-14` 那段注释说的正是远程场景——
  「交代一件事，然后去干别的」。而人不在电脑前时，**「跑完了」比「等你批」更常发生**：
  一次改动跑四分钟，你在地铁上，没有推送就只能反复掏手机刷。
- **顺带能把那个已知的洞补上**：`attention.ts:29-33` 记着「窗口在前台、但你看的是**另一条**
  会话时收不到任何信号——真要补，得让渲染层把当前选中的会话报上来，那是另一条通道」。
  **§5.1 的分级 replay 本来就需要这条通道**（手机得告诉宿主它正在看哪条，宿主才知道
  该发哪条的正文）。一条通道，两处收益——所以这个洞该在这一步顺手补掉，
  而不是继续记在「已知限制」里。
- **风险**：**必须真机验**。iOS 的 Web Push 有一堆前提（必须加主屏、必须在用户手势里请求
  权限、拒了之后没有第二次机会）。另外 `focused()`（`:57`）这条抑制在远程语境下**是反的**：
  桌面窗口在前台**不代表**你在电脑前，更不代表那部手机该闭嘴。远程推送的抑制判据得换成
  「有没有客户端正在看**这一条**会话」——也就是上面那条新通道。

### 第 7 步 · 远程档位上限 + 设备管理（半天）

- **改成**：`Settings` 加一节 `remote: { enabled, relayUrl, maxTrust }`，
  设置面板加一页设备列表（照 codex 的 `client/list`：显示名、机型、系统、最后活跃时间）+ 吊销。
- **为什么**：手机丢了不该等于在你的仓库里任意执行代码。`maxTrust` 接的是现成的三档矩阵
  ——远程连接上来的会话，档位按 `min(会话档, maxTrust)` 算。

## 5. 四个会咬人的地方

### 5.1 全量重建的体积（唯一一处真正的新设计）

`rebuild`（`host.ts:379-407`）把**每条会话的整份 journal** 读出来发过去。同机 IPC 无所谓，
蜂窝网上不行。而 `sequence.ts` 的 5000 条环，手机进一趟地铁隧道就超了，超了就触发全量——
于是「网不好」的惩罚是「把所有历史重下一遍」，正好在最不该重下的时候。

**改成**：远程 sink 的 replay 分级——先发会话头（`thread.started` / `thread.updated` + 标题
+ 状态），正文只发**当前打开那条**的最后 N 条 item；切会话时按需拉。
这需要客户端把「我正在看哪条」报上来——**同一条通道第 6 步也要用**（见那一节）。

codex 那边不存在这个问题，因为它的 `thread/list` 本来就是分页的、正文按需拉。
**这是 omni 独有的坑**，根源是「全量重建」这个设计假设了一条零成本的本地管子。

### 5.2 Mac 会睡

最典型的「在桌前一切正常、真要用时静默失灵」。

有轮次在跑时挂 `powerSaveBlocker.start("prevent-app-suspension")`。
**但盖上盖子照样会睡**——那要接电源 + `caffeinate -s`。这一条修不干净，
所以要在界面上说实话（照 `README.md` 那些「已知限制」的写法），别假装解决了。

### 5.3 omni 得开着

codex 的 remote-control 跑在**独立守护进程**里（`codex remote-control start` 起的是 app-server
daemon，不是 TUI），所以你关掉终端它照样在。omni 的 host 住在 Electron 主进程里，
`claimSingleInstance`（`main/index.ts:238`）保证只有一个实例——退出应用，远程就断。

v1 接受这一点并在设置里写清楚。真要常驻，得把 host 抽成一个能无头跑的进程，
Electron 只是它的一个客户端——**那正好是第 1 步 Sink 抽象铺好的路**，但不是现在做的事。

### 5.4 安全：这台机器上跑着有写和执行权限的 agent

不可谈判的五条：

1. 本地**只 listen 127.0.0.1**，唯一入口是自己开的隧道 / 自己外拨的连接。
2. 中继地址**只认 https/wss**，且按 codex 那条坑做**后缀匹配**（`.你的域名` 而不是
   `endsWith("你的域名")`——`你的域名.evil.com` 是能注册的）。
3. 配对码短期有效，换出来的设备令牌可吊销，吊销**在 Mac 关着时也要能做**（§2.6）。
4. 日志与错误预览里抹掉令牌（codex 为此专门写了一条测试）。
5. 远程档位上限（第 7 步）。

## 6. 不做什么

- **不做原生 App**（RN / Swift）。PWA 够用，且省掉一整条发布链路。真需要原生再说。
- **不把 host 搬上云**（§1.3）。
- **不做端到端加密**（v1）。中继是你自己的服务器，把这件事说清楚比加密更重要。
- **不做手机端的 diff 编辑、终端、项目管理、拖放排序**。手机上要的是「看一眼、放个行、
  说句话」。
- **不把桌面 UI 改成响应式**。两套界面各自负责各自的形状，第 0 步的垫片只是过渡。
