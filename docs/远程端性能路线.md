## 已经做掉的（都量过前后）

| 做了什么 | 前 | 后 |
| --- | --- | --- |
| 静态产物 gzip（`static.ts`） | 首屏 378.8 KB | **117.2 KB** |
| WebSocket permessage-deflate（`server.ts`） | 一份全量 235 KB 上线 | **71 KB**（3.3×）|
| 出口合并 delta（`host.ts` 的 outlet） | 一次构建刷满 5000 条保留 | 同样条数覆盖的时间长 1~2 个数量级 |
| 补发（catchup）上大小闸门 | 补不动时反复要同一帧，**不会自己好** | 超 192K 码元回 `reset`，走有上限的全量 |
| 分级 replay 换成按大小算（上一轮） | 271 个分片 | **14 个分片** |
| `ItemView` / `Markdown` / `ToolRow` 包 memo | 每帧重解析整屏 Markdown | 只有正在长的那条重画 |
| 折叠的工具行按需拼正文 | 每帧把所有 diff join 一遍 | 点开才拼 |
| 「还没到」和「真的没有」分开 | 基线在路上时说一句假话 | 骨架 / 「正在取…」 |
| service worker 缓存外壳 | 断网点开 = 浏览器错误页 | **omni 的界面还在**（真 kill 掉服务端验过）|
| 长会话先挂 80 条 | 一次挂 200 条 | 80 条 + 「显示更早的 120 条」，点开时视口钉住不跳 |
| 正文被裁时说出来 | 看起来像「从中间开始的」 | 顶上一条「更早的内容没有加载」 |

**合起来：手机第一次打开 614 KB → 188 KB。**

## 下一批：按「改动小 × 用户感受得到」排

### ~~1. 浏览器端一个 `memo` 都没有~~ —— **做了**

`apps/web/src/components/ItemView.tsx:31`、`Markdown.tsx:16`

桌面端 `ItemView` / `Markdown` / `Transcript` 三层都包了 `memo`，注释里有实测数字
（「20 条消息的会话，一帧要花 30ms——帧预算的两倍」）。**web 全目录 grep 不到一个 `memo`。**
而手机单核大约是那台 Mac 的三分之一。

更糟一点：web 的 `Markdown` 把 `remarkPlugins={[remarkGfm]}` 和 `components={{...}}`
写成**行内字面量**——桌面端专门把它们提到模块作用域并写了注释警告，这边一条没抄。

引用稳定性已经核过，`memo` 直接生效不用自定义比较器：`patchItem` 只 `[...list]`
换掉命中那一格，没变的 `Item` 保持同一引用；`send` 是 `useCallback([], )`；`offline` 是布尔。

顺手一起收的：`ToolRow.tsx:49` 的 `bodyOf` **每帧都把所有 diff map+join 一遍，哪怕折叠着**。

### ~~2. 「这条会话还没有内容。」是一句假话~~ —— **做了**

`apps/web/src/screens/Thread.tsx:58`、`screens/Threads.tsx:59`

基线还在路上时，列表写的是「还没有会话。到桌面上新建一条」，正文写的是
「这条会话还没有内容」。两句都是**确定的、错误的**。用户的反应是去查是不是配对掉了，
或者退出重开——而重开会打断正在传的那份全量，回到起点。

改法：`useRemote` 里加一个 `hydrated`（收到过 `replay`、或 hello 走的是续传那条路即为真），
三分：没连上 → 交给 ConnBar；连上但没 hydrated → 骨架屏；hydrated 且真空 → 才说那句话。
骨架还顺带给出高度，全量到达时列表不会整块跳一下。

**这一条和分级 replay 是一对**：分级之后「正文晚一拍到」成了常态，
而界面对这个状态没有表达，只会说一句假话。

### ~~3. service worker 不缓存 app shell~~ —— **做了**

`apps/web/public/sw.js:5`

从主屏点开时，如果 Mac 睡了 / 隧道断了 / 你在电梯里，看到的是**浏览器的错误页**，
而不是 omni 的界面配一条「正在重连…」。后者本来是这套东西最该给的：界面在、
状态说清楚、网一回来自己接上。

改法：无条件 `register('/sw.js')`（推送那条照旧在手势里 subscribe）；
precache 带哈希的 `/assets/*` + 一份 `index.html`；导航请求 stale-while-revalidate，
`/assets/` cache-first，`/api/*` 一律不碰。

### ~~4. 长会话一次性挂载全部 item~~ —— **做了简单那一版**

`apps/web/src/screens/Thread.tsx`

**没上虚拟滚动**：那要接管滚动数学，而这一端还要同时管贴底、「回到底部」
和键盘弹起时的视口变化——在没有真机的情况下做那个，出错的样子是
「滚到一半跳回去」，比慢难受得多。

做的是「先挂最近 80 条 + 显示更早的 N 条」：点开一次就全挂上，之后行为不变。
点开时用 `useLayoutEffect` 把滚动位置按回原处——内容是往上长的，
不补偿的话你正在看的那一段会整块往下跑，而人刚点的是「往上看」。

真开无头浏览器验过：打开 200 条的会话只挂 80 条，按钮写「显示更早的 120 条」，
点开后 scrollTop 正好等于新增内容的高度（视口钉住没动）。

**要不要上真正的虚拟滚动，等真机上用一阵再说**——80 条在手机上挂得动，
而虚拟滚动的复杂度只有在「几千条」时才划算。

### ~~5. 全量是一条不可分割的大帧~~ —— **压缩上线之后不值得做了**

`apps/desktop/src/main/host.ts:415`

14 片全收齐才画第一笔。而画出列表真正需要的只有各会话的头，**加起来一片就装得下**。

评审在这条上纠正了提案的两个说法，值得记下来：
- **不是 14 个往返**（一次性写进同一条 socket），瓶颈是带宽不是 RTT。真实收益是
  「画第一笔要先收 10~20 KB」而不是「先收最坏 570 KB」——好 wifi 上无感，
  蜂窝 1 Mbps 上省 3~4 秒。
- **`reduceHistory` 是清空重建**，不是「只补没有的」。所以基线帧 + N 条正文帧
  必须在**同一次同步写**里灌进 socket，否则中间几秒的 delta 会被随后落地的正文帧抹掉。

**重新算过账，这条现在不值得做了。** 勘察时那 3~4 秒是拿**未压缩的 570 KB** 算的，
而 permessage-deflate 已经把同一份全量压到线上 71 KB：

| | 1 Mbps | 5 Mbps |
| --- | --- | --- |
| 现在收完整份 | 0.55 秒 | 0.11 秒 |
| 拆帧后第一笔 | 0.12 秒 | 0.02 秒 |
| **省下** | **0.44 秒** | **0.09 秒** |

半秒不值得去动这套东西里最脆弱的那一段（基线）——尤其是这一段今天已经出过
一次严重的错。**两个优化重叠，先做了便宜的那个，贵的那个就该重新估价。**

**另外那个「更便宜的一半」是错的，别做。** 判据是：续传只给增量，
而刷新之后客户端的状态是空的——把 501 号往后的增量应用到空状态上，
得到的是一份残缺的界面，而且**不会报错**。要安全就得连整个 `ViewState`
一起持久化，那是几 MB 的同步写（localStorage 会卡主线程）。
记在这里是因为它听起来很便宜，而它的失败方式是静默的数据错乱。

### 6. 不看的会话的 delta 照样推 —— 3 天以上，风险中（**收益已经被削掉一半**）

`apps/desktop/src/main/host.ts:90`

你在手机上读会话 A 等审批，桌面上 B 在跑构建——B 的每一行输出都完整过隧道进你的手机。
分级 replay 把「第一次连上」按会话收窄了，**稳态推送这一半还是全量广播**。

难点在序号：`@omni/wire` 的 `received` 要求 seq 连续，一过滤就出洞，
客户端立刻 resync 把你刚省掉的要回去。两条路：
(a) 对未观察会话的 delta 发**同 seq 的占位事件**（几十字节），切过去时走已有的
`watch` → `thread` 补正文；(b) 每个 sink 一条独立编号的流，代价是账本从
「一份共享缓冲」变成「每客户端一份」。

**(a) 改动小得多，但要把「占位」这个状态贯穿到归约器和界面**——不能让一条会话
显示成空白却没人说为什么（那正是这个项目最讨厌的一类）。

**估价也要跟着降**：压缩之后同样的内容线上小了 3.3×，而合并 delta 之后
一次构建的几百条输出collapse 成一条。剩下的主要是**蜂窝流量**，不再是延迟。
仍然建议先量一天真实数据再决定。

## 量过之后判定「不值得」的

- **`scope.ts` 的 `sizeOf` 每条事件 stringify 一次**：真实数据 3291 条事件跑完 **7 ms**。可以忽略。
- **合帧 16ms 改粗**：拿延迟换带宽，而合并 delta 之后带宽那头已经省下来了；
  在做完 memo 之前也判断不出 16ms 到底卡在哪一端。
- **换 br 压缩**：`createBrotliCompress` 慢一个量级，静态文件这点体积换不来。

## ~~一条没解决的~~（做了）

**正文被裁掉开头这件事，客户端完全不知情**（`scope.ts`）。
超长会话只带尾巴，而界面上没有任何东西说「上面还有」——用户会以为记录丢了。

做法就是当时写的那个最小版：`Replay` 多一个 `trimmed`（哪几条被裁了）、
`thread` 帧多一个 `trimmed` 布尔，转录区顶上画一条
「更早的内容没有加载。完整记录在桌面上。」
**只说实话，不假装能加载**——往上翻加载更早的那条路仍然没做，
而画一个点了没反应的按钮比什么都不画糟。
