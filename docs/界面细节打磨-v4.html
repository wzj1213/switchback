01

圆角：名义上四档，实际上一档

数了一遍全仓 border-radius 的 token 用量：--radius-sm（6px）46 处、--radius（9px）11 处、--radius-lg（13px）5 处。四分之三的圆角是同一个 6——22px 的行内按钮、32px 的侧栏行、一整块代码，用的是同一个值。

用得最多的那一档占比74%46 / 62 处都是 --radius-sm
32px 控件的圆角8px现在 6px —— 高 ÷ 4 应该是 8
阶梯改成6 / 8 / 12 / 16现在 6 / 9 / 13，且 9 和 13 几乎没人用

问题不是数值不好看，是没有规则——每处圆角都是当场拍的，于是最省事的那一档被拍了 46 次。补两条规则，圆角以后就是算出来的，不是判断出来的：

  • 圆角 ≈ 高 ÷ 4。22px 的行内按钮 → 6；32px 的侧栏行和按钮 → 8。这是「看起来一样圆」的条件，不是「数值一样」。
  • 同心：外圆角 = 内圆角 + 内边距。否则内外两条弧的间距在拐角处会突然收紧——这是「看着别扭但说不出哪儿别扭」最常见的一种。

「黑白灰」不等于没有颜色

你给的那张 codex 图里，链接是蓝的、diff 的加减是绿红的——它的界面外壳全是灰的，颜色只出现在内容里。这才是那种「高级」的来源：不是把颜色删光，是颜色只给内容语义（链接、diff、失败），不给 UI 状态（选中、悬停、当前项）。

tokens.css 开头那句「强调色只用于焦点与链接；主按钮用近黑，不用彩色」写的就是这条规矩——它本来就在，这一版只是把值调准，顺便把违反它的地方挑出来。

05

对齐：居中留着，钉死的是宽度

上一稿我把这排胶囊改成了左对齐，理由写的是「它会漂」。会漂是真的，但锅不在居中，在宽度会变。居中本身没毛病——这排东西是浮在输入框上方的一条状态，它不属于任何一条正文左边缘，浮着才对。改成左对齐是把症状连着东西一起删了。

上一稿那个「269 / 274」是我编的

第一稿在这儿写了「计划条在 269，输入框在 274，两条边差 5px」。那两个数是从我自己画的小样里量的，而小样里 .uplan 我随手写成了 max-width:760;margin:0 auto。真实的 plan.css:105 写的是 width: min(var(--content-max), calc(100% - 2 * var(--sp-4)))——本来就是对的。是我的小样有问题，不是应用有问题。小样已经改回真值，上面那张图里计划条和输入框现在是重合的。

真正会漂的只有一样：变更胶囊。.changed{align-items:center} 把它居中，宽度由内容决定。这件事仓库已经防了一半——.changed__pill 上有 font-variant-numeric: tabular-nums，注释写的是「文件数从 9 跳到 10，整枚胶囊左右各挪半格」。

等宽数字管的是每个数字一样宽，管不了位数会变：9 → 10 多一个字符，胶囊照样宽一格；更大的一跳是 Changed.tsx 里 added === 0 时那个 <span> 整个不渲染，一下少掉一截。所以这一条不是新发现，是把已经开了个头的那件事补完。

已经有的tabular-nums管住了「每个数字一样宽」
还差的位数 · 空 span9→10 多一字符；added === 0 时整段不渲染
动的东西1 个 spanChanged.tsx 里给 Stat 包一层定宽

把 Stat 那两枚数字包进一个定宽 span（display:inline-block; min-width:9ch; text-align:right），文件数同理留两位。内容再怎么变，胶囊宽度不变，居中算出来就是同一个 x。居中一个字节都不用动。

顺带一条，同样不改位置

转录区、计划条、排队条三处的宽度算式各写各的：max-width: 760（app-main.css:160）、min(760, 100% - 32px)（plan.css:105）、min(760, 100%)（app-composer.css:191）。窗口宽的时候三者都是 760 居中、完全重合，只有窄到 792 以下才开始各缩各的，差 16–32px。统一成中间那条就行——它是三条里唯一在窄窗口下还留边距的。

三枚并排之后，这一排读起来是一句连贯的话：它在做第 3 步 → 已经改了 5 个文件 → 去审核。现在这三样分在两行、两种形制（居中胶囊 ＋ 通栏卡片），它们的关系得自己在脑子里接。

×（本会话收起计划）从常驻按钮降级进浮层里那一行。它是低频动作，不该在一排常驻胶囊里占一个 22px 的目标——而且它紧挨着「审核」，误点的代价不对称。

代价

当前步只剩个开头，而且 hover 不是所有人都有

  • 当前步的文案整条不显示了。这是选 B 要付的账：通栏那张卡能显示约 40 个汉字，现在一个字都没有——「它在干嘛」完全靠 hover，胶囊只回答「它在动，第 3 步，一共 7 步」。换来的是宽度恒定、永不漂，以及一排里最安静的一枚。如果用起来发现「不点开就完全不知道在干嘛」受不了，退路是 A（带文案 ＋ max-width: 28ch ＋ ellipsis），上面那张小样还留着。
  • hover 是鼠标专属。键盘和触屏没有 hover。所以 hover 只能当预览，真入口必须是点击：点一下钉住（aria-expanded），钉住之后鼠标移开也不收，Esc 收起。不能做成只有 hover——那样计划对键盘用户等于不存在。上面小样演的是预览那一半。
  • 浮层里想滚就得先钉住。七步以上要滚动，而 hover 出来的浮层鼠标一挪出胶囊就没了。PlanSteps 现在 max={8}，超过八步本来就折。
  • 这一排的宽度会变得更爱漂。三枚胶囊都在变宽，整排还是居中的——所以上面 05 那条「定宽」从「小修」升级成这个方案的前提：计划胶囊 max-width ＋ ellipsis，变更胶囊 min-width: 9ch。不做定宽的话，这个方案会让漂移比现在更严重。

一个分支要处理

progressLabel 在 stepProgressOf 拿不到当前序号时返回的是「共 N 步」，不是「第 N / M 步」。胶囊里得认这个分支——显示成 · 7 步，而不是硬凑一个假的当前序号出来。引擎没报的东西，omni 不替它编。

定了 B

那颗标记换成加载圈：转圈说的是「在跑」，不是「跑了多少」

现在 PlanPanel 那颗标记是个字形——in_progress 画 ◐，否则 ○。换成一枚 11px 的环之后，同一个判断能多说一件事：它现在到底动没动。

3 / 7 3 / 7 7 / 7 7 步

1转圈 ＝ 当前步 in_progress，engine 正在跑 2静环 ＝ 当前步只是 pending，没人在动它 3实心 ＝ complete 4拿不到序号时：只有「7 步」，环不转

为什么是转圈，不是进度条

进度条要回答「还剩多少」。omni 不知道一步内部走到哪儿了——引擎报的只有每一步的 status，没有百分比、没有预计时间。画一根按 done / total 填充的条，看着像在说「完成度 43%」，而那是用步数冒充工作量：第 3 步可能是「改一行 CSS」，第 4 步可能是「重写整个转录区」。

转圈只说一件事：它在动。这句话是真的，而且恰好是你盯着它时想知道的那句。

不新立一套动画

仓库里已经有 @keyframes row-spin（900ms linear infinite），侧栏行、构建按钮、冷启动那一圈都用它——这里照用，不另写。跟着它的还有那条规矩：每处 row-spin 都配一段 @media (prefers-reduced-motion: reduce) { animation: none }。

停下来之后剩的是一段 3/4 的弧，和 pending 的整圈仍然分得开——降级之后信息不丢，只是不动了。（把动画关掉再看上面那一排就是这个样子。）

还有一处容易做错：PlanPanel 的 currentStep 是「先找 in_progress，找不到退而取第一个 pending」。所以胶囊里显示的那一步，未必正在跑——比如卡在等你批的时候。这种时候环必须停，一直转就是在说「它在忙」，而它其实在等你。

顺着这一条

浮层里的待办也是环：四个字形换成同一枚环的四个状态

胶囊换了环，浮层里那一列还留着字形就成了两套话。而且这四个字形本身也有问题：○ ◐ ● × 在不同字体里宽度和基线都不一样，那一列 18px 的标记槽会跟着晃。换成同一枚 11px 的环之后，四态直径相同、光学重量相同，标记列一个像素都不动。

这一条会暴露一个已经存在的重复

PlanSteps.tsx 顶上那个 STATUS 表的注释写着「正文卡与常驻面板共用，避免两处把『当前步』画成两套语言」。可 PlanPanel.tsx 自己又画了一遍——它有独立的 plan-panel__mark，独立的 ◐ / ○，连 CSS 都是另一份（plan.css 里 .plan-step__mark[data-status] 和 .plan-panel__mark[data-status] 两组配色各写各的）。它自己那条注释已经失效了，只是没人注意到。

所以这一条真正要做的不是「把 ◐ 换成转圈」，是把标记抽成一个组件，胶囊、浮层、正文里的 PlanCard 三处共用。不抽的话，这次是把两套语言变成两套动画，更糟。

做完的划掉——但它和 dropped 现在的画法撞了

plan.css 里划线现在归 dropped（.plan-step[data-status="dropped"] .plan-step__text { text-decoration: line-through }）。两个状态不能共用同一条最强的信号。

我的建议是划线归 done：待办清单里划掉一条的意思是「做完了」，这个手势比「放弃了」强得多——现在这个映射其实是反直觉的。dropped 改成斜杠环 ＋ 最淡一档 ＋ 不划线，两个状态各有各的独占信号。

还有一条：线只划字，不划环。一条线穿过标记列会把四态糊成一团。线本身也要压——text-decoration-color 取当前色的 55%，不然划掉的那条反而比没划的更抢眼。

抽出来之后还得管一件事：转圈只在真的在跑时转。浮层里同时最多只有一枚 in_progress，但正文里的 PlanCard 是历史快照——那张卡记的是「计划在何时变过」，里面的 in_progress 是当时的状态，不是现在。历史快照里的环不该转，转了就是在说一件早就结束的事正在发生。

顺带一个可以顺手收掉的东西

in_progress 的标记现在是 --accent（蓝）。转圈之后运动已经把「在跑」说完了，颜色是第二遍——按上面 04 那条「颜色只给内容语义，不给 UI 状态」，这一处的蓝可以退成灰。done 的 --ok 绿我建议留着：它和 diff 的加减是同一类，属于内容语义。这一条不影响别的，单独判断就行。

再挖一轮：字号，和数据的展示形态

你点的这两处都查出了东西。字号那条和圆角是同一个病；缓存那条是数据已经在手里，被丢在引擎边界了。

07

字号：一半的界面文字是最小那一档

数了一遍 styles/*.css 里字号 token 的用量：--text-xs（11.5px）91 处、--text-sm（13px）49、--text-code 14、--text-base（14px）只有 9、--text-lg 7、--text-prose 2、--text-xl 1。

最小那档的占比53%91 / 173 处都是 11.5px
--text-base（14px）9 处名义上的控件正文字号，几乎没人用
绕过 token 的硬编码21 处其中 12px 出现 10 次——而 12px 不在这套阶梯里

tokens.css 里那段注释写得很清楚：「上一版整套小了一档，和 codex 并排一放就显得小气……桌面应用的正文没有理由比系统默认（13）还小。」阶梯是抬上去了，分布没跟上——一半的界面文字仍然停在 11.5px，比它自己引的那条 13px 底线还低一档半。

而且那 21 处硬编码里 12px 出现了 10 次，它不是任何一个 token 的值——等于这套界面实际上有第八档字号，没人登记过。

不是整体放大，是把该升的那些升上去

11.5px 是附注的字号：时间戳、token 数、`+A −B`、次级说明。这些留着不动。要挑出来的是被顺手写成 11.5 的正经内容——按钮里的字、下拉里的选项名、设置项的标题（settings.css 一个文件就有 16 处 --text-xs）。它们该是 13。

做法和圆角那条一样：先立规则再过一遍。规则是「要读的是 13，扫一眼的是 11.5」，然后把 12px 那 10 处收进 token。

用量表：百分比藏在 tooltip 里，而标签的宽度会推着右边的按钮走

顶栏那枚 51.9k / 262k，三处可以修，都很小。

  • 百分比只在 title 里。meterOf 算出了 ratio，进度条把它画了出来，可「已用 78%」这句话被放进了 title——要 hover 一秒才出来。而那正是这个控件唯一想说的话。分母是恒定的，每次重绘只有分子在变，让眼睛读两个数去得出一个比例，不如直接把比例写出来。
  • 标签的字符数会变，右边的按钮跟着挪。TopBar.tsx 里顺序是 spacer → ContextMeter → LimitPill → 对比 → 分叉 → …。compact() 在 100k 处换档：99.9k 是 5 个字符，100k 是 4 个——标签一缩，它右边那几颗图标按钮整体左移一格。这和变更胶囊是同一个病，药也一样：.meter__label 给一个 min-width（ch）。tabular-nums 管得住每个数字一样宽，管不住少一个字符。
  • 「本会话累计」也只在 tooltip 里。它和上下文占用是两件事——一个是「这一轮带了多少上去」，一个是「这条会话一共烧了多少」。第二件才是你决定要不要开新会话时看的那个数，而它现在只能 hover 到。
