## 0. 一条总纲压着三份

`AGENTS.md` 的「产品边界」新加的那条，是读这三份方案时唯一需要先记住的东西：

> **omni 与引擎是共建者，不是上下级。**
> 判据：这件事是引擎自己把它当功能暴露出来的，还是 omni 拿它的零件替它攒出来的？
> 后者一律不做——哪怕零件够得着、哪怕体验更好。

它已经改掉过一条结论（方案甲的 codex 侧问，见 §1）。往后每次拿不准，先问这句。

配套三条禁令：不往模型上下文里塞 omni 写的话（照抄厂商原文也算）；不替引擎改它自己的行为；
不给引擎自报的状态叠 omni 的猜测。

## 2. 它们之间的接口

```
                 ┌─────────────────────────────────────┐
   丙  能力适配层 │ Support = true | Absent{why×5}      │  ← 地基
                 │ 缺席时的界面语汇判定表               │
                 └───────┬──────────────────┬──────────┘
                         │ 插行              │ 插行
              ┌──────────▼─────────┐  ┌─────▼──────────────┐
   甲  侧栏    │ modeReadback       │  │ 乙  计划/上下文     │
              │ sideQuestion       │  │ **不插位**（见下）  │
              │ (workflow 进度)     │  └────────────────────┘
              └────────────────────┘
```

- **甲 → 丙**：新增 `modeReadback`、`sideQuestion` 两位，走丙的 `Support` 形状与判定表。
  甲自己的 `Thread.engineState`（一组具名轴）不是能力位，是**数据**，两者不冲突。
- **乙 → 丙**：**乙明确不插位**，理由值得记住——`plan: true` 会撒谎。
  能力位是握手时报的静态值，而「这一轮有没有计划」是动态的（codex 的 `update_plan` 可关、
  claude 的 Task 族被远程 开关控制、kimi 今天一条不发）。乙改成**纯数据驱动**：
  没有 plan item 就不进 DOM。**这条是丙那张表的边界的一个正面例子**，不是例外。
- **丙 §8.4.1 补的那条边界**同时约束甲和乙：能力位回答「这家引擎有没有」，
  不回答「omni 今天这条路径通不通」。后者是 bug，必须修，不许用 why 文案解释掉。

## 3. 一个根，四处症状

三份方案独立跑出来的问题里，有一族共享同一个根：

> **omni 把「我让它去的那一档」当成「它现在在哪一档」显示。**

| 症状 | 位置 | 在哪份 | 状态 |
| --- | --- | --- | --- |
| 引擎自己切档后，界面切回原档是空操作 | `acp/mode.ts` 的短路 | 甲 §2.1 | **已修** `f8ea588` |
| agent 自己换模型后，`Thread.model` 没人改 | `config_option_update` 只 emit 清单 | 甲 §2.1-5 | **已修** `f8ea588` |
| 续跑的 ACP 会话上，强度设不上、**切档是个完全的空控件** | `acp/open.ts` 丢掉 `session/load` 回包 | 丙 §2 / §8.4.2 | **已修** `76962de`，拆成 `adoptCatalogue()` + `adopt()` |
| 引擎报的档位变化被 `LOUD` 静默丢弃 | `store/reduce.ts:165` | 甲 §2.1-1 | 甲的批 1 |

**第三条和前两条是同一族病的第三例**，而且它坏掉的四样里最显眼的那样（换模型）
恰好被巧合救了——这正是它一直没被发现的原因。

## 5. 已拍板（2026-08-19）

| # | 问题 | 决议 | 一句理由 |
| --- | --- | --- | --- |
| 1 | 侧问只剩 claude 一家，还做不做 | **做**，排批 3 | 它是 `Item.lane` 轴的第一个消费者，而 workflow 进度树也要用同一根轴——**用一个小功能把轴验穿，比直接上进度树便宜**。claude 那条是 SDK 原生 `askSideQuestion`，omni 零垫付。另外四家按判定表「留位 + 禁用 + 一句话」，措辞必须说真实原因（「没从 app-server 那扇门出来」），不许写「不支持」 |
| 2 | codex 要不要声明 `experimentalApi` | **声明，但以「认领清单 + CI 双向断言」为硬前置** | 甲丙在这条上是**冲突的**（甲要它换档位回读，丙建议先别）。冲突的实质不是要不要，是**顺序**：丙担心的「被 omni 自己的握手挡住的格子，会伪装成引擎的属性」是真风险，而它给的解药（一份「omni 认领了什么」的常量表 + CI 断言：已消费的必须认领、认领了的必须消费）恰好能消掉它。**没建那张表之前不许声明；建好了就声明。** |
| 3 | 常驻进度浮层第一版做不做 | **做**，排乙的批 3 之后 | 完全数据驱动、跨轮沿用；砍它只需删三个文件，不牵连其余批次 |
| 4 | `by-design` 收不收 | **收** | 不收的话 claude 的 compact/trust 两格只能落 `unwired`，那是一张**永远不会兑**的支票，还会往 CI 欠账清单里塞死条目 |
| 5 | 新建会话首屏 | **做，排最后**，只做「显示上下文 + 换个地方开」 | 不抄起手卡片——那是抄外观，解决不了它原本要解决的问题（Dock 冷启动默认工作区是 home） |
| 6 | 项目改名 | **本版不做** | `SidebarGroup.tsx` 已 196/200，且 `thread.title` 是建会话那刻的快照、改名不跟随，会出现两个名字 |
| 7 | grok 收尾清扫加不加私有判据 | **不加** | 撞总纲第三条（不给引擎自报的状态叠 omni 的猜测）。且判据本身 n=1 |
| 8 | 注不注入 `CLAUDE_CODE_ENABLE_TODO_TOOLS` | **不注入** | 撞总纲第二条（不替引擎改它自己的行为）。用户想要，claude 自己的 settings/env 就能开 |
| 9a | `compact` 这一位问什么 | **维持现有语义**（omni 要不要补入口）；grok/zcode 从 `false` 改 `unknown` | 丙担心的「unknown 会给出一个可能 404 的按钮」**在 9c 拍定之后自动消失**（写类槽位的 unknown 不给入口）。所以「下一轮重定义成三态」降级为**观察项，不排期** |
| 9b | `transcript` 破不破收位判据一 | **破例** | 它删的是**现存的**硬规则违规（`Transcript.tsx:41-46` 硬编码引擎名、且对 codex 已过期）。破例换来删违规，划算 |
| 9c | `unknown` 的「仍然可点」要不要无差别套用 | **拆两句**：读类槽位「不断言、照常显示」；写类 / omni 提供入口的槽位「不给入口 + 诊断页留账」 | 原规则搬自 `EngineInfo.state`，那里的语境是**引擎选择**（灰掉一个能用的引擎更糟）；对 omni 自己提供的入口照常给按钮，等于把「点了没反应」换个地方复发 |

**7、8 两条是被总纲收敛掉的**，不是权衡出来的——留在表里是为了记住它们曾经是开放问题。

**2 和 9c 之间有一条隐含依赖**：9c 定的「写类槽位的 unknown 不给入口」，正是 2 里
「没建认领清单之前不声明 `experimentalApi`」能被接受的原因——那期间 codex 的档位回读
落 `unknown`，界面**不给**一个假的回读指示，而不是给一个永远不更新的。

## 8. kimi 在这台机器上没登录

`kimi acp` 的 `session/new` 直接回 `-32000 Authentication required`，
stderr 是 `no provider configured; complete onboarding via /login`。日志里今天第一条就是
`auth summarize: total=0 oauthProviders=[]`——**不是今天弄坏的，从 7 月起就是这样。**

两个后果：

1. **§6 的 #2 #3 在这台机器上跑不了**，要先 `kimi login`。这不是我该替你做的事。
2. **有一个前提要重新确认**：整件事的起点是「kimi 能选模型、但选不了思考强度」。
   而 kimi 在这台机器上连会话都开不出来。所以那个观察多半来自 **host-b**，
   或者来自 **Kimi 自己的 Web UI**（最初那几张截图确实是 Web UI）。
   **这不影响已修的那个 bug**——它在共用的 ACP 代码里，用 grok 验的，kimi/zcode 同样中招；
   但它影响「omni 上的 kimi 到底什么表现」这一类结论，方案丙 §2 的因果闭环仍然欠着。

## 7. 一处仍然张着的口

`adapter:kimi` 那个 agent 中途 API 断线，§8.4 是我事后手写补的。补的过程里改掉了原方案的
「修法一行」（`adopt()` 遇到不返回 sessionId 的 `session/load` 会当场抛，把静默降级换成硬失败），
并补了 §8.4.1 那条 why 表的边界。**但 kimi 那四位仍然没有证据**，停在 `unknown`——
按丙自己的规则，`unknown` 的界面表现是「入口仍然可点」，所以这不是欠账挂在用户面前，
只是挂在 §6 的表里等一次探测。
