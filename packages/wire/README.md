# @switchback/wire

事件流的**传输层规矩**：编号、按确认保留、分片、游标补洞。**宿主与客户端共用同一份。**

`@switchback/protocol` 的 README 写着「事件流假设有序且不丢，**序号是传输层的事**，本包不做」——
这个包就是那句话里的「传输层」。它不建连接、不发字节，只回答两个问题：
**发送端该留着什么**、**接收端收到的这批能不能应用**。

同机 IPC 上这些规矩也成立，只是代价看不出来；对着网络就全露出来了：
客户端会断、会重连、会掉队，而丢一条事件的后果不是「少显示一条」，
是**状态永久错位且不报错**。

## 拥有什么

- `Sealed` / `Replay` / `ClientFrame` / `ServerFrame` / `ChunkFrame` —— 线上的形状
- `call` / `result`（`CallResult`）与 `WireBytes` —— 远程模式里「调一条宿主通道」的形状。
  不进序号、按 `id` 配对；谁能调哪条不归这里管（见 `docs/远程模式方案.md`）
- `createLedger()` —— 发送端账本：编号 + **按确认保留** + 条数上限
- `replayed` / `received` / `resynced` / `reset` —— 接收端的游标与补洞（纯函数）
- `encodeFrame` / `createReassembler` —— 大帧的切分与重组

### 为什么保留量由「确认到哪」定

上一版是一个固定 5000 条的环。同机 IPC 上够用，对着网络就不对了：
**一次 `pnpm build` 就能刷满 5000 条**，而手机进一趟隧道要几分钟。出隧道时缺口
已经被挤出缓冲，唯一的出路是全量重建——正好在网最差的时候把最贵的事做一遍。

所以改成：`join` 进来的客户端各报各的确认位，**所有人都确认过的才丢**。
没 join 的消费者（桌面窗口那条同机 IPC）不参与下限，照旧靠条数上限兜。
条数上限**压过**确认下限：一个连着却再也不确认的客户端不能把宿主内存拖垮，
代价是它下次走全量——那是对的，掉队到 5000 条以外，补差量本来也不比重建便宜。

## 不拥有什么

- **不拥有传输本身**。不建连接、不认识 WebSocket、不碰 `fetch`、不起服务器。
  线上怎么把这些字符串送过去，是 `apps/desktop/src/main/remote/` 和客户端各自的事。
- **不拥有鉴权与配对**。谁能连上来由宿主那侧决定，本包只处理已经连上的那条流。
- **不拥有事件语义**。它只搬运 `Event`，从不读里面有什么；
  `Event` 该怎么变成界面状态是 `@switchback/store` 的事。
- 不拥有持久化。保留缓冲在内存里，宿主重启就从头数——序号本来就是**本次运行内**的。
- 不拥有时钟。超时与心跳的节奏由调用方定（本包一个计时器都不起）。

## 已知限制

- **保留缓冲按条数算，不按字节算**。一条事件多大不看——估算大小要对每条
  `JSON.stringify` 一次，而这正是最热的路径（`item.delta` 一秒上千条）。
  所以一条 8 MB 的 diff 和一条三个字的 delta 在这里等价。真实的兜底是上游：
  `@switchback/store` 对 shell 输出留尾 8000 字符，`@switchback/journal` 单会话 32 MB 封顶。
- **分片按 UTF-16 码元切，不按字节**。切点只保证不劈开代理对，所以一片的字节数
  最坏是码元数的四倍（全 emoji）。上限因此取得保守，宁可多切几片。
- **同时只装配一条逻辑帧**。换了 `id`、乱了 `index`、或者中间插进一条整帧，
  在装的那条就作废。一条连接上的帧是有序的，同时装两条只可能是对端出了问题——
  与其猜它想干什么，不如让这一帧丢掉并报出去。
- **接收端不做乱序容忍**。序号跳了就攒着去补，不猜「大概是网络乱序，等等看」。
  等看不出对错，补得出来。
- **`leave` 必须调**。一个断开却没被摘掉的客户端会永久钉住保留下限，直到条数上限
  把它顶掉。这一条没有自动兜底（本包不读时钟，判不了「多久没动就算走了」）。
