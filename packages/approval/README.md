# @omni/approval

审批判定器。**omni 是外层策略，引擎自审是内层**——内层弹出的每个权限请求先过这里，
只有判定为 `escalate` 才打断用户。上一版（crew）是「一律 escalate」，实测一小时被打断 20+ 次；
这里的目标是 escalate 占比 **< 5%**。

## 判定管线

```
Request ─→ normalize ─→ redline ─→ memory ─→ trust ─→ Verdict
             │            │          │         │
             │            │          │         └─ 三档矩阵（read-only / auto-edit / full）
             │            │          └─ 会话/项目级记忆规则（不得覆盖红线）
             │            └─ 红线表，优先级最高，不分档位
             └─ 命令切分与路径归一；**解析不了一律 escalate，绝不 allow**
```

## 拥有什么

- `decide(req, state): Verdict` —— 唯一入口，纯函数
- 三档信任矩阵（`trust.ts`）
- 红线表（`redline.ts`）—— 表驱动，每条配正反例
- 命令切分与签名归一（`command.ts`）—— 供记忆规则做模式匹配
- 工具分类表（`classify.ts`）—— 把各家的工具名归一成 read/write/exec/net

## 不拥有什么

- **不拥有任何 IO**。不读文件、不查磁盘是否存在、不发通知、不落盘记忆。
  记忆规则由调用方读出来放进 `SessionState.memory`。
- 不拥有时钟与随机源——需要时间由调用方传入（lint 已禁 `Date.now`）。
- 不拥有沙箱。沙箱是最后一道防线，由宿主施加；本包只回答「该不该做」。
- 不拥有与引擎的通信。把 `Verdict` 翻译成各家的应答格式是 `@omni/engine` 各驱动的事。
- 不拥有 UI 文案排版——`Verdict.reason` 是给**引擎**读的，不是给人读的。

## 已知限制

- **shell 解析是保守近似**。只按 `; && || |` 与换行切分，尊重引号，但**不展开** `$(...)`、
  反引号、变量、`eval`、别名。凡是含这些结构的命令一律判 `escalate`，理由是
  「解析不了的东西不能自动放行」。代价是这类命令会打扰用户，收益是不会静默放行注入。
- **路径判定是纯字符串运算**，不解析符号链接。`worksite` 外的软链指进 `worksite` 会被判成外部；
  反之，`worksite` 内指向外部的软链**判不出来**——这一层交给沙箱兜底。
- 分类表按工具名硬编码。新引擎的新工具名落 `unknown`，`unknown` 在 `auto-edit` 及以下一律
  `escalate`。这是有意的：宁可多问一次，不可漏判。
- **`tool` 认不出来时会按 `toolLabel` 的词根补一次方向**（`NAME_CATEGORY`）。
  这一层是被 ACP 逼出来的：协议里工具的身份是一张短枚举 `kind`，而各家往上映射是
  有损的——实测 kimi 只认十个名字，其余全报 `other`，于是它 k3 那套工具
  （`Shell`、`ReadFile`）在自动编辑档下每条都要弹窗。
  **这张表没有兜底成 allow 的分支**：认不出词根照旧 `unknown`；网络那条排在最前
  （`WebFetch` 同时含 `fetch` 和 `web`）；档位与红线都在它之前，只读档下
  名字认成 `Shell` 也一样 `deny`。代价是词根撞名的工具会被归错方向
  ——比如一个叫 `WriteReport` 的网络工具会被当成写文件。
- 不做速率限制。同一个命令连续请求一百次会被放行一百次；防重复是宿主的事。
