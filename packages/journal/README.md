# @omni/journal

事件落盘与回放。**重启之后会话还在。**

一个会话一个 JSONL 文件，追加式。为什么是追加而不是「存一份状态快照」：
事件流本来就是真源，而 `@omni/store` 的归约器是纯函数——回放一遍就能得到
当时的界面状态，不需要第二套序列化逻辑，也就不会出现「快照和事件对不上」这类问题。

## 拥有什么

- `createRuleStore(dir)` —— 审批记忆的落盘。**和事件日志分开**：
  事件是某一次会话的流水，规则是某个工作区的长期设置，删会话不该把规则一起删了

- `createJournal({ dir })` —— `append` / `read` / `list`
- `codec.ts` —— 事件 ↔ JSONL 的编解码，**纯函数不碰文件系统**，
  落盘格式的正确性能在没有磁盘的情况下被穷举测试
- 落盘取舍：跳过 `item.delta`（冗余，见下）与 `engine.status`（描述的是那一次进程）

## 不拥有什么

- **不拥有事件的语义**。它只管字节进出，不知道 `item.updated` 是什么意思。
- 不拥有回放后的状态——那是 `@omni/store` 的归约器的事。
- 不决定落在哪里。`dir` 由宿主传绝对路径进来；本包不读环境变量、不猜 home。
- 不拥有引擎会话的恢复。磁盘上有的是**历史**，不是活着的进程。

## 已知限制

- **`item.delta` 不落盘。** 每条流式 item 最后都有一条 `item.updated` 带完整内容，
  回放只认最终值，结果一样而文件小一个数量级。代价：回放看不到「逐字冒出来」的过程，
  只能看到最终文本。这是有意的。
- **写入失败一律吞掉并继续。** 磁盘满了、目录被删了，都不该让一个正在跑的会话中断——
  用户宁可丢历史也不愿丢正在进行的工作。
- 单文件上限 32 MB，超过就**停笔**，没有轮转。停笔比无声地把磁盘写满好，
  而且现在**停笔会出声**（`onFull` → 界面上一条「能力受限」横幅）——
  以前是一声不响，那才是真的坑：你以为还在记，其实早就不记了，
  重启之后发现历史断在半个月前，已经补不回来。
  轮转仍然没做，理由是量：**实测这台机器上最大的一个会话日志 2.45 MB / 1545 行**，
  按平均每行 1.4 KB 算，32 MB 约合 24000 条事件——还有 15 倍余量。
  真撞上再做轮转，那时也才知道该按什么维度切。
  **第一次真撞上，撞的不是量，是重复**（2026-08-24）：ACP 驱动把同一条工具调用的
  同一份投影写了 9793 遍，一条 2.7 MB。所以这个上限先当**驱动的哨兵**用——
  它响了先去看是谁在重复写，别急着调大或者加轮转。去重挡在宿主的唯一出口上
  （`host/src/ctx.ts` 的 `echoed`）——那里认得事件的身份，journal 这层不认识
  「一样」这回事，也不该认识：它拿到的是一行已经编好的 JSON。
- 没有压缩、没有索引、没有跨会话查询。会话多到需要索引的时候再说。
- 读的时候整个文件进内存。32 MB 上限之内可接受。
