# @omni/host

会话编制与进程生命周期。**唯一允许做编排的地方**——其余包都只做一件窄事。

宿主拥有 thread / turn 的身份，引擎拥有 item 的身份。这条分工是有意的：
prompt 是宿主发出的，所以宿主知道一轮什么时候开始；引擎知道自己产出了什么，
所以 item 由它铸造 id。`turn.completed` 由引擎发（只有它知道自己什么时候真收工）。

## 拥有什么

- `createHost(deps)` —— 命令分发（`Command` → 引擎）与事件汇聚（引擎 → `Event`）
- 会话注册表：thread id → 活着的 `EngineSession`
- 审批闸（`gate.ts`）：把驱动的 `askUser` 变成一张 transcript 里的审批卡，
  等渲染层的 `approval.resolve` 命令来落定
- **会话状态**（idle / running / waiting_approval / failed）。只有宿主同时看得见
  「提示词发出」「审批挂起」「轮次收工」这三件事，所以状态归它改。
  轮次收工是引擎直接发给渲染层的，宿主看不到——所以在传给驱动的 `emit` 上截了一道
- **事件的唯一出口**（`emit()`）：转发给渲染层 → 落盘 → 旁路观察。
  所有发事件的地方都必须走它，落盘才不会漏
- **旁路的身份与主线闸门**（`item-scope.ts`）：引擎给的 lane id 重铸成 omni 全局 id
  （理由同 item——一条会话会中途换引擎，两家都报 `t1` 时后一条会盖掉前一条），
  item 上的 `lane` 归属跟着重铸；**`kind: "approval"` / `"error"` 的 `lane` 一律剥掉**
  （`mainlineOnly`）。写成运行时闸门而不是文档里的一句话，是因为类型表达不了
  「这两种 kind 不许有这个字段」，而只写在文档里的约束，接第五家引擎时没人会记得
- **回声闸**（`echoed()` / `echoKey()` / `shapeOf()`）：`item.started` / `item.updated` /
  `thread.updated` 三种事件，**除时间戳外和上一条逐字节相同就整条丢掉**。
  丢掉的字节数是零——那样一条对归约器、渲染层、journal 三边都是空操作。
  挡在出口而不是各家驱动里，因为它不只是某一家的毛病：ACP 那条线把同一份工具投影
  翻译出来 9793 遍，而 `thread.updated` 是宿主自己十几处各发一遍的
- **临时会话的生老病死**（`Thread.provisional`）：新建出来先是临时的——引擎照起
  （模型清单、斜杠命令要它才有），但**不落盘、切引擎当场生效、建下一条时把上一条收掉**；
  发出第一句话才转正。界面据此决定它进不进侧栏
- 信任档需要重建原生沙箱时，在空闲状态续接同一引擎句柄重启；运行中不打断、不先写假状态
- 处置：`dispose()` 关掉全部会话，并把还挂着的审批**按拒绝 settle**

## 不拥有什么

- **不拥有审批判定**。判定在 `@omni/approval`，宿主只负责把「需要人」这件事送到界面。
- 不拥有引擎协议。各家的握手与消息翻译在 `@omni/engine`。
- 不拥有视图状态。归约在 `@omni/store`，宿主只发事件。
- 不拥有 UI、IPC 传输。
- 不拥有落盘格式。宿主只是把事件交给 `@omni/journal`，字节怎么排是那边的事。

## 「本轮剩下的都放行」

审批卡下拉里的那一项。它**省掉的是打断，不是判定**，所以三条边界一条都不能松
（`approval.ts` 的 `passes`，测试在 `passturn.test.ts`）：

- **红线照旧逐条问。** 那 8 条正是最不该被一次点击盖掉的；一个能盖掉红线的按钮
  等于把档位机制整个绕过去。驱动因此要把 `verdict.redline` 透传进 `ApprovalAsk`——
  不带的话宿主分不出「档位升级上来的普通请求」和「凭据读取」。
- **存的是轮次 id，不是布尔。** 失效因此不需要任何人记得去清：下一轮 id 不一样，
  比较自然就不成立了。布尔要在 `turn.completed`、被打断、切引擎、会话回收四处各清一次。
- **armed 之后不发卡。** 再弹一张「已自动允许」的卡，等于把用户刚想省掉的打断
  原样还回去。做了什么在工具行里照样看得见，而且 `Thread.passTurn` 会让界面
  亮一枚「本轮已放行」——这个状态不该只活在宿主内存里。

## 已知限制

- **不做背压**。`emit` 必须同步返回得比引擎产出快，否则事件在内存里堆积。
- **回声闸只认三种事件，而且只比对上一条。** `item.delta` 永远放行（两条一样的增量是
  两次真的追加）；`turn.*` / `thread.started` 描述的是一次发生，不是一份现状；
  `LIVE_STATE` 那几种自己就按键留最后一条。A → B → A 会发三条，因为记的是
  「上一次发出去的样子」，不是见过的所有样子。指纹每轮清一次（`turn.completed`），
  所以驻留量是一轮的 item 数——代价是跨轮的重复各会漏过一条，那是一条不是一万条。
- **它挡的是症状，不是病灶。** 驱动或宿主自己在重复发事件仍然是 bug：白写的
  `JSON.stringify` 和 `synthDiff` 都发生在这道闸门之前。闸门存在的意义是
  **32 MB 那条硬线后面是整条会话不再落盘**，不能等每一处都自觉。
- **同时活着的引擎会话有上限（默认 4），超了就把最久没动的空闲会话收掉**，
  标成 `detached`，点「继续」接回来（记录、句柄都不动）。
  量出来的（这台机器，codex）：**7 条会话 28 个进程 1.83 GB；上限 4 之后
  16 个进程 1.06 GB**。重点不是省了 42%，是从「开几条涨几条」变成了有上限。
  三种绝不收：正在跑的、等着审批的、没有引擎句柄的（那种收掉就回不来了）。
- **回放出来的会话要点一下「继续」才接得回引擎。** 磁盘上有的是历史，
  引擎那边的对话记忆要靠 `engineHandle` 续跑才回得来。没有句柄的旧记录只能读——
  这时**宁可报错也不静默新建**：起一个全新会话却看着像接上了，是最坏的结果。
- **记忆规则不做跨工作区共享**。`project` 级规则按工作区路径分文件存；
  换一个目录就要重新勾一次。全局级还没有——它的风险面比 project 大得多，
  值得单独设计而不是顺手加一档。
- **接力（L2）不搬运模型上下文，也不注入摘要。** 各家原生会话格式不通；
  omni 只在 `Thread.segments` 里保存原始记录路径并展示在时间线。
  需要另一家复核时，由用户明确给路径、让它用自己的文件能力读取。
- **接力之后旧引擎的进程就没了**，但那条会话还回得去：每一家的句柄各存各的
  （`Thread.segments`），切回去续的是它自己那条。代价是切回去要重新起一次进程。
- **换过去的那家起不来时，会原样退回旧那家**（旧进程要等新的起来才停）。
  退回之后引擎下拉上显示的还是旧那家——错误由横幅说明，不假装换成了。
